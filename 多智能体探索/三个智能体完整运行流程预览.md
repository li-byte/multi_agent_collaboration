# 三个智能体完整运行流程预览

最后修改时间：2026-10-08 17:33:37（北京时间，UTC+08:00）

本预览模拟三个智能体完成一次用户请求的全过程。使用 Mermaid 时序图表示消息、状态提交与等待关系，所有名称、时间和数据均为演示设定。本文独立阅读，不依赖其他设计文档。

## 1 模拟场景与角色

用户请求：“分析 9 月订单收入，解释相较 8 月的变化，输出带数据依据的报告。”

授权边界：只读订单数据，可以生成报告，不修改业务数据库、不自动发送报告。验收要求：统一人民币口径、排除取消订单、明确退款处理、引用查询与数据快照；结论必须与计算结果一致。

三个智能体分别为：

| 智能体 | 职责 | 本次产出 |
| --- | --- | --- |
| A 主智能体 | 理解用户目标、规划子任务、分配执行、处理反馈、整合报告 | 计划、有效决策、最终报告 |
| B 执行智能体 | 读取任务和输入，调用查询及计算工具，提交候选结果 | 数据口径说明、指标文件、解释草稿 |
| C 评估智能体 | 核对原始证据及具体版本，执行验收，决定通过或退回 | 结构化评估与总体报告验收 |

协调 API、PostgreSQL、消息总线、工具和产物存储是基础设施，不是额外智能体。租约回收和通知派发由协调服务的后台任务执行。

本次只有一个执行智能体，因此子任务由 B 依次执行，A 和 C 同时承担调度与审核职责。三个角色形成流水线，不把“有三个智能体”误解为三个子任务必须并行。

## 2 子任务与共享记录

全局请求为 G1，项目为 P1；初始计划版本为 1，有效决策为 D1。

| 任务 | 输入与依赖 | 输出 | 验收重点 |
| --- | --- | --- | --- |
| T1 确定收入口径 | 用户约束、订单字段说明，无前置任务 | 口径文件 R1 | 取消订单排除、退款规则和时间范围明确 |
| T2 计算指标 | T1 completed、同一数据快照 S1 | 指标文件 R2 | 月收入、环比及查询证据可复核 |
| T3 解释变化 | T2 completed、R1 和 R2 | 解释草稿 R3 | 原因有证据，推测单独标识 |
| T4 最终整合 | T1、T2、T3 completed | 报告 R4，由 A 执行 | 总体目标完整、结论一致、引用齐全 |

T4 的执行者为 A，评估者仍为 C。A 对自身汇总结果不能直接宣布完成。

交接对象包含 global_task_id、task_id、attempt_id、输入快照、证据引用、假设、已排除方向、权限、结果引用和验收规则。所有产物引用指向不可变内容，并带内容摘要。

任务工作流为 pending → running → submitted → completed。结论另标记 candidate、verified、conflict 或 rejected。未通过或需要人工处理时不允许下游领取。

## 3 正常运行的完整时序

图中的“同事务”步骤同时保存共享状态、命令回执和 Outbox 事件。总线至少一次交付；接收者读取当前状态后行动，不直接依据通知正文宣布完成。

```mermaid
sequenceDiagram
    actor U as 用户
    participant A as A 主智能体
    participant B as B 执行智能体
    participant C as C 评估智能体
    participant S as 协调服务
    participant P as PostgreSQL
    participant M as 消息总线
    participant T as 查询与计算工具
    participant O as 不可变产物存储

    U->>A: 分析收入变化并形成有依据的报告
    A->>A: 明确授权和标准，拆分 T1 至 T4
    A->>S: 创建 G1 计划、依赖、分配和决策 D1
    S->>P: 锁项目，校验无环及权限，同事务保存计划和事件
    P-->>S: 提交成功
    S-->>A: 计划版本 1，任务 ID 和命令回执
    S->>M: Outbox 发布 T1 ready
    M-->>B: T1 可执行通知
    B->>S: 读取 T1、验收标准和输入快照
    B->>S: claim T1，携带任务版本和稳定命令 ID
    S->>P: 校验指定执行者，创建 attempt a1、token 1 和租约
    S-->>B: 执行授权和最新任务版本
    B->>T: 读取字段说明与数据快照 S1
    T-->>B: 字段、数据范围及工具证据
    B->>O: 保存口径文件 R1 和摘要
    O-->>B: 不可变 result_ref
    B->>S: submit T1，输入版本、证据、R1、a1 和 token 1
    S->>P: 校验租约及版本，保存 submitted，关闭执行租约
    S-->>B: 候选结果已提交
    S->>M: Outbox 发布 result_submitted
    M-->>C: T1 待评估
    C->>S: 读取当前候选、标准和证据引用
    C->>O: 获取精确摘要对应的 R1
    C->>C: 核对收入口径与用户约束
    C->>S: accept T1，评估通过、结论 verified、next_action continue
    S->>P: 再校验候选和基准，同事务保存 completed 及评估事件
    S->>M: 发布 evaluation_finished
    M-->>A: T1 评估已完成
    A->>S: 读取 T1 completed，确认 T2 依赖满足
    A->>S: 调度 T2
    S->>M: 发布 T2 ready

    loop T2 计算指标与 T3 解释变化，按依赖顺序执行
        M-->>B: 任务 ready
        B->>S: 读取基准并领取任务，获得新 attempt 和租约
        B->>T: 在固定输入上查询或计算
        T-->>B: 工具结果和原始证据
        opt 执行超过续租周期
            B->>S: renew 当前 attempt 和 token
            S->>P: 校验执行权后延长 lease_until
            S-->>B: 续租确认
        end
        B->>O: 保存候选产物及摘要
        B->>S: submit 结果、证据及相关版本
        S->>P: 校验后保存 submitted 和 Outbox
        S->>M: 发布 result_submitted
        M-->>C: 待评估通知
        C->>S: 读取候选版本及上游有效结果
        C->>T: 复核查询或执行验收检查
        T-->>C: 验证结果、退出状态及证据
        C->>S: accept，通过并记录评估依据
        S->>P: 保存 completed 和结论状态
        S->>M: 发布 evaluation_finished
        M-->>A: 评估完成
        A->>S: 读取最新状态，推进下一任务
    end

    A->>S: claim T4，确认 T1 至 T3 均有效完成
    S-->>A: 汇总任务执行授权
    A->>O: 读取 R1、R2、R3，生成最终报告 R4
    A->>S: submit T4，绑定上游版本与 R4 摘要
    S->>P: 保存 submitted 和 Outbox
    S->>M: 发布 T4 result_submitted
    M-->>C: 最终报告待验收
    C->>S: 读取 T4、原始用户目标及有效决策
    C->>O: 读取 R4，核对完整性、数字、引用和推测标识
    C->>S: accept T4，总体目标验收通过
    S->>P: 保存 T4 completed 和最终评估
    S->>M: 发布 evaluation_finished
    M-->>A: 最终验收完成
    A->>S: 重新读取必要任务和最终结果的有效状态
    S-->>A: T1 至 T4 completed，无未决冲突或阻塞
    A-->>U: 返回报告 R4，说明数据基准和结论依据
```

## 4 同一次运行中的验收返工

假设 T2 的第一份产物未扣除退款。C 否决后，T3 仍未就绪；A 安排 B 修正 T2，不重做已通过的 T1。

```mermaid
sequenceDiagram
    participant A as A 主智能体
    participant B as B 执行智能体
    participant C as C 评估智能体
    participant S as 协调服务
    participant M as 消息总线

    C->>S: reject T2，退款遗漏，claim rejected，next_action retry
    S->>S: 同事务保存失败证据，T2 回 pending，T3 仍 blocked
    S->>M: 发布 evaluation_finished
    M-->>A: T2 未通过
    A->>S: 读取失败项，确认标准正确、只需修正执行
    A->>S: 重新调度 T2
    M-->>B: T2 ready
    B->>S: claim，获得新 attempt 和更高 token
    B->>B: 复用 T1 口径，重新计算退款后的收入
    B->>S: 提交新的 R2 和证据，不覆盖旧候选引用
    S->>M: 发布 result_submitted
    M-->>C: 新候选待评估
    C->>S: 读取新版本并复核，accept T2
    S->>M: 发布 evaluation_finished
    M-->>A: T2 completed
    A->>S: 确认依赖满足，再调度 T3
```

如果 C 发现原标准本身有歧义，则返回 change_route、narrow_scope 或 human_required，设置 dispatch_block。A 明确处理并批准变更后才解除阻塞；不能通过反复重试绕过问题。

## 5 租约到期与迟到结果

仍然只有 A、B、C 三个智能体。这里模拟 B 的旧运行失联，再由 B 恢复后的新执行尝试接管；attempt 变化不等于增加智能体数量。C 始终负责评估，不临时充当执行者。

```mermaid
sequenceDiagram
    participant A as A 主智能体
    participant B as B 执行智能体
    participant S as 协调服务与回收器
    participant P as PostgreSQL
    participant M as 消息总线

    B->>S: claim T2
    S-->>B: attempt a2，token 2，租约 60 秒
    Note over B,S: B 暂停或断线，未能续租
    S->>P: 锁项目，检查租约到期与外部动作记录
    alt 没有未决外部写动作
        S->>P: 撤销 a2，T2 回 pending，增加版本并保存事件
        S->>M: 发布 lease_expired
        M-->>A: T2 执行权已撤销
        A->>S: 读取恢复状态，重新分配 T2 给 B
        B->>S: 恢复后读取并 claim T2
        S-->>B: 新 attempt a3，token 3
        B->>S: 旧执行回调迟到，携带 a2 和 token 2
        S-->>B: FENCED，旧结果不得写入当前状态
        B->>S: a3 计算完成，提交当前基准上的新结果
        S-->>B: submitted，等待 C 评估
    else 存在 dispatched 或 unknown 外部写动作
        S->>P: 撤销旧授权，设置 recovery_required 和资源阻塞
        S->>M: 发布恢复处理通知
        M-->>A: 禁止重新派发写动作，先核查远端
        A->>S: 请求回查或人工处理
        Note over A,P: 证据确认动作已完成或可安全重放后，才解除阻塞
    end
```

本场景只读业务数据，正常情况下进入第一分支。第二分支说明如果以后增加报告发送或业务写操作，接管不能仅依据租约到期；旧远端请求可能仍在执行。

## 6 通知重复与提交响应丢失

command_id 防止数据库命令重复生效，event_id 防止通知重复处理。它们均不能替代外部业务动作的幂等键。

```mermaid
sequenceDiagram
    participant B as B 执行智能体
    participant S as 协调服务
    participant P as PostgreSQL
    participant M as 消息总线
    participant C as C 评估智能体

    B->>S: submit command X，稳定请求正文
    S->>P: 同事务保存候选、回执 X 和 Outbox
    P-->>S: COMMIT 成功
    Note over B,S: 返回响应途中断线，B 不知道结果
    B->>S: 使用相同 command X 和正文重试
    S->>P: 查询已提交回执 X
    S-->>B: 返回原结果，不再次修改任务
    S->>M: 发布 event E
    M-->>C: 第一次投递 E
    C->>S: 读取候选，登记待评估工作并去重
    M-->>C: 重复投递 E
    C->>S: 查询同一 consumer 的 E 处理记录
    S-->>C: 已登记，复用既有待评估工作
    C->>S: 以稳定验收命令提交评估结果
    S->>P: 校验版本，同事务保存评估和后续通知
```

登记待评估工作与 inbox 去重必须共同持久化，不能先标记消息已处理、再启动尚未记录的工作。评估调用失败时恢复这一待评估步骤；协调服务周期扫描 submitted 任务作为通知恢复保障。

## 7 运行结束时应看到什么

| 检查项 | 本次成功结束的状态 |
| --- | --- |
| 用户目标 | 原始要求及授权边界可查 |
| 任务图 | T1 → T2 → T3，T1、T2、T3 → T4，依赖无环 |
| 任务状态 | 必要任务全部 completed，且当前依据仍有效 |
| 产物 | R1 至 R4 有不可变引用、摘要和输入基准 |
| 评估 | 每项评估绑定精确候选版本，保留验证证据 |
| 结论 | 必要结论 verified，推测显式标识，无未决 conflict |
| 执行权 | 已提交任务无活动执行租约，旧 attempt 不能再提交 |
| 恢复事项 | 无 recovery_required、human_required 或未确认写动作 |
| 最终答复 | A 返回经过 C 总体验收的 R4，而非拼接未验证草稿 |

该预览的关键是：A 决定工作如何推进，B 产生候选结果，C 检查是否达到标准；共享服务记录与校验事实，租约限制执行权，消息总线提醒各层继续工作。三者可以异步运行，但有效状态只能通过统一提交协议改变。
