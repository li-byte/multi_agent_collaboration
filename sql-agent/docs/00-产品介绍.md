## 一、产品是什么

**你说一句中文，它把这句话变成对数据库的操作 —— 先校验、再执行，危险的停下等你点头，全程留痕、花费可查。**

| | |
| --- | --- |
| **一句话** | 面向数据操作的自然语言入口 |
| **形态** | 一个网页对话界面（背后是一套多智能体协作链路 + 一本可回放的账） |
| **输入** | 中文提问（只能提问，不能贴 SQL —— 见第六节） |
| **输出** | 数据本身（一张真表），或一条"我为什么不能做"的说明 |
| **不输出** | 猜测、编造、"已处理 0 个操作"这种说了等于没说的话 |

### 30 秒版本

> 业务同事想问数据，今天要么排队等分析师，要么让大模型直接连库 —— 前者慢，后者不敢用：
> 模型会编字段名、会写出不带条件的 `DELETE`，改完谁也不知道改了什么。
>
> 我们把这件事做成一条**有护栏的链路**：六个智能体分工（判意图 / 写 SQL / 校验 / 执行 / 修正 / 汇总），
> 关键的几步不交给模型拍板 —— 没校验过的 SQL 到不了执行器，删除必须有人点确认，
> 越界请求直接拒绝并给替代方案。多步问题会一步一步走，后一步用得上前面真查出来的值，而不是各查各的。
> 每一轮花了多少次调用、多少 token，界面上能逐条查到。

### 三条定位边界（避免误期待）

| 它不是 | 因为 |
| --- | --- |
| **不是 BI / 报表工具** | 不做看板、不做定时任务、不做指标沉淀。它解决"临时想起一个问题"，不解决"每天看同一张图" |
| **不是数据库客户端** | 不面向 DBA 写复杂 SQL。用户不会写 SQL 才是它的存在理由 |
| **不是"让 AI 接管数据库"** | 是"AI 提出动作 + 运行时守边界 + 人点确认"。它的价值不在于自动化程度高，在于**敢让人用** |

## 二、为什么需要它：三个问题

### 问题 ① 想用数据，但不会写 SQL

| | |
| --- | --- |
| **今天的做法** | 提需求给数据分析师排队；或者自己现学 `JOIN`；或者放弃，凭感觉决策 |
| **代价** | 一个"北京客户订单总额是多少"的问题，等半天到一天；等待成本高到很多人干脆不问 |
| **我们的做法** | 一句话提问 → 几十秒内拿到一张表；口径变了就追问一句，不用重新提需求 |
| **用户感知** | 答复里是**真数据表格**，不是「查询返回 8 行」这种等于没回答的摘要 |

### 问题 ② 敢让模型直连数据库吗

| | |
| --- | --- |
| **今天的做法** | 给模型一个数据库连接，让它自己写自己执行 |
| **代价** | 三类事故：**编造表名字段名**（语法没错、跑出来是错的）、**危险的写操作**（漏 `WHERE` 的全表更新）、**不可追溯**（改了哪几行、谁点的、花了多少，事后说不清） |
| **我们的做法** | 四层防线（见表）+ 高危操作人工确认 + 每一步落账 |
| **用户感知** | 危险请求会被**明确拒绝并解释原因**，而不是执行完再道歉；需要确认的操作会**停下等你**，卡片上写清风险、涉及的表、预估影响行数 |

### 问题 ③ 多步问题，三步各查各的（本产品真正想解决的问题）

这是多智能体最典型的假成功，也是这套系统最初被做出来的原因：

```
用户：先找出库存小于 10 的商品，再看这些商品都有哪些订单，最后统计涉及多少客户
  ↓
朴素做法：拆成 3 个任务，各查各的
  st-1 查出商品 id = 1、3、5…
  st-2 不知道 st-1 的结果 → 自己又从全表捞一遍订单
  st-3 同样自己捞一遍客户
  ↓
每一条链单独看都"跑通了"、都成功、都有数据 —— 合起来回答的却不是同一个问题
```

| | |
| --- | --- |
| **代价** | 数字对不上、结论不可信，而且**看不出哪里错了**（每一步都是"成功"）。这类错误比报错危险得多 |
| **我们的做法** | 每一步真跑过的事实写进**共享记忆**（带来源，可回查），交接时按结构给全，下一步直接用上一步的具体值；每做完一步回到规划器**复查**：继续 / 调整后续 / 到此为止 |
| **用户感知** | 界面上看得到 `🧠 写入共享记忆 · sql_id=44 · 可复用实体：products.id = 1、3、5…` 和 `🔁 规划器复查`，连续性不是一句承诺，是**事件流里的事实** |

## 三、目标用户

| 角色 | 想做什么 | 产品给什么 | 他最在意 |
| --- | --- | --- | --- |
| **业务运营 / 产品经理**（主用户） | 临时问数、批量订正一批数据 | 一句话提问、表格答复、危险操作要他点一下 | 快、看得懂、别改错 |
| **数据分析师**（次用户） | 快速取一版数、验证一个口径 | 免写脚本的取数入口 + 生成的 SQL 可读可复用 | 口径准确、能拿走 SQL |
| **数据 / 安全负责人**（治理侧） | 敢放开这个入口 | 权限上就做不了 DDL、全程审计、消耗可查 | 拦得住、查得到、说到做到 |
| **研发 / 评审**（评估者） | 判断这套协作是否可信 | 时序图、数据流转链路、原始状态结构、离线自检结果 | 别只会说"我们做了多智能体" |

### 典型场景

| 场景 | 用户怎么说 | 产品做什么 | 用户看到什么 |
| --- | --- | --- | --- |
| **只读问数** | 帮我查一下北京客户的订单总额，按金额从高到低排序 | 规划 → 选表 → 生成 → 校验 → 执行 → 汇总 | 一张 Markdown 真表格 |
| **批量订正** | 把所有库存少于 10 的商品库存补到 20 | 生成带 `WHERE` 的 `UPDATE` → 校验 → 执行 | 影响行数 + 改了哪张表（会话列表里标 `✎ 改 products 3 行`） |
| **高危删除** | 删掉所有已取消的订单 | 判为"需确认" → 暂停 | 确认卡片：风险级别、涉及表、预估影响行数、**级联删除提醒** |
| **越界请求** | 帮我给 customers 表加一个字段，再把它清空 | 判为越界（DDL）→ 拒绝 + 给替代做法 | 一段说明：为什么不行、可以改成什么 |
| **危险请求** | 帮我删掉 orders 表 | 静态防线判禁止 | 拒绝，不产生任何 SQL |
| **闲聊** | 你好，你能做什么？ | 判 `chat`，不进生成/执行 | 一句话回答，**不会**回"已处理 0 个操作" |

## 四、能力地图

| 能力 | 用户看到什么 | 一句话凭什么 |
| --- | --- | --- |
| **一句话提问** | 输入框 + 「试试」示例 | 规划器先判这一句到底想要什么 |
| **先判意图** | 聊天 / 查库 / 拒绝，三种去向 | 模式只有 `chat` 和 `execute` 两种，不搞花活 |
| **多轮追问** | 左栏一个会话一条，回放所有轮次 | 上一轮**实际执行过的 SQL** 会带给规划器，所以"那再按城市分组看看"能接上 |
| **多步任务** | 拆成 `st-1`/`st-2`/`st-3`，一步一停 | 串行推进 + 每步复查（串行正是复查能成立的前提） |
| **每步先校验** | 校验项逐条列出 | 校验器**零数据库操作**，但表和字段必须对得上系统目录 |
| **修正闭环** | `第 2 轮` 折叠区里是数据库原话 | 拿数据库真实报错重写；已试过并失败的 SQL 会喂回去，**明令不许重复** |
| **无进展就停** | `⏹ 已停止重试` + 摊开两版失败 SQL | 同一条 SQL 失败 ≥2 次 / 同一错误连现 ≥2 次 → 主动停止，不耗轮次 |
| **人工确认** | 确认卡片 + 级联提醒 | `interrupt()` 真暂停；点取消**一行都不改** |
| **结果交付** | 真表格，不是"返回 N 行" | 提示词里写死：不许只写行数不给数据 |
| **过程可见** | 时序图 / 数据流转 / 原始结构 | 全部来自事件表，刷新页面依然完整、可回放 |
| **消耗可见** | 顶栏实时 `消耗 6 次 · 10,198 tok` + 清单页 | token 是**响应里的真数**，不按字符数估算 |
| **会话账** | `✎ 改 orders 4 行 · 已完成 · 3 轮对话`；整个会话能**导出成一个独立网页**（给同事看 / 打印成 PDF，不依赖任何东西） | 摘要直接来自 SQL 审计表（只统计真正执行成功的） |
| **换一套表** | 换文件 / 改配置 / 调接口热换 | 表信息是**数据不是代码**，验证逻辑里零硬编码 |

## 五、一次典型使用旅程

```
① 打开页面
   左栏是历史会话（按最后活动时间倒序，一眼看出哪次真的改了数据）

② 提问
   「先找出库存小于 10 的商品，再看这些商品都有哪些订单，最后统计涉及多少客户」

③ 看着它一步步走（对话流里每步都有气泡，可以折叠）
   规划器  □ 判 mode=execute · 危险/越界评估通过 · 拆出 3 个子任务（后两个依赖前一个）
   生成    □ 第一层选表 products → 第二层写出 SELECT ... WHERE stock < 10
   校验    □ 6 条校验项逐条通过（含按目录核对表与字段）
   执行    □ 返回 10 行 · 🧠 写入共享记忆 · 可复用实体 products.id = 1、3、5、9…
   规划器  🔁 复查：剩余计划不变，继续做 st-2

④ 想看清楚的时候，切三个视图
   📊 时序图    7 条生命线，谁交给谁、哪里被暂停等你确认
   🔀 数据流转  每一次交接**具体传了什么内容**（选中的表 / SQL / 校验项 / 记忆 / 确认请求）
               卡片底部还能展开**原样落库的完整结构**（含只存在于状态里的 EXPLAIN 计划树）
   💸 消耗清单  这一轮 6 次调用、10,198 token、缓存命中 4,096、按智能体/按步骤拆分

⑤ 需要他点头的时候，停下来
   ⏸ 需要你确认后才执行 —— DELETE FROM orders WHERE status = '已取消'
      风险：需确认（DELETE）｜ 涉及表：orders ｜ 预估影响：3 行
      ⚠ orders 的删除会级联删除 order_items.order_id
      [ 确认执行 ]  [ 取消 ]        ← 取消则一行都不改，审计停在"等待确认"

⑥ 交付
   答复是数据本身，可以拿走；不满意就追问一句，接着上一轮往下走
```

**用户不是"用了一个 AI"，而是"看着一件事被办完"。** 这是这个产品在体验上的核心选择：
把协作过程摆出来，而不是只给一个答案。

## 六、信任是怎么被设计出来的

不靠"我们相信大模型"，靠**四层防线 + 一条硬门禁 + 一句透明话**。

### 四层防线（产品语言版）

| 层 | 做法 | 产品含义 |
| --- | --- | --- |
| **应用层** | 危险语句扫描 + 风险分级（禁止 / 需确认 / 自动） | 负责**解释与体验**：让用户看到"为什么不允许"，而不是等数据库报错 |
| **表信息层** | 按系统目录静态核对**表和字段** | 负责**拦在进库之前**：挡住"表对了、字段是编的" |
| **数据库层** | 执行角色**只有增删改查权限，没有任何 DDL** | 负责**兜底与保证**：应用层校验可能被绕过，**权限绕不过去**（已实测：删表/清空/改结构/建表/删库全被拒，提权尝试后权限快照完全一致） |
| **执行沙箱** | 事务 + 超时 5s + 结果上限 500 行 + 影响超 1000 行转人工 | 限制**爆炸半径** |

> **设计立场**：应用层拦截是给用户看的，数据库权限才是给事故看的。只有前者是纸门，只有后者是坏体验 —— 两个都要。

### 硬门禁：模型说了不算

系统里有 8 条运行时一致性不变量（SQL 必须经过校验才能执行、需确认的操作必须有确认记录、
执行过的 SQL 必须有结果留痕、被判定禁止的语句永远不能被执行……）。

**只要有一条不通过，汇总审查器的 `approve` 会被运行时强制改写成 `veto`。**
一句话：**模型负责判断，运行时负责证明。**

### 一句透明话：护栏改道

链路不固定 —— 每个智能体可以建议下一步交给谁，但"能不能去"由运行时候选集决定。
当模型想去 A、护栏要求去 B 时，界面**不藏这件事**：

```
② SQL生成 ──▶ SQL校验        护栏改道
   模型建议交给 SQL执行  →  护栏改去 SQL校验
   理由：SQL 必须经过校验才能执行
```

同时要说清：**这不是报错**。正常的推进（上一步做完了接着做下一步）不会被标成告警 ——
不然界面上满屏"异常"，真正需要看的改道就淹没在里面了。

### 用户只能提问，不能给 SQL

这条一开始让内部争论过：有人希望"我贴一条 SQL 让它评估/改一下"，看起来更专业。

**我们最终拒绝了，并且是运行时确定性拒绝**（不指望模型自觉）。理由：

- 一旦允许外部 SQL 进来，就**开了旁门** —— 入库的语句不再必然出自"根据你的问题生成"这条链路，安全与一致性就无处安放（实测过最坏情况：用户贴一条查 `users` 表的语句，模型"聪明地"换成 `customers` 顶上，校验全过、执行成功、返回 0 行。**全链路看起来都对，就是答错了问题**）。
- 所以现在有两条**不交给模型**的硬拦：① 输入里夹带 SQL → 直接按越界拒；② 用户提到的表不在可用范围内 → 直说不可用，**绝不拿另一张表顶替**（换表顶上 = 换了问题）。

约束带来的收益是明确的：**入库的每一条 SQL 都必然出自同一套流程**，账才能对得上。

## 七、"一致性"在产品上意味着什么

多智能体不是卖点，**"接得上"才是**。用户不关心有几个智能体，只关心数字对不对。

连续性钉在四个地方，缺一个都会退化成"三个孤军"：

| 环节 | 干什么 | 用户能看到的证据 |
| --- | --- | --- |
| **① 共享记忆** | 只有**真正执行过**的语句才算事实，每条带 `sql_id` + SQL 原句，可回查 | `🧠 写入共享记忆 · sql_id=44 · 10 行` |
| **② 六类结构化交接** | 每次交接按六类给状态：基于哪一版 / 已确认什么 / 仍在猜什么 / 允许做什么 / 产物在哪里 / 怎样算完成 | 数据流转视图里每个卡片的内容 |
| **③ 依赖显式化** | 每个子任务声明依赖谁、怎样算完成；交接时**按依赖取哪几条记忆**，不把无关结果全灌进去 | 交接块里的「【依赖】st-1」 |
| **④ 复查循环** | 每做完一步回规划器，拿**实际结果**判断：继续 / 调整后续 / 到此为止 | `🔁 规划器复查` 事件 |

关键一条：**「已确认的事实」这一栏只可能来自共享记忆** —— 也就是执行器真跑过、带 `sql_id` 的那些条目，
模型自己说的话进不来。文档里那句话说的就是没有这一层时会出什么事：

> **下游拿到的不是任务，只是一句传闻。**

顺带说个反面：复查如果做成"做完一个就复查"而没有记号，会**原地打转**；
如果复查结论是"不用继续了"却不把剩余任务从计划里删掉，一致性校验会把它刚做出的结论**再推翻一次**。
这两处现在是硬性约束（同一位置只复查一次；提前收尾时计划跟着缩，被去掉的任务在界面上写明白）。

## 八、成本看得见

用户和老板都会问一句：**"这一轮到底花了多少？"** 答案不能靠估。

实测一轮只读查询（真实模型，非离线模拟）：

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 调用次数  6   │ 输入 token   │ 输出 token   │ 合计 token   │
│ 全部成功      │ 8,462        │ 1,736        │ 10,198       │
│              │ 缓存命中 4,096│ 模型生成的部分│ 累计耗时 10.9s│
│              │ （48%）       │              │              │
└──────────────┴──────────────┴──────────────┴──────────────┘

按智能体   汇总审查 26% · 生成 24% · 校验 21% · 规划 20% · 执行 9%
按步骤     同一个"生成"智能体里，选表 800 / 写 SQL 1,694  ← 只看角色会把这件事盖住
调用明细   6 条逐条可查：谁、在干什么、第几轮、哪个子任务、模型、输入/输出、缓存命中、耗时
```

| 读数 | 产品含义 |
| --- | --- |
| **token 是响应里的真数** | 不按字符数估算 —— 估算出来的账单没法对账 |
| **读不到就记 0** | 各家的用量字段名不一样，读不到时**不猜** |
| **缓存命中单独一列** | 它和输入 token 是包含关系，混在一起就算不出真实花费（这一轮 48% 的输入命中缓存） |
| **失败的调用也记** | 重试一样花输入 token，漏掉的话账单会**比真实花费少** |
| **按"角色 + 步骤"分组** | 定位到具体哪一步贵，才能谈优化（比如选表这步是否值得换更小的模型） |
| **不给金额** | 单价经常变，硬编码价目表只会给出一个错的数；token 与对账口径是准的，换算成钱按当期价格算 |
| **离线模式不装样子** | 用离线模拟跑时，面板直说"这一轮没有大模型调用"，而不是显示一堆 0 让人觉得"这个模型真省" |
| **消耗是观测不是业务** | 写消耗账失败只记日志、不影响主流程 —— **观测坏了不能拖垮任务** |

## 九、和常见做法比

| 维度 | 手工写 SQL | BI 拖拽报表 | 通用 Chat + 模型直连库 | **本产品** |
| --- | --- | --- | --- | --- |
| 上手门槛 | 要会 SQL | 会拖，但只能问预先建好的模型 | 会说话就行 | 会说话就行 |
| 临时/长尾问题 | 能做，慢 | **基本做不了**（没建过模型） | 能做 | 能做 |
| 多步问题 | 靠人会拆 | 靠预先建模 | 常常各查各的，**看不出来** | 拆步 + 共享记忆 + 每步复查，**界面上看得见** |
| 危险操作 | 靠人小心 | 一般不涉及写 | **不可控**（模型可能写出全表更新） | 风险分级 + 人工确认 + 权限兜底 |
| 表/字段编造 | 不适用 | 不适用 | 常见，且**语法没错** | 按系统目录静态核对，拦在进库前 |
| 可追溯 | 部分靠日志 | 弱 | 通常只存聊天记录 | 每条 SQL 全程留痕 + 事件可回放 + 状态增量落库 |
| 成本可控 | 人时成本 | 建模成本 | 常见"说不清花了多少" | 次数与 token 逐条可查 |
| 换库/换租户 | 改 SQL | 重建模型 | 改提示词 | **换一个数据文件**（可运行时热换，不改代码） |
| 输出 | SQL 结果 | 图表 | 一段话（常常没有真数据） | **数据本身**（真表格） |

> 对比只说明适用场景不同，不是说别的做法不好：**每天看同一张图，报表工具就是对的选择。**

## 十、产品边界

### 明确不做（不是"还没做"，是"不做"）

| 不做 | 为什么 |
| --- | --- |
| **任何 DDL**（建表、加字段、改结构） | 执行角色在权限上就做不了，提示词、护栏、权限三层一致地拒绝。**不给的能力不假装能给** |
| **替用户决定口径** | 聚合方式、时间范围由提问者表达。系统猜错口径比查不出数据更糟 |
| **让用户提交 SQL** | 见第六节：一旦开口，安全与一致性就无处安放 |
| **报表 / 看板 / 定时任务** | 那是 BI 的活，不是这个产品要解决的问题 |
| **用另一张表顶替用户提到的表** | 换表顶上 = 换了问题。宁可说"这张表不可用" |
| **多子任务并发执行** | 串行是复查循环能成立的前提：**一步做完才有"实际结果"可复查** |

### 已知限制（诚实清单）

| 限制 | 影响 | 现状 |
| --- | --- | --- |
| 修正轮次上限是**全局一个**（3 轮），没按子任务分别算 | 多子任务时，前一步用掉的轮次会挤占后一步 | 已知，在路线图里 |
| 预估影响行数来自 `EXPLAIN` | 是**估算**不是真实行数（`EXPLAIN ANALYZE` 会真执行，绝不能用） | 只用于人工确认提示，**不用于判定** |
| 写操作（`UPDATE`/`DELETE`）抽不出具体实体 | 共享记忆里这一步的可复用实体是空的 | **不编**：下游要看范围就读来源 SQL 里的 `WHERE` |
| 只支持 PostgreSQL + 单一业务库 | 换库要改连接与表目录 | 表目录已外部化，数据库方言适配未做 |
| 演示库的 4 张表规模很小 | 性能结论不可外推到大表 | 种子数据可重灌，方便演示 |
| 危险判定的"合理性"不判 | 只判语句类型（比如"这条 `DELETE` 的 `WHERE` 是否合理"没人管） | 那是汇总审查器的语义职责 |
| 界面链路没有自动化端到端脚本 | 回归靠手动演示 | 刻意取舍：那种脚本走的是和点界面同一个接口，跑一次就往**你的**会话列表里塞假会话。会话只该由对话产生 |

## 十一、落地形态与集成

### 交付物

| 交付物 | 内容 |
| --- | --- |
| **一个网页** | 对话流 + 会话列表 + 确认卡片 + 时序图 + 数据流转 + 消耗清单（原生 HTML/JS，无构建步骤）。会话记录、数据流转可导出成**自包含 HTML**，消耗清单、时序图可导出 **PNG** |
| **一套服务** | 单服务进程，FastAPI + SSE 实时推进度 |
| **一本账** | 6 张表：运行 / 任务 / 事件 / SQL 审计 / 共享记忆 / 大模型消耗明细 |
| **一套自检** | 7 个离线脚本，**不依赖服务、不写账本、不产生会话** |
| **一份表目录** | `config/tables.json`：换库、换租户、换环境改它就行 |

### 接口速查

| 接口 | 用途 |
| --- | --- |
| `POST /api/runs` → `POST /api/runs/{id}/start` | 发起提问（**唯一会产生会话的入口**：建会话 + 开始跑） |
| `GET /api/runs/{id}/stream` | 实时看它一步步走（SSE） |
| `POST /api/runs/{id}/confirm` | 确认或取消高危操作 |
| `GET /api/runs/{id}/usage` | 这一轮的消耗明细（消耗清单面板；可导出 PNG） |
| `GET /api/usage` | 全部会话累计（**接口保留，界面刻意不展示**：消耗清单只回答"这一轮花了多少"） |
| `GET /api/runs` · `GET /api/conversations/{id}` | 会话列表 / 多轮回放 |
| `POST /api/catalog/reload` | **运行时热换表目录**，不必重启 |
| `GET /api/health` | 健康检查（表目录加载失败会在这里暴露） |

### 换一套表要动什么

| 想换 | 怎么做 |
| --- | --- |
| 换一份表目录 | 改 `config/tables.json`，重启即可 |
| 指到别处 | 配置 `TABLES_FILE` |
| 运行时换 | `POST /api/catalog/reload`（可带路径） |

换完**立刻生效**的地方：表白名单、生成器两层表结构（选表看简述+关系，写 SQL 看完整字段）、
校验器的字段核对、"用户提到的表在不在范围内"那一关 —— 全都跟着变，**代码一行不动**。

> ⚠️ 一处需要注意：执行角色的授权语句里写着具体表名，换一套表要同步授权（文档已注明）。
> 加载失败会**直接报错起不来**，不会拿一份空目录凑合跑 —— 空目录会让所有 SQL 都判"未授权"，那个报错会把人带偏到完全错误的方向。

## 十二、怎么衡量它好不好

| 指标 | 定义 | 现状 |
| --- | --- | --- |
| **一次成功率** | 一次提问无需人工介入即拿到正确结果的比例 | 待埋点（需人工标注"结果是否正确"） |
| **危险请求拦截率** | 应拒的请求里真被拒的比例 | 已实测：删表 / 清空 / 改结构 / 建表 / 删库 / 越权读系统表 / 提权 全部拦下；静态防线对抗性用例 **99/99** |
| **越界如实说明率** | 目录外的表被"换成别的表顶替"的次数 | 目标为 **0**，护栏已钉死（曾经真的发生过，已修） |
| **多步连续性** | 后续子任务是否**使用**了上游真查出的值 | 离线端到端已验：三子任务依次落地、每步一条共享记忆、两次复查事件 |
| **人工确认率** | 需确认操作里用户点确认的比例 | 待埋点（可从审计表统计 `await_confirm` → `confirmed/取消`） |
| **单次问答成本** | 一轮的调用次数与 token | 已可逐条对账：一轮只读 = 6 次调用 / 10,198 token（含缓存命中 4,096） |
| **修正闭环成功率** | 首次校验不通过后最终跑通的比例 | 待埋点（可从 `sql_audit` 的轮次分布统计） |
| **无进展主动停止** | 重复失败时主动停下的次数 | 已实现并纳入自检（同 SQL 失败 ≥2 次 / 同错误连现 ≥2 次） |
| **过程可复现** | 一次运行能否被完整回放 | 每个节点的产出与**交出去的状态增量**都落库，刷新后依然完整 |

> 工程侧的自检现状：静态防线 99/99 · 路由护栏 33/33 · 提示词 24/24 · 消耗统计 20/20 ·
> 两库隔离全部符合预期 · 离线端到端通过 · 真实模型消耗对账通过 · 真实危险请求被拒。
> 这些都是**离线、可重复**的，不依赖谁的演示状态。

## 十三、路线图

### 近期（把已知缺口补上）

1. **写操作前先预览影响**：`UPDATE`/`DELETE` 执行前先跑一次等价的 `SELECT`，把"将要改的这几行"摆给用户看 —— 现在的确认卡片只有预估行数。
2. **每个子任务独立的修正预算**：解决"第一步用光轮次、第二步没机会"的问题。
3. **补充连续性语义规则**：让运行时能判"这一步是否真的用上了上游事实"，而不是只在界面上展示。

### 中期（从演示走向可用）

4. **成本预算护栏**：一轮超过设定的 token 上限就停下并说明，而不是跑完才发现贵。
5. **更多表 / 只读副本**：把表目录与授权做成可批量生成，降低换库成本。
6. **口径记忆**：把用户反复用到的口径沉淀成可复用的事实（**仍然只记引用与状态，不取代权威数据源**）。

### 远期（生态）

7. **审批流**：高危操作从"单人点确认"扩展到"按规则走审批"。
8. **接入指标层 / 语义层**：把"北京客户"这类业务口径交给已有的语义定义，产品只负责翻译与执行。

## 十四、三档讲法

**30 秒**（对业务方）
> 用中文问数据，它帮你查、帮你改；删除这类危险操作会停下等你确认，改错不了。
> 多步问题它会一步一步走，后一步用得上前面真查出来的数，不会各查各的。
> 每一轮花了多少 token、谁改了什么，界面上都能查到。

**3 分钟**（对技术评审）
> 六个智能体分工，链路不固定 —— 每个智能体建议下一步交给谁，运行时用候选集过滤。
> 该有分歧的地方才允许分歧：校验不通过和执行失败这两处，模型可以选"小修"还是"重新理解问题"。
> 关键边界不交给模型：没校验过的 SQL 到不了执行器，模型说 approve 但校验不过一律改写成 veto。
> 表信息是外部数据文件，换库换租户不改代码；校验阶段零数据库操作，SQL 能不能跑由执行器给真实答案。
> 多子任务的连续性落在四件事上：共享记忆、六类结构化交接、依赖显式化、每步复查。

**10 分钟**（演示顺序）

1. **正常一问**：「查一下北京客户的订单总额」→ 一条链直达，答复是**真表格**
2. **看连续性**：三步链路那个问题 → 一步一步走，注意 `🧠 写入共享记忆` 和 `🔁 复查`
3. **看协作过程**：切「📊 时序图」看形状 → 切「🔀 数据流转」看内容，展开**原始结构**看"真实传过去的状态"
4. **看人工协作**：「删掉所有已取消的订单」→ 停下等确认，卡片上有风险与级联提醒 → 点取消，证明**一行都没改**
5. **看拒绝**：「帮我删掉 orders 表」「帮我给 customers 加个字段」→ 拒绝并给替代方案
6. **看成本**：点「💸 消耗清单」，逐条对账
7. **看连续性怎么落地**：换一套表目录（`POST /api/catalog/reload`）→ 白名单、字段核对全都跟着变

## 十五、名词对照（产品口径 ↔ 技术口径）

| 产品上怎么说 | 技术上是什么 | 用户为什么要知道 |
| --- | --- | --- |
| 规划器 / 生成 / 校验 / 执行 / 修正 / 汇总 | 六个 LangGraph 节点 | 知道"谁在干什么"才看得懂过程 |
| 共享记忆 | 表 `agent_memory`，只有执行器写 | 这就是"后一步用得上前一步"的落点 |
| 护栏改道 | 运行时对 `handoff_to` 的候选集过滤 | 说明系统行使了否决权，**不是出错** |
| 硬门禁 | 不变量不通过 → 模型的 `approve` 强制改写成 `veto` | 决定"该不该信这个结论" |
| 需确认 | `interrupt()` 暂停 + `Command(resume=...)` | 你的点头是流程的一部分，不是弹窗打扰 |
| 数据流转 | `agent_event` 表 + 节点状态增量落库 | 过程可回放、可审计 |
| 消耗清单 | 表 `llm_call` | 账单要对得上，就得逐条记 |

**一句话总结**

> 这个产品的价值不在于"AI 会写 SQL"，而在于**它敢让人用**：
> 该拦的拦得住（权限兜底）、该问的会问你（人工确认）、该连的连得上（共享记忆 + 每步复查）、
> 花多少看得见（逐条对账），出错了也说得清（全程可回放）。
