# 01 · 设计说明：从冻结项目继承了什么、改了什么

> 冻结版：`../demo-validation`（通用问答 · 引用必须逐字命中资料）
> 本项目：`sql-agent`（自然语言 → SQL → 验证 → 执行 · 删除需人工确认）
> 继承的是**设计思想**，不是代码形状。

---

## 一、直接继承的设计思想

| 冻结项目里的做法 | 本项目怎么用 | 为什么还成立 |
| --- | --- | --- |
| **模型负责判断，运行时负责证明** | 验证智能体说"通过"不算数：静态防线 + `EXPLAIN` 说不过就不许执行 | 判断可以分歧，边界不能含糊 |
| **硬门禁**：校验器 fail 时模型的 approve 一律无效 | 同上，汇总审查器不得 approve 未通过校验的结果 | 把"运行时"放在"模型"之上 |
| **接入层适配器**（`mode="before"` 归一化 LLM 输出） | 原样保留：DeepSeek 会把嵌套对象序列化成字符串、把 list 写成换行长文本 | 老坑都踩过一遍了 |
| **结果必须能被校验** | 冻结版：引用摘录必须逐字命中资料；本项目：表名字段名必须在真实 schema 里、SQL 必须过 `EXPLAIN` | 「同一份事实」的两种落地 |
| **事实来源必须是能真正依据的那一份** | 冻结版看用户给的资料；本项目用**受限角色**去读 `information_schema` —— 智能体只看得到它真能访问的表 | 白名单与权限天然一致，不会出现"说要查却没权限" |
| **权威层只读** | 冻结版 `source_chunk`；本项目表结构快照 + 权限不给 DDL | Agent 不能改写事实 |
| **账本**：租约 / 幂等键 / 乐观锁 / 事件回放 | 原样保留（`agent_run`/`agent_task`/`agent_event`） | 与业务无关的通用能力 |
| **两条防线分工**：运行时抓结构，审查器抓语义 | 冻结版：运行时证明"引用是真的"，审查器判断"引用是否支持结论"；本项目：运行时证明"没越权、语法通"，审查器判断"这条 SQL 是否真的完成了意图" | 运行时管不了语义，语义也替代不了运行时 |
| **对话式前端 + 实时事件** | 保留对话流、气泡、折叠、SSE 回放 | 演示效果 |
| **Windows 事件循环修复 / `run_server.py`** | 原样保留 | psycopg 异步在 Windows 上只能跑 SelectorEventLoop |

## 二、改掉的

| 冻结项目 | 本项目 | 原因 |
| --- | --- | --- |
| 四个角色固定链 `规划→研究→执行→审查` | **六个智能体 + `router` 节点，链路不固定** | 本项目的需求就是"智能体之间自己选择协作对象" |
| 校验的是「引用是否逐字命中」 | 校验的是「SQL 是否越权 / 是否过 EXPLAIN / 是否验证过才执行 / 确认记录是否齐」 | 场景变了，该守的边界变了 |
| 无副作用（只出文字答案） | **有真实副作用**（改数据、删数据） | 所以多了三层防线 + 人工确认 |
| 复核轮次靠模型判断 | 修正轮次由护栏控制（`MAX_ROUNDS`），且**修正方向由模型选** | 保留模型的判断空间，同时兜住死循环 |

## 三、新引入的两件事

### 1. 动态链路（`app/router.py`）

```
候选集只有一个元素 → 直接去，模型的建议无效（硬边界）
候选集有多个元素   → 让模型在合法范围内自己选（真正的协作自由度）
```

候选集为多的两个地方，正是真实存在的分歧点：

- **验证不通过** —— 小修（fixer）还是重新理解问题（planner）？
- **执行失败** —— 改 SQL（fixer）还是重新拆问题（planner）？

这两处才让"链路不固定"有意义：不是随机乱走，而是**该有分歧的地方允许分歧**。

### 2. 人工协作（LangGraph 原生 `interrupt`）

删除类操作在图里暂停，前端渲染确认卡片，用户的决定通过 `Command(resume=...)` 送回去。

⚠️ **Python 3.10 的兼容处理**：LangGraph 给异步节点注入 config 依赖
`asyncio.create_task(coro, context=ctx)`，而 `context=` 是 3.11+ 才有。
3.10 上会走 `await self.afunc(...)`，节点里读不到上下文，`interrupt()` 直接报错。
`app/graph.py::_with_config` 让节点多接一个 config 参数并自己 set 上下文，等价于 3.11+ 的默认行为。

## 四、安全设计的取舍

**应用层拦截 vs 数据库权限，为什么两个都要？**

- 只有应用层：`sql_guard` 是正则 + 解析器，理论上可能被绕过（注释、别名、新语法…）
- 只有数据库权限：用户会得到一个生硬的 `permission denied`，而且我们**希望**在生成 SQL 阶段就拦住，
  让用户看到"为什么不允许"，而不是等数据库报错

所以：**应用层负责"解释与体验"，数据库权限负责"兜底与保证"。**
`check_isolation.py` 实测证明第二层是真的。

## 五、已知取舍

| 取舍 | 说明 |
| --- | --- |
| `EXPLAIN` 只给预估，不给真实行数 | `EXPLAIN ANALYZE` 会真的执行，绝不能用。预估行数用于人工确认提示，不用于判定 |
| 修正轮次上限 3 | 超过就去汇总，如实告诉用户"没搞定"，而不是无限重试 |
| 删除只按「语句类型」判风险 | 没做"这个 WHERE 条件是否合理"的语义判断 —— 那是审查器的活 |
| 一次处理一个子任务 | 用 `cursor` 串行推进。多子任务并发会带来状态合并的复杂度，当前阶段不值得 |
| 演示库的种子数据会被改 | `python scripts\init_db.py --seed` 可重灌 |
