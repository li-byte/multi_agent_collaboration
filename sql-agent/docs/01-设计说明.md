# 01 · 设计说明：从冻结项目继承了什么、改了什么

> 冻结版：`../demo-validation`（通用问答 · 引用必须逐字命中资料）
> 本项目：`sql-agent`（自然语言 → SQL → 校验 → 执行 · 删除需人工确认）
> 继承的是**设计思想**，不是代码形状。

---

## 一、直接继承的设计思想

| 冻结项目里的做法 | 本项目怎么用 | 为什么还成立 |
| --- | --- | --- |
| **模型负责判断，运行时负责证明** | 校验智能体说"通过"不算数：静态防线说不过就不许执行；能不能跑由执行器实测 | 判断可以分歧，边界不能含糊 |
| **硬门禁**：校验器 fail 时模型的 approve 一律无效 | 同上，汇总审查器不得 approve 未通过校验的结果 | 把"运行时"放在"模型"之上 |
| **接入层适配器**（`mode="before"` 归一化 LLM 输出） | 原样保留：DeepSeek 会把嵌套对象序列化成字符串、把 list 写成换行长文本 | 老坑都踩过一遍了 |
| **结果必须能被校验** | 冻结版：引用摘录必须逐字命中资料；本项目：表名字段名必须来自**系统内置目录**，SQL 能不能跑由执行器实测 | 「同一份事实」的两种落地 |
| **事实来源必须是**系统定义**的那一份** | 冻结版看用户给的资料（系统给的）；本项目看 `config/tables.json` 里的表目录 —— **不读数据库** | 读了库，系统就会自己发现表被改名并改口，真实报错轮不到修正智能体看 |
| **权威层只读** | 冻结版 `source_chunk`；本项目表目录 + 权限不给 DDL | Agent 不能改写事实 |
| **账本**：租约 / 幂等键 / 乐观锁 / 事件回放 | 原样保留（`agent_run`/`agent_task`/`agent_event`），并加了 `llm_call`（消耗明细） | 与业务无关的通用能力 |
| **共享记忆**：带来源的候选主张 → 检查 → 可复用事实层 | `agent_memory`：执行器真跑过才写，每条带 `sql_id` + 原句；下游读它续上前面的事实 | **记录引用和状态，不取代权威数据源** |
| **交接要按结构给全** | `prompts.HANDOFF_BLOCK` 六类：基于哪一版 / 已确认什么 / 仍在猜什么 / 允许做什么 / 产物在哪里 / 怎样算完成 | 混成一段自然语言，下游拿到的就是一句传闻 |
| **两条防线分工**：运行时抓结构，审查器抓语义 | 冻结版：运行时证明"引用是真的"，审查器判断"引用是否支持结论"；本项目：运行时证明"没越权、语法通"，审查器判断"这条 SQL 是否真的完成了意图" | 运行时管不了语义，语义也替代不了运行时 |
| **对话式前端 + 实时事件** | 保留对话流、气泡、折叠、SSE 回放 | 演示效果 |
| **Windows 事件循环修复 / `run_server.py`** | 原样保留 | psycopg 异步在 Windows 上只能跑 SelectorEventLoop |

## 二、改掉的

| 冻结项目 | 本项目 | 原因 |
| --- | --- | --- |
| 四个角色固定链 `规划→研究→执行→审查` | **六个智能体 + `router` 节点，链路不固定** | 本项目的需求就是"智能体之间自己选择协作对象" |
| 校验的是「引用是否逐字命中」 | 校验的是「SQL 是否越权 / 是否校验过才执行 / 确认记录是否齐」（**校验阶段零数据库操作**） | 场景变了，该守的边界变了 |
| 无副作用（只出文字答案） | **有真实副作用**（改数据、删数据） | 所以多了三层防线 + 人工确认 |
| 复核轮次靠模型判断 | 修正轮次由护栏控制（`MAX_ROUNDS`），且**修正方向由模型选** | 保留模型的判断空间，同时兜住死循环 |

## 三、新引入的三件事

### 1. 动态链路（`app/router.py`）

```
候选集只有一个元素 → 直接去，模型的建议无效（硬边界）
候选集有多个元素   → 让模型在合法范围内自己选（真正的协作自由度）
```

候选集为多的两个地方，正是真实存在的分歧点：

- **校验不通过** —— 小修（fixer）还是重新理解问题（planner）？
- **执行失败** —— 改 SQL（fixer）还是重新拆问题（planner）？

这两处才让"链路不固定"有意义：不是随机乱走，而是**该有分歧的地方允许分歧**。

### 2. 人工协作（LangGraph 原生 `interrupt`）

删除类操作在图里暂停，前端渲染确认卡片，用户的决定通过 `Command(resume=...)` 送回去。

⚠️ **Python 3.10 的兼容处理**：LangGraph 给异步节点注入 config 依赖
`asyncio.create_task(coro, context=ctx)`，而 `context=` 是 3.11+ 才有。
3.10 上会走 `await self.afunc(...)`，节点里读不到上下文，`interrupt()` 直接报错。
`app/graph.py::_with_config` 让节点多接一个 config 参数并自己 set 上下文，等价于 3.11+ 的默认行为。

### 3. 连续性：共享记忆 + 六类交接 + 复查循环

拆成多个子任务时，"每个都跑通了"不等于"合起来答对了问题"——
常见失败是三步各查各的，1 查出来的具体值 2 和 3 根本没用上。

| 环节 | 落在哪 | 解决什么 |
| --- | --- | --- |
| **共享记忆** | 表 `agent_memory`（只有执行器写） | 让"上一步的事实"成为**可传递、可核对**的东西：带 `sql_id` 与原句，`verified` 只由执行成功置位 |
| **六类结构化交接** | `prompts.HANDOFF_BLOCK` | 交接的是**可继续工作的状态**，不是聊天记录，也不是一句"上一步做了点事" |
| **依赖显式化** | `QueryIntent.depends_on` / `acceptance` | 决定交接时**取哪几条**记忆、**怎样算完成**；不把无关结果全灌进去 |
| **复查循环** | `router` 规则⑤ + `prompts.PLANNER_REPLAN_*` | 每完成一个子任务，拿**实际结果**判断剩余计划：`continue` / `revise` / `finish` |

两个容易做错的细节，都在代码注释里写明了原因：

- **复查同一位置只做一次**（`replanned_cursor`），否则"做完一个就复查"会原地打转；
- **`revise` 必须清掉上一版 SQL**、**`finish` 必须把剩余任务从计划里去掉** ——
  前者防止"改了计划却没改动作"，后者防止一致性校验把规划器刚做出的结论又推翻一次。

## 四、安全设计的取舍

**应用层拦截 vs 数据库权限，为什么两个都要？**

- 只有应用层：`sql_guard` 是正则 + 解析器，理论上可能被绕过（注释、别名、新语法…）
- 只有数据库权限：用户会得到一个生硬的 `permission denied`，而且我们**希望**在生成 SQL 阶段就拦住，
  让用户看到"为什么不允许"，而不是等数据库报错

所以：**应用层负责"解释与体验"，数据库权限负责"兜底与保证"。**
`check_isolation.py` 实测证明第二层是真的。

## 五、已知取舍

| 取舍 | 说明 |
| --- | --- |
| `EXPLAIN` 只给预估，不给真实行数 | `EXPLAIN ANALYZE` 会真的执行，绝不能用。预估行数用于人工确认提示，不用于判定 |
| `EXPLAIN` 由**执行器**做，校验器不做 | 校验阶段必须零数据库操作。代价是"表不存在"这类问题只能在执行前一刻暴露，好处是报错真实、轮得到修正智能体处理 |
| 表结构写在外部数据文件 `config/tables.json` | 换库/换租户改数据文件即可（`TABLES_FILE` / `POST /api/catalog/reload` 热换）。换来的是「系统以为的库」和「真实的库」可以不一致 —— 不一致正是要测的东西 |
| 修正轮次上限 3 | 超过就去汇总，如实告诉用户"没搞定"，而不是无限重试。**全局一个上限**，没按子任务分别算 —— 多子任务下前一步用掉的轮次会挤占后一步 |
| 删除只按「语句类型」判风险 | 没做"这个 WHERE 条件是否合理"的语义判断 —— 那是审查器的活 |
| 一次处理一个子任务 | 用 `cursor` 串行推进。多子任务并发会带来状态合并的复杂度，当前阶段不值得。**串行是复查循环能成立的前提**：一步做完才有"实际结果"可复查 |
| 写操作（UPDATE/DELETE）抽不出具体实体 | 写操作只返回影响行数，拿不到行 id，所以共享记忆里这一步的 `entities` 是空的 —— **不编**，下游要判断范围就去读来源 SQL 里的 WHERE |
| 演示库的种子数据会被改 | `python scripts\init_db.py --seed` 可重灌 |
