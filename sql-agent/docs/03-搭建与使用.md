## 1. 前置条件

| 需要 | 版本 / 说明 | 必需吗 |
| --- | --- | --- |
| **Python** | 3.10（本项目在 3.10.0 上开发）；3.11+ 也能跑 | ✅ |
| **PostgreSQL** | 12 以上（用到 `jsonb`、`make_interval`、`GENERATED … AS IDENTITY`） | ✅ |
| **建库权限** | 需要能 `CREATE DATABASE`（默认用 `postgres` 超级用户） | ✅ |
| **DeepSeek API Key** | <https://platform.deepseek.com>；**没有也能跑**（离线 mock），但 mock 不验提示词 | 建议有 |
| Node.js | 只有 `check_js.py`（前端 JS 语法校验）用它；没有就自动跳过 | 可选 |

> ⚠️ **两个库不会自动创建。** `scripts/init_db.py` 只建**表**和**角色**，
> 库本身要你先建好 —— 这一点卡住过很多人，见 §4 第 1 步。

## 3. 两个库的分工（这是本项目的核心安全设计）

| 库 | 谁连 | 权限 | 放什么 |
| --- | --- | --- | --- |
| `agent_sql` | 应用（`PG_USER`） | 建表 / 读写 | 账本：会话、任务、事件、SQL 审计、共享记忆、大模型消耗 |
| `cs_v1` | 应用建表（`PG_USER`） | 建表 / 灌种子 | 4 张业务表 —— 智能体**查改删**的目标 |
| `cs_v1` | **智能体执行（`agent_sql_runner`）** | **只有 4 张表的 DML，没有任何 DDL** | 同上 |

为什么要分开、为什么执行要用受限角色：**应用层的正则拦得住是一回事，数据库层拦得住才是保证**。
`scripts/check_isolation.py` 会实测这一点（删表 / 清空 / 改结构 / 提权全被拒）。

## 4. 从零搭建（六步）

下面命令以 Windows PowerShell 为例，Linux/macOS 只改路径写法。

### 第 1 步 · 建两个数据库

```sql
-- 用 psql / pgAdmin / Navicat 连上你的 PostgreSQL，执行：
CREATE DATABASE agent_sql;
CREATE DATABASE cs_v1;
```

`init_db.py` **不会**替你建库。漏了这一步，第 4 步会直接报「无法连接 agent_sql」。

### 第 2 步 · 建虚拟环境 + 装依赖

项目根目录（`multi_agent_collaboration/`）下：

```powershell
cd multi_agent_collaboration

# 用 3.10 建虚拟环境（名字随意，两个子项目共用这一个就行）
py -3.10 -m venv .venv310

# 装依赖
& .\.venv310\Scripts\python.exe -m pip install --upgrade pip
& .\.venv310\Scripts\python.exe -m pip install -r sql-agent\requirements.txt
```

Linux / macOS：

```bash
cd multi_agent_collaboration
python3.10 -m venv .venv310
./.venv310/bin/python -m pip install -r sql-agent/requirements.txt
```

> 依赖里带 `[standard]` / `[binary,pool]` 的扩展（uvicorn、psycopg）会装预编译包，
> 不需要本机编译器和 libpq。

### 第 3 步 · 配置 `.env`

```powershell
cd sql-agent
copy .env.example .env
notepad .env          # 填下面这几项
```

| 配置项 | 填什么 | 说明 |
| --- | --- | --- |
| `PG_HOST` / `PG_PORT` | 你的 PostgreSQL 地址端口 | 默认示例是 `192.168.10.101:5432`，本机就写 `127.0.0.1` |
| `PG_USER` / `PG_PASSWORD` | 有建库建表权限的账号 | 默认 `postgres` |
| `PG_DB_LEDGER` | `agent_sql` | 项目自己的记录库 |
| `PG_DB_BIZ` | `cs_v1` | 智能体执行 SQL 的目标库 |
| `RUNNER_USER` / `RUNNER_PASSWORD` | `agent_sql_runner` / 自定义密码 | **受限角色**，由 `init_db.py` 自动创建，不用你手动建 |
| `DEEPSEEK_API_KEY` | 你的 Key | 没有就先把 `LLM_MODE=mock` |
| `DEEPSEEK_MODEL` | `deepseek-chat` | |
| `LLM_MODE` | `deepseek` 或 `mock` | `mock` = 离线兜底，不调大模型 |
| `USE_CHECKPOINTER` | `on` | **删除类操作的"等你确认"依赖它**，关掉就没有人工确认 |
| `TABLES_FILE` | 留空 | 留空 = 用 `config/tables.json`；换表见 §7 |

> `.env` 已被 `.gitignore` 排除 —— **不要把 Key 提交上去**。

### 第 4 步 · 初始化数据库（建角色 + 建表 + 灌种子）

```powershell
& ..\.venv310\Scripts\python.exe scripts\init_db.py --reset
```

它会依次做四件事，每件都会打印结果：

```
[1/4] 已创建 角色 agent_sql_runner（由 postgres 授权）
[2/4] 已删除系统表：llm_call, agent_memory, sql_audit, agent_event, agent_task, agent_run
      系统表就绪（15 条语句）：agent_run / agent_task / agent_event / sql_audit / agent_memory / llm_call
[3/4] 业务表就绪（10 条语句）：customers / products / orders / order_items
      种子数据已重灌（5 条语句）
      受限执行身份：agent_sql_runner @ cs_v1
          customers      DELETE,INSERT,SELECT,UPDATE
          order_items    DELETE,INSERT,SELECT,UPDATE
          orders         DELETE,INSERT,SELECT,UPDATE
          products       DELETE,INSERT,SELECT,UPDATE
[4/4] LangGraph checkpoint 就绪（agent_sql）—— 人工确认依赖它
```

| 命令 | 作用 | 会动数据吗 |
| --- | --- | --- |
| `init_db.py` | 建角色 + 建表（表已存在则不动） | ❌ |
| `init_db.py --seed` | 上面 + **重灌演示数据** | ✅ TRUNCATE + 重新 INSERT 业务表 |
| `init_db.py --reset` | 上面 + **先删光 `agent_sql` 的账本表**再重建 | ✅ 会话/审计/消耗全清 |

演示数据：**8 个客户 · 10 个商品 · 15 张订单 · 19 条订单行**；
其中库存 < 10 的商品有 5 个（所以「库存小于 10」这类问题一上手就有结果）。
`--seed` 随时可把被智能体改过的数据恢复原样。

### 第 5 步 · 离线自检（不连服务、不写账本、不产生会话）

**建议先跑这一步**：环境问题在这里暴露，比在浏览器里排查容易得多。

```powershell
& ..\.venv310\Scripts\python.exe scripts\check_guard.py      # 99 项：静态防线 + 表/字段核对 + 用户输入
& ..\.venv310\Scripts\python.exe scripts\check_router.py     # 33 项：路由护栏 + 复查循环
& ..\.venv310\Scripts\python.exe scripts\check_isolation.py  # 两库隔离 + 权限兜底（要连库）
& ..\.venv310\Scripts\python.exe scripts\check_js.py         # 前端内联 JS 语法（要 node）
& ..\.venv310\Scripts\python.exe scripts\check_prompts.py    # 24 项：提示词模板渲染 + 关键约束
& ..\.venv310\Scripts\python.exe scripts\check_usage.py      # 20 项：token 用量解析 + 接口序列化
& ..\.venv310\Scripts\python.exe scripts\check_export.py     # 74 项：四个导出的产物（要 node）
```

看到这几句就算通了：

```
✓ 静态防线通过：危险语句全拦截、正常语句不误伤、偷换表与目录外表被拦下
✓ 护栏符合预期
✓ 全部符合预期：
    · 业务库：能查能改能删，**做不了任何 DDL**，也改不动授权
    · 记录库：连项目自己的系统表都读不到
✓ 前端内联 JS 语法全部通过
✓ 提示词模板全部可用（注意：离线 mock 不走这些提示词，改完要用真实模型验证）
✓ 消耗统计符合预期：读得到就读真数，读不到就记 0，绝不估算
✓ 导出符合预期：图能画出来、元素不溢出、HTML 零外部依赖（换台机器也能打开）
```

`check_isolation.py` 会连数据库（它测的就是权限）；其余全是纯离线，连账本都不写。

### 第 6 步 · 起服务

```powershell
& ..\.venv310\Scripts\python.exe run_server.py
# 换端口：run_server.py --port 8090
# 只监听本机（默认）：--host 127.0.0.1
```

浏览器打开 <http://127.0.0.1:8000>。

> **为什么不用 `uvicorn app.server:app`**：uvicorn 在 Windows 上会用 `ProactorEventLoop`，
> 而 psycopg 的异步连接只能跑 `SelectorEventLoop` —— 会直接报
> `Psycopg cannot use the 'ProactorEventLoop'`。`run_server.py` 自己拿循环，绕开这件事。

## 5. 怎么用

### 界面导览

```
┌───────────────────────────────────────────────────────────────────────────┐
│ sql-agent · 自然语言转 SQL   [状态][轮次][消耗][连接信息]  [💸消耗][🧾审计][🔀流转][📊时序] │
├──────────────┬────────────────────────────────────────────────────────────┤
│ 会话列表      │ 对话流：用户提问 → 各智能体气泡（可折叠）→ 最终答复          │
│ （按最近活动  │                                                            │
│   排序，显示  │ 每个气泡 = **一次节点调用**（不是按角色合并）                │
│   改了哪些数据│                                                            │
│   /消耗/token）│ 底部：试试（示例问题） + 输入框                             │
└──────────────┴────────────────────────────────────────────────────────────┘
```

**四个覆盖层视图**（都是点开一个浮层，数据来自账本，可逐条回放）：

| 视图 | 看什么 | 数据来源 | 能导出 |
| --- | --- | --- | --- |
| 💸 **消耗清单** | 调用次数、输入/输出/合计 token、缓存命中、按智能体与按步骤分组、逐条明细（**只有这一轮**） | `llm_call` | **PNG** |
| 🧾 **SQL 审计** | 每条 SQL 从生成 → 校验 → 等确认 → 执行/失败的全程，含风险等级、影响行数、确认人 | `sql_audit` | — |
| 🔀 **数据流转** | 每次交接「谁 → 谁、带了什么过去」，含共享记忆写入与规划器复查；可展开**原样落库的完整结构** | `agent_event` | **HTML** |
| 📊 **时序图** | 整条链路的形状（7 条生命线） | `agent_event` | **PNG / SVG** |

导出按钮在浮层右上角，**按钮文案随视图变**（消耗清单＝「导出 PNG」、数据流转＝「导出 HTML」、
时序图＝「导出 PNG」+「导出 SVG」）。三种格式**都不依赖任何库、也不连网**：

- **PNG**：面板内容重画成一张 SVG，再交给浏览器栅格化成 2 倍图（放 PPT / 文档不糊）。
  不走 html2canvas 那类方案 —— 要么引 CDN（内网就废），要么用 `<foreignObject>`（部分浏览器画不出来、中文还容易缺字）。
- **HTML**：把当前页面的样式**内联**进一个独立文件，双击就能在任何浏览器打开，
  不需要这个服务在跑、也不需要网络。导出时「真实传递过去的内容·完整结构」会强制展开
  （静态页里没有那个折叠开关，否则最该看的部分反而被折起来了）。

消耗清单**只统计当前这一轮** —— 把别的会话的账混进来，这一轮的数字就不好对账了。

**还有一个「📄 导出会话」在顶栏**（不是浮层）：把**当前会话的全部轮次**导出成一份独立网页，
给同事看、或打印成 PDF 都用它。它复用对话流那一套渲染（导出与界面不会说两套话），
但把**要点击才成立**的东西去掉：确认按钮、[数据流转]/[消耗清单] 这类入口、等待动画。
待确认的那一步会写成「⏸ 当时在等用户确认」，没跑完的气泡写明「导出时这一步还在进行中」——
导出的是**记录**，把当时的真实状态写出来比留个空白气泡有用。
页眉带上状态 / 轮次 / 改了什么数据 / 消耗；文件名取首问（`会话记录-查一下北京客户的订单总额.html`）。

顶栏三个数字：**状态**、**轮次**（修正轮次）、**消耗**（本轮调用次数与 token 合计，实时累加）。

### 推荐的上手顺序

| # | 问什么 | 看什么 |
| --- | --- | --- |
| 1 | `帮我查一下北京客户的订单总额，按金额从高到低排序` | 完整链路一气呵成；答复是**一张真表格**，不是「返回 N 行」 |
| 2 | `你好，你能做什么？` | `mode=chat`：直接回一句，**不进生成/执行**，也不会回「已处理 0 个操作」 |
| 3 | `帮我删掉 orders 表` | 规划器拒绝 + 给替代做法；`sql_audit` 里**一条 SQL 都没有** |
| 4 | `先找出库存小于 10 的商品，再看这些商品都有哪些订单，最后统计涉及多少客户` | 拆成 3 个有依赖的子任务；每步之后回规划器**复查**；执行器气泡里出现「🧠 写入共享记忆」，下一条 SQL 直接用上一步查出的**具体 id** |
| 5 | `删掉所有已取消的订单` | ⏸ 暂停等确认（含级联删除提醒）→ 点「确认执行」→ 继续跑完 |
| 6 | 接着第 1 条追问：`那再按城市分组看看` | 同一会话内的**多轮对话**：规划器拿到了上一轮实际执行的 SQL |
| 7 | 点开「💸 消耗清单」 | 这一轮每次调用的 token / 耗时 / 缓存命中；右上角「导出 PNG」存成图片 |
| 8 | 点开「🔀 数据流转」 | 每次交接过去的内容，包括被护栏改道的那一步；「导出 HTML」得到一个不依赖任何东西的单文件页面 |
| 9 | 点顶栏「📄 导出会话」 | 把当前会话（含全部轮次）存成一个独立网页：给同事看、或打印成 PDF |

示例问题也可以直接点输入框上方的「试试」按钮。

### 消耗清单怎么读

- **token 是模型响应里的真数**，不按字符数估算 —— 所以数字能拿去对账。
- **缓存命中**和输入 token 是**包含**关系（命中部分便宜得多），所以单列一列。
- **按 `stage` 分组**：同一个生成智能体，「第一层·选表」和「第二层·生成 SQL」是两笔账。
- **失败的调用也在里面**（带 `✕` 和错误原文）—— 重试一样花输入 token。
- `LLM_MODE=mock` 时面板会写明「**根本没发请求**」，而不是显示一排 0
  （但历史那几轮是真实模型跑的，明细照样显示）。
- 不给金额：单价会变，硬编码价目表只会给出一个错的数。

## 6. 离线 mock 模式（没有 Key 也能演示）

```dotenv
LLM_MODE=mock
```

然后照常 `run_server.py`。区别只有一处：**大模型调用换成本地固定输出**（`app/mock_llm.py`），
其余（账本、SQL 校验、权限、执行、确认、事件流）全都是真的。

适合：没有 Key 时先把环境跑通 / 演示时不想花钱 / 网络不通时排查前端问题。

⚠️ **mock 不读提示词** —— 它有自己的固定输出。所以：
"mock 跑通了"不等于"提示词写对了"，改了提示词必须用真实模型再验一次。

## 7. 换一套表（不用改代码）

表信息在 `config/tables.json`（数据文件），智能体关于「库里有什么」的**唯一依据**就是它，
**任何验证逻辑都不读数据库**。所以换库 / 换租户只需要换这个文件。

```jsonc
{
  "tables": [
    {
      "name": "products",
      "summary": "商品（一句话，给选表用）",
      "notes": "补充说明",
      "columns": [
        { "name": "id",    "type": "int",          "pk": true,  "desc": "主键" },
        { "name": "name",  "type": "text",         "nullable": false, "desc": "商品名" },
        { "name": "price", "type": "numeric(10,2)","desc": "单价" },
        { "name": "cat",   "type": "text", "enum": ["外设","显示"], "desc": "分类" }
      ]
    }
  ]
}
```

两种换法：

```powershell
# ① 启动前指定（环境变量 / .env）
$env:TABLES_FILE = 'D:\my\tables.json'

# ② 运行时热换（不用重启，立刻生效）
#    同样注意中文/反斜杠：路径用单引号或双反斜杠，稳妥起见走字节体
$body = [Text.Encoding]::UTF8.GetBytes('{"path":"D:\\my\\tables.json"}')
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/catalog/reload `
  -ContentType 'application/json; charset=utf-8' -Body $body
# → {"source":"D:\\my\\tables.json","tables":[...],"count":N,"error":"","ok":true,"reloaded":true}
```

换完立刻生效的地方：`sql_guard` 的表白名单、生成器的两层表结构、校验器的表/字段核对、
「用户提到的表在不在目录里」的判定 —— 全都跟着变。

> ⚠️ **别忘了一件事：授权。** `sql/biz.sql` 里的 `GRANT` 是**写死 4 张表名**的，指向新表时
> 要用管理连接补一条：
> ```sql
> GRANT SELECT, INSERT, UPDATE, DELETE ON 新表 TO agent_sql_runner;
> GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO agent_sql_runner;
> ```
> 否则目录里认了、静态防线也过了，执行时会撞 `permission denied for table 新表`。

目录文件写错时：**服务会拒绝启动**，错误信息里直接指出是哪一份文件、缺了什么
（JSON 不合法 / 没有任何表 / 外键指向目录里不存在的表）。
服务已经起来了但目录有问题，`/api/health` 的 `catalog.error` 和界面右上角那颗状态灯也会变红。

## 9. 常见问题排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `Psycopg cannot use the 'ProactorEventLoop'` | 用了 `uvicorn app.server:app` | 用 `python run_server.py` |
| `无法连接 agent_sql` / `database "cs_v1" does not exist` | 库还没建 | 见 §4 第 1 步 |
| `password authentication failed for user "postgres"` | `.env` 里账号密码不对 | 核对 `PG_USER` / `PG_PASSWORD` |
| `已创建 角色 …` 这一步失败 | 当前账号没有建角色权限 | 用超级用户跑 `init_db.py`，或手动 `CREATE ROLE` |
| `permission denied for table xxx` | 受限角色没有被授权 | 见 §7 末尾那条 `GRANT` |
| 表目录加载失败 / 目录里一张表都没有 | `TABLES_FILE` 路径错、JSON 写坏、外键指向不存在的表 | 看启动日志与 `/api/health` 的 `catalog.error` |
| 点了「删除」没有弹出确认卡片 | `USE_CHECKPOINTER=off` | 改成 `on` 再起服务 |
| `Called get_config outside of a runnable context` | Python 3.10 + `interrupt()` 的已知坑；`app/graph.py` 的 `_with_config` 就是为它写的 | 别把 `_with_config` 从节点装配里去掉 |
| 模型报 `json_schema` 相关错误 | 换成了不支持 function calling 的模型 | `STRUCTURED_METHOD=function_calling` + `DEEPSEEK_MODEL=deepseek-chat` |
| 前端改了没生效 | 浏览器缓存 | `Ctrl+F5` |
| 端口被占用 | 8000 已被占 | `run_server.py --port 8090` |
| 中文变乱码、文档字符丢失 | 用 PowerShell 的 `Get-Content -Raw` + `Set-Content` 批量改过 UTF-8 文件（按 cp936 读、还写 BOM） | 用编辑器或 Python 显式 `encoding="utf-8"` 读写 |
| 消耗清单全是「没有记录」 | 那一轮是在消耗统计上线之前跑的 | 重新问一轮；老记录补不回来 |

排查顺序建议：**先看 `/api/health`** → 再跑 §4 第 5 步的离线自检 → 最后才怀疑模型。

## 10. 数据与重置：哪些操作会清掉什么

| 操作 | `agent_sql`（账本） | `cs_v1`（业务数据） | 角色 |
| --- | --- | --- | --- |
| `scripts/reset_ledger.py` | **清空 6 张表**再重建（会话列表归零） | ❌ 不动 | ❌ 不动 |
| `scripts/init_db.py --seed` | ❌ 不动 | **重灌种子**（TRUNCATE 后重新 INSERT） | ❌ 不动 |
| `scripts/init_db.py --reset` | **删表重建**（等于清空） | 重灌种子 | 已存在则跳过 |
| 界面上的 `DELETE /api/runs/{id}` | 删这一轮（级联删它的任务/事件/审计/记忆/消耗） | ❌ 不动 | ❌ 不动 |
| 服务重启 | ❌ 不动 | ❌ 不动 | ❌ 不动 |

要点：

- **服务启动只整理自己的账本表，绝不碰 `cs_v1` 的结构。**
  所以你手动改过、删过的业务表，重启后不会被"改回来" —— 这正是要测的场景。
- 只有 `init_db.py` 会碰业务表结构；只有它和 `--seed` 会写业务数据。
- 删一轮任务用界面或 `DELETE /api/runs/{id}`，比 `reset_ledger.py` 精细 —— 后者是**全清**。
