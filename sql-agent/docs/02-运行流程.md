# 运行流程

> 本文只讲**一轮是怎么跑起来的** —— 从用户提交问题，到拿到答复。
> 建库、建角色、灌种子、配置这些不在范围内。
>
> 文中所有事件流都是**真实抓取**的（`LLM_MODE=mock`），不是凭记忆写的。

---

## 0. 一轮运行的全貌

```
用户提交一句话
      │
      ▼
┌─────────────────────────────────────────────────────────────────┐
│  langgraph 状态机（一条共享状态在节点之间流转）                   │
│                                                                 │
│   START ──► planner ◄─┐                                          │
│              ▲        │ 复查（每做完一个子任务回来看一眼）        │
│              │        │                                          │
│            router ────┘                                          │
│              ▲   ⇄ ┌ generator                                  │
│              │     ├ validator                                  │
│              │     ├ executor ──►（写共享记忆）──┐               │
│              │     └ fixer                      │               │
│              └──────────────────────────────────┘               │
│                                    reviewer ──► END              │
└─────────────────────────────────────────────────────────────────┘
      │
      ▼
答复（Markdown）
```

三个要点先说清楚，后面才好读：

| 要点 | 说明 |
| --- | --- |
| **智能体之间只通过共享状态通信** | 没有点对点消息。每个节点 `return` 一个字典，langgraph 合并进 `TaskState`，下一个节点读到的就是这个 |
| **链路不固定** | 每个节点在输出里附带「我建议下一步交给谁」，但真正去哪由 `router` 节点的**运行时候选集**决定 |
| **收尾只有一个节点：`reviewer`** | 正常路径是 `reviewer → END`。`router` 的每条规则最终都汇到它（禁止的不去执行、没校验的不去执行、聊天的直接答复……） |

多子任务时还有一个**内循环**：执行器每做完一个子任务就把结论写进**共享记忆**，
`router` 随后把规划器叫回来**复查**（拿着实际结果判断剩余计划还成不成立），再决定继续做哪个。
所以"1 → 2 → 3"不是三条独立的链路，而是一条**有记忆、有依赖、每步回头看一眼**的链。

## 1. 入口：两步

```python
POST /api/runs              → 建一轮，返回 run_id / conversation_id / turn   (201)
POST /api/runs/{id}/start   → 开始跑，立刻返回 {accepted: true}              (202)
```

代码在 `app/server.py:187` 和 `app/server.py:204`。

**为什么要拆两步**：让前端**先订阅上 SSE 再开始跑**。合成一个接口的话，
`start` 返回时前几条事件（`run_created` / `planner` 的 `node_start`）已经推完了，
前端还没连上 —— 界面上的「全过程」就断了。

```python
# app/server.py:204
asyncio.create_task(_guarded(orch, lambda: orch.run(run_id), f"任务 {run_id}"))
return {"global_task_id": run_id, "accepted": True}
```

- `asyncio.create_task` —— 丢后台跑，接口立刻返回。一轮要调好几次大模型、还可能停下等确认，同步等会超时。
- `_guarded` —— 包一层把异常记进日志，避免变成「静默消失的协程」（asyncio 对没人 await 的 task 不吭声）。
- `RUN_SEMAPHORE` —— 限制并发，别把数据库连接打满。

## 2. 装配初始状态

`app/graph.py:290` 的 `Orchestrator.run()` 把这一轮要用的共享状态拼出来：

```python
state: TaskState = {
    "global_task_id": run_id,
    "question": run["question"],
    "conversation_id": ...,
    "turn": ...,
    "prior_turns": await self._prior_turns(...),   # 多轮上文
    "mode": "", "safety": "", "chat_reply": "",
    "status": "created", "version": ..., "round": 0,
    "intents": [], "cursor": 0, "history": [],
    "memory": [], "replanned_cursor": -1, "plan_note": "",   # 共享记忆 + 复查进度
    "draft": None, "verdict": None, "checks": None, "result": None,
    "explain": None, "confirmed": False,
}
```

- `memory` —— **共享记忆**。初始为空，只有执行器执行成功后往里写；下游读它来续上前面的事实。
- `replanned_cursor` —— 复查进度。`-1` 表示还没在任何位置复查过。
- `plan_note` —— 最后一次复查的结论（给汇总审查器用：「为什么继续 / 改了什么 / 为什么收尾」）。

`prior_turns`（`app/graph.py:240`）是**前几轮的摘要**，带上「上一轮实际执行了什么 SQL」——
追问常常省略主语（「那再按城市分组看看」），规划器得知道「再」指的是什么。

## 3. 推进：`_drive`

`app/graph.py:265`：

```python
async def _drive(self, run_id: str, payload) -> bool:
    paused = False
    async for chunk in self.graph.astream(payload, self._config(run_id), stream_mode="updates"):
        interrupts = chunk.get("__interrupt__")
        if interrupts:
            paused = True
            for item in interrupts:
                await self._on_interrupt(run_id, getattr(item, "value", item) or {})
    return paused
```

它同时干两件事：

1. **把图往前推**（`astream`，逐个节点跑）
2. **捕获 `interrupt`** —— 执行器停下来等人工确认就是从这儿冒出来的。返回 `True` 表示「停在确认」

## 4. 每个节点都做三件事

所有节点都被 `app/graph.py:172` 的 `traced()` 包了一层，所以每个节点的行为是统一的：

```python
async def run(state):
    out = await fn(state)                      # ① 干活，返回状态增量
    await rt.emit(..., role, "state_delta",     # ③ 把增量落成事件（供「数据流转」视图）
                  {"keys": sorted(out), "delta": _slim(out)})
    return out
```

② 是节点自己发的业务事件（`plan` / `sql` / `check` / `result` / `memory` …）。

所以**每个节点至少产生两条事件**：它自己广播的业务事件 + 一条 `state_delta`。
两者的区别很关键：

| | 谁写的 | 内容 |
| --- | --- | --- |
| 业务事件 | 同一个节点 | 它**挑出来给人看**的字段 |
| `state_delta` | 同一个节点 | 它 `return` 出去的**完整结构**（下一个节点真正读到的东西） |

实测差集（`sql_audit` / `explain` / `next_agent` 这些**只存在于状态增量**里）：

| 节点 | 广播了什么 | 只存在于状态增量 |
| --- | --- | --- |
| planner | `node_start` `plan` `node_end` | `cursor` `replanned_cursor` `plan_note` `last_agent` `next_agent` `status` `version` |
| generator | `node_start` `tables` `sql` `node_end` | `checks: null` `confirmed: false` `result: null` `next_agent` |
| validator | `node_start` `check`×8 `verdict` `node_end` | `attempts` `checks` `history`（含查询行） |
| **executor** | `node_start` `result` **`memory`** `node_end` | **`explain`（整棵 EXPLAIN 执行计划树）** **`memory` 的完整版（广播里只有摘要）** `result` `history` `cursor` |

> 另外每个节点里**每次大模型调用**都会广播一条 `llm_call`（由 `_call` 统一发），
> 它不属于状态增量 —— 消耗是观测，不进智能体之间的交接。

## 6. `router` 是怎么决定的

`app/graph.py:153` 的 `node_router` 调 `app/router.py:60` 的 `decide()`：

```python
want = state.get("next_agent")        # 模型自己建议的下一步
nxt, reason = router.decide(state, max_rounds)   # 运行时算出的「能去哪」
await rt.emit(..., "handoff", {
    "from": ..., "to": nxt, "reason": reason,
    "model_wanted": want,
    "overridden": bool(want and want != nxt),    # ← 护栏改道标记
})
```

`decide()` 按顺序判 **17 条规则**，**先命中先返回**：

| # | 条件 | 去哪 | 守什么 |
| --- | --- | --- | --- |
| ⓪ | `status == "failed"` | reviewer | 有节点没干成，收尾交代 |
| ⓪' | `refusal` 非空 | reviewer | 规划器拒绝执行 |
| ⓪'' | `give_up` 非空 | reviewer | 修正器判断修不了 |
| ⓪''' | `mode == "chat"` | reviewer | 聊天不进生成/执行 |
| ① | 没有 `intents` | planner | 不能直接生成 |
| ② | `cursor >= len(intents)` | reviewer | 子任务全完成 |
| ③ | `round >= max_rounds` | reviewer | 修正轮次用尽 |
| ④ | **刚做完一个子任务**（`cursor > 0`、后面还有、`replanned_cursor != cursor`、上一步执行成功） | planner | **复查循环**：后面的计划要按前面**实际结果**评估 |
| ⑤ | 没有 draft / draft 不属于当前子任务 | generator | **SQL 只能由生成器产出** |
| ⑥ | `verdict.level == "禁止"` | reviewer | **禁止语句永不执行** |
| ⑦ | `checks is None` | validator | **没校验不能执行** |
| ⑧ | `not checks.passed` | fixer / planner | 让模型选：小修还是重拆（先查无进展） |
| ⑧' | `mode != "execute"` | reviewer | 保险丝：非执行意图不进执行器 |
| ⑨ | 需确认且未确认 | executor | 执行器内部会 `interrupt` 暂停 |
| ⑩ | `result is None` | executor | 可以执行了 |
| ⑪ | `not result.ok` | fixer / planner | 让模型选：改 SQL 还是重拆（先查无进展） |
| ⑫ | 其它 | generator | 推进下一个子任务 |

**只有两处是真的多选**（⑧ 和 ⑪）：候选集有多个元素时，模型在合法范围内自己选。
其余全是唯一候选 —— 模型想去别处也没用，`handoff` 事件里会标 `overridden: true`。

> 规则 ④ 的四个条件缺一不可。少写 `replanned_cursor != cursor`，
> "做完一个就复查"会变成**原地打转**：复查完回到同一位置，条件又满足。
> 少写「上一步执行成功」，执行失败也会被当成"做完了"去复查 —— 那一步该走修正。

### 共享记忆：连续性的落点

执行器**执行成功**后写一条 `agent_memory`：结论 + `sql_id`（来源，可回查）+ 从结果里抽出的主键值。
`verified` 只在这里置位 —— **模型说的不算，只有真跑过才算事实**。

下游拿到的「已确认的事实」只来自这张表，所以：

```
st-1 执行成功 → agent_memory(st-1, sql_id=44, products.id=[1,3,5,…])
                      ↓  交接（HANDOFF_BLOCK 的【已确认的事实】）
st-2 生成器：直接用 products.id 这批具体值写 WHERE，不再自己另找条件
```

`depends_on` 决定**取哪几条**记忆（没声明就退化成"取全部已完成的"，宁可多给也不丢连续性）；
`acceptance` 直接写进交接的【怎样算完成】。六类结构缺一类，下游拿到的就是一句传闻。

### 场景 C · 多子任务 + 复查循环

**输入**：`先找出库存小于 10 的商品，再看这些商品都有哪些订单，最后统计涉及多少客户`
（规划器拆成 st-1 / st-2 / st-3，st-2 依赖 st-1，st-3 依赖 st-1+st-2）

```
  planner    plan         [首次拆解] 3 个任务（含 depends_on / acceptance）
  router     handoff      planner → generator｜为子任务 st-1 生成 SQL
  generator  sql          SELECT * FROM products WHERE stock < 10
  validator  verdict      校验通过
  executor   result       {"ok":true,"rowcount":10}
  executor   memory       🧠 sql_id=44 · 10 行 · products.id=[1,3,5,9,6,…]
  router     handoff      executor → planner｜子任务 st-1 已执行完成，回到规划器复查剩余 2 个
  planner    plan         [复查·continue] 已完成 1｜剩余计划仍然成立
  router     handoff      planner → generator｜子任务 st-1 已完成，接着为 st-2 生成 SQL
  …（st-2、st-3 同上，每步都再复查一次）
  router     handoff      executor → reviewer｜3 个子任务全部完成，进入汇总
```

复查的三种结论（`plan_action`）：

| 结论 | 运行时动作 |
| --- | --- |
| `continue` | 计划不动，接着做下一个 |
| `revise` | 换掉计划 + **清空上一版 SQL**（否则"改了计划却没改动作"）；游标按"哪几个真执行过"重算，不按模型给的列表形状 |
| `finish` | **把剩余任务从计划里去掉**再收尾 —— 留着不删，一致性校验会判「子任务没落地」而否决，等于把规划器的结论又推翻一次 |

### 暂停与恢复是怎么实现的

```
执行器调 interrupt({...})
      ↓
langgraph 把这一轮挂起，astream 抛出 __interrupt__
      ↓
_drive 捕获 → _on_interrupt()          app/graph.py:276
      ↓  · 把确认请求落成 await_confirm 事件
         · 补一条 sql_audit（stage=await_confirm）
         · run.status = confirming
      ↓
接口返回；前端渲染确认卡片
      ↓
用户点击 → POST /api/runs/{id}/confirm
      ↓
Orchestrator.resume(approve, by)        app/graph.py:318
      ↓  · 发 confirmed 事件
         · _drive(run_id, Command(resume={...}))   ← 图从暂停点继续
      ↓
执行器**从头再跑一遍**（interrupt 之前的代码会重跑），
这次 interrupt 直接返回用户决定，继续往下执行
```

> ⚠️ **`interrupt` 之前的代码会重跑** —— 所以执行器把 EXPLAIN 放在 `interrupt` 之前
> （纯读、无副作用），而 `node_start` / 租约等副作用一律放在 `interrupt` 之后。
>
> 这也是为什么 `await_confirm` 事件出现在 `node_start` **之前** ——
> 前端渲染时得按「事件流顺序」而不是「节点顺序」来理解。

## 8. 三种「不走完整链路」的运行

### 8.1 打招呼（`mode=chat`）

**输入**：`你好，你能做什么？`

```
  75  system   run_created   {"question":"你好，你能做什么？","turn":1,…}
  76  planner  node_start    {}
  77  planner  plan          {"mode":"chat","safety":"安全","intents":[],
                              "chat_reply":"你好！我是 SQL 智能体，…"}
  78  planner  node_end      {"summary":"打招呼 / 闲聊，不需要动数据库","suggests":"reviewer"}
  80  router   handoff       {"from":"planner","to":"reviewer",
                              "reason":"打招呼 / 闲聊，不需要动数据库，直接答复"}
  81  reviewer node_start    {}
  82  reviewer consistency   {"passed":true}
  83  reviewer review        {"reason":"闲聊，无需访问数据库"}
  86  system   done          {"status":"done",…}
```

**没有 generator / validator / executor，`sql_audit` 是空的。**
答复也不会出现「已处理 0 个数据操作」这种废话。

### 8.2 危险请求（规划器拒绝）

**输入**：`帮我删掉 orders 表`

```
  87  system   run_created   {"question":"帮我删掉 orders 表",…}
  89  planner  plan          {"mode":"execute",
                              "safety":"越界：请求包含「删掉 orders 表」，属于 DDL / 越权操作，
                                        执行角色没有任何 DDL 权限",
                              "intents":[],
                              "refusal":"这个请求超出允许范围…可以改成「删掉符合条件的行」"}
  90  planner  node_end      {"summary":"拒绝执行：…","suggests":"reviewer"}
  92  router   handoff       {"from":"planner","to":"reviewer",
                              "reason":"规划器判定请求超出允许范围：…"}
  93  reviewer node_start    {}
  95  reviewer review        {"reason":"规划器判定请求超出允许范围"}
  98  system   done          {"status":"done",…}
```

**同一轮里也挂了两个运行时硬拦**（在 `app/agents.py:166` 的 planner 节点里，不交给模型判断）：

| 硬拦 | 触发 | 结果 |
| --- | --- | --- |
| ① 输入里夹带 SQL | `sql_guard.find_user_sql()` 命中 | 拒绝：「你只能通过提问，语句由我生成」 |
| ② 用户提到的表不在目录里 | `catalog_check.unknown_tables()` 命中 | 拒绝：列出可用的表，**绝不换表顶替** |

## 9. 落库与回放

一轮运行往四张表写东西：

| 表 | 写什么 | 谁写 |
| --- | --- | --- |
| `agent_event` | 上面所有事件（带 `seq` / `role` / `event_type` / `round` / `version` / `payload`） | `rt.emit()` |
| `sql_audit` | 每条 SQL 的全程：`generated → validated / rejected → await_confirm → confirmed → executed / failed` | 各节点 + `_on_interrupt` |
| `agent_memory` | **共享记忆**：执行成功才有，一个子任务一条，带 `sql_id` + SQL 原文 + 抽出的主键值 | 只有执行器写 |
| `llm_call` | **大模型消耗明细**：每次调用一条，role / stage / 轮次 / 子任务 / 模型 / 输入输出 token / 缓存命中 / 耗时 / 成败 | `Runtime.record_llm()`（由 `_call` 调） |

因为**事件先落库再推给 SSE**（`app/runtime.py` 的 `Runtime.emit`），所以：

- 刷新页面 / 重新打开会话能**完整回放**全过程（`GET /api/conversations/{id}` 按轮次回放）
- 「🔀 数据流转」视图直接读这份事件流，包括被护栏改道那一步（`overridden` / `model_wanted`）
- 「🧾 SQL 审计」视图读 `sql_audit`，一眼看清每条 SQL 走到哪一步、影响了多少行
- 「💸 消耗清单」读 `llm_call`（明细）+ 一次聚合；顶栏那个数字则是跟着 `llm_call`
  事件实时累加的 —— 面板给对账，事件给实时
- 共享记忆**在 state 里流转**（`state["memory"]`），下游节点读的是它，不是再去查库 ——
  所以"下一步到底拿到了什么"在 `state_delta` 里看得一清二楚

```
emit() = 先 append_event 落库 ──► 再 bus.publish 推给在线订阅者
                │
                └─► 断线重连 / 事后回看都靠它
```

## 10. 附：六个节点各自读写什么

| 节点 | 代码 | 提示词 | 读 state | 写 state（状态增量） |
| --- | --- | --- | --- | --- |

| **generator** | `agents.py:470` | `prompts.GENERATOR_FILTER_*`（选表）<br>`prompts.GENERATOR_*`（写 SQL） | `question` `intents[cursor]` `memory` `history`（经 `_handoff` 组装六类交接） | `draft`（含 `tables`）`verdict` `checks=None` `result=None` `next_agent` |
| **validator** | `agents.py:560` | `prompts.VALIDATOR_*` | `draft` `question` | `checks` `attempts` `history` `next_agent` |
| **executor** | `agents.py:696` | `prompts.EXECUTOR_*` | `draft` `verdict` `confirmed` | `result` `explain` **`memory`** `history` `cursor` `attempts` `next_agent` |
| **fixer** | `agents.py:910` | `prompts.FIXER_*` | `draft` `checks` `result` `attempts` `memory` | `draft`（新版）`verdict` `checks=None` `round+1` `next_agent` |
| **reviewer** | `agents.py:1002` | `prompts.REVIEWER_*` | `intents` `history` `result` `mode` `refusal` **`memory`** `plan_note` | `status`（done / failed） `next_agent=done` |

> **所有提示词都在 `app/prompts.py`**，`agents.py` 里只有一句 `.format(...)`。
> system 是纯常量、user 是模板；占位符名字写错会直接 `KeyError`，
> `scripts/check_prompts.py` 会把每个模板渲染一遍提前抓出来。
> ⚠️ 离线 mock **不走提示词**，改了要用真实模型验证。

> `validator` 那一关里有 4 项**运行时**检查（`rt-static` / `rt-intent-tables` / `rt-catalog` / `rt-no-db`）
> 加上模型侧若干条（离线模式下是 `m-1`…`m-4`，一条对应一个运行时检查）。
> **全部 pass 才允许进执行器**；任何一项 fail → `checks.passed=False` → 路由去 fixer。
>
> 汇总时 `app/validators.py:41` 再算一遍 8 条运行时一致性不变量（S1–S8）；
> 只要有一条 fail，`reviewer` 的 `approve` 会被**强制改写成 `veto`**（`forced_by_runtime=true`）。

## 11. 一句话总结

```
一句话进来
   │
   ├─ 聊天？        → 规划器直接给答复，收尾
   ├─ 危险 / 越界？  → 规划器拒绝 + 给替代做法，收尾
   └─ 要数据        → 拆任务 → 写 SQL → 校验 → 执行 → 汇总
                        ↑         ↑        ↑        ↑
                     规划器    生成器   校验器   执行器
                        └──────── router 在每一步之间决定能不能去 ────────┘
                                  （禁止的永远不去，没校验的永远不执行）

   拆了多个任务时，它是**一条链**而不是三件互不相干的事：
       执行完一步 → 把「带来源的事实」写进共享记忆
                  → 回规划器复查（后面的计划还成不成立）
                  → 继续 / 改计划 / 收尾
       下一步拿到的是上一步**具体的值**（某个 id 列表），不是一句「上一步做了点事」。
```
