# sql-agent · 多智能体自然语言转 SQL

用 **LangGraph 1.x** 搭的多智能体系统：**你说一句话，六个智能体协作把 SQL 写出来、校验、执行**，
失败就自动修正；删除操作停下等你确认；任何 DDL 一律拒绝。

支持**多轮对话**，也会先判**你这一句到底想要什么** —— 打招呼、只要 SQL、只要评估、还是真的执行。

> 设计思想沿用已冻结的 `demo-validation`：**模型负责判断，运行时负责证明。**
> 但这一版的**协作链路不固定** —— 每个智能体自己建议下一步交给谁，护栏决定能不能去。

## 1. 一句话看懂它做什么

```
你：删掉所有已取消的订单
  ↓
规划器  → 只拆任务：「删除 orders 中 status='已取消' 的行」（不指定表）
生成     → 第一层选表：orders（顺带按关系补上 customers、order_items）
         → 第二层看详情：写出 DELETE FROM orders WHERE status = '已取消'
校验     → 程序门禁（权限、语法、表字段、SQL 绑定）；模型语义复核默认关闭 —— **一个字都不碰数据库**
执行     → EXPLAIN（语法语义 OK，预估影响 4 行）→ ⏸ 暂停等确认
  ↓
你点确认 → 执行 → 影响 4 行 → 汇总审查器给答复
```

查数据时，答复是**一张表**而不是一句「返回 N 行」：

```
你：查一下北京客户的订单总额
  ↓
规划 → 选表(customers/orders) → 生成 → 校验 → 执行（EXPLAIN 预估 → 执行 → 返回 8 行）
  ↓
汇总：| id | name | city | level | … |      ← 真正的数据
```

### 规划器先判两件事：是不是在聊天 / 该不该拒

模式**只有两种** —— `chat` 和 `execute`：

| 用户说的话 | `mode` | 链路 | 会执行吗 |
| --- | --- | --- | --- |
| 「你好，你能做什么」 | `chat` | 规划 → **直接答复** | ❌ |
| 「查一下北京客户的订单总额」 | `execute` | 完整链路 | ✅ |
| 「删掉所有已取消的订单」 | `execute` | 完整链路（删除前停下等你确认） | ✅ |
| 「帮我给 customers 加个字段」 | —— | 规划 → **拒绝 + 给替代做法** | ❌ |
| 「`SELECT * FROM users WHERE name = 张三`」 | —— | 规划 → **拒绝** | ❌ |
| 「查一下 users 表里有没有张三」 | —— | 规划 → **拒绝**（表不在目录，不拿别的顶替） | ❌ |

#### 铁规矩：用户只能**提问**，不能给 SQL

用户的权限只体现在**对话**里，不体现在「递过来一条能跑的语句」上。
所以消息里一旦夹带 SQL，直接按越界处理 —— **运行时确定性判定，不指望模型自觉**：

```
我不能执行你给的 SQL —— 你只能通过提问告诉我你想查什么，语句由我根据你的问题生成。

把需求说成一句话就行，比如「查一下 name 是张三的客户」。
```

这条规矩顺带保证了另一件事：**入库的每一条 SQL 都必然出自生成器**，不留旁门。

判定用「SQL 动词 + 结构词」两条同时命中（`SELECT … FROM` / `DELETE FROM` / `UPDATE … SET` / `DROP TABLE`…），
所以正常的中文提问不会被误伤 —— 「给我一条查北京的 SQL，不用执行」这种**提到** SQL 的也算正常提问。

#### 换表顶上 = 换了问题

用户提到一张**目录里没有的表**（比如 `users`）时，绝不能把意图里的表悄悄换成另一张。
模型很会这么干：它看到没有 `users`，就"聪明地"改用 `customers` ——
语句跑通了、还执行成功、返回 0 行，**全链路看起来都对，就是答错了问题**。
所以规划器在链路开始前就把用户提到的表认出来，不在目录里就直接说明不可用：

```
你提到的表 users 不在我能访问的范围内。我不会拿另一张表顶替它 —— 那回答的就不是你的问题了。

系统目录里可用的表是：customers、order_items、orders、products。换成其中之一，我就帮你查。
```

这两条都**不交给模型判断**，是运行时的确定性检查 —— 模型可以想帮忙，但运行时不让它帮错忙。

危险 / 越界的判定维度：DDL（`DROP`/`TRUNCATE`/`ALTER`/`CREATE`/`GRANT`/加字段）、
越权访问（`agent_run` 等系统表、别的 schema、`pg_` 开头）、绕过授权、**夹带 SQL**。

### 多轮对话

同一个会话里可以连续追问，**上一轮实际跑过什么 SQL 会带给规划器**：

```
你：查一下北京客户的订单总额
    ↓  规划 → 选表 → 生成 → 校验 → 执行（返回 8 行）
你：那再按城市分组看看          ← 省略了主语，"再"指什么？
    ↓  规划器拿到的上文：
       [{ 第几轮:1, 用户问:"查一下北京客户的订单总额",
          实际执行的 SQL:["SELECT * FROM customers LIMIT 20"], 结果:"done" }]
    ↓  → 知道"再"是"在刚才那个查询基础上再分组"
你：只把 SQL 给我，不要执行      ← 同一会话里切模式也正常
```

实现要点：

- `agent_run` 加 `conversation_id` / `turn` 两列（**幂等** `ADD COLUMN IF NOT EXISTS`，
  对已有库不重建表、不丢数据；没有这两列的老记录按 `global_task_id` 各自成条，升级不打乱历史）
- 左栏会话列表**一个会话一条**，显示「N 轮对话」
- 点开某个会话会**把所有轮次按顺序回放**，不是只显示最后一轮
- 界面每一轮之间有分隔条，每轮的气泡按 `runId` 隔离（否则第 2 轮会合并进第 1 轮）

## 2. 六个智能体 + 动态链路

| 智能体 | 职责 |
| --- | --- |
| **规划器** | 判**这一句是聊天还是要动数据** + **危险与越界评估** + 拆任务。不指定表、不写 SQL |
| **SQL 生成** | 两层取表（简述+关系过滤 → 详情）→ **SQL 只在这里产生** |
| **SQL 校验** | 程序门禁 + **按系统目录的表信息核对表与字段**；模型语义复核可选。**零数据库操作** |
| **SQL 执行** | **唯一碰数据库的智能体**：EXPLAIN + 执行；需确认时暂停。**前面必过校验器** |
| **SQL 修正** | 拿**执行器抛出的数据库原话**重写 SQL |
| **汇总审查** | 汇总结果 + 硬门禁 + 给用户的答复 |

### 提示词都在 `app/prompts.py`

六个智能体 + 公共约定，**所有提示词集中在这一个文件里**，改词不用翻 `agents.py`：

| 常量 | 用途 | 类型 |
| --- | --- | --- |
| `CONTRACT_HINT` | 追加在每个 system 提示词后面的输出约定 | 常量 |
| `PLANNER_SYSTEM` / `PLANNER_USER` / `PLANNER_PRIOR` | 规划器（判 chat/execute、危险评估、拆任务） | 常量 + 模板 |
| `GENERATOR_FILTER_SYSTEM` / `_USER` | 生成器第一层：选表 | 常量 + 模板 |
| `GENERATOR_SYSTEM` / `_USER` | 生成器第二层：写 SQL | 常量 + 模板 |
| `VALIDATOR_SYSTEM` / `_USER` | 校验器 | 常量 + 模板 |
| `EXECUTOR_SYSTEM` / `_USER` | 执行器（执行后点评结果） | 常量 + 模板 |
| `FIXER_SYSTEM` / `_USER` | 修正器 | 常量 + 模板 |
| `REVIEWER_SYSTEM` / `_USER` / `REVIEWER_MODE_RULE` / `REVIEWER_BLOCKED_RULE` | 汇总审查器 | 常量 + 模板 |

约定：**system 提示词是纯常量**；**user 提示词是模板**，变量用 `{占位符}` 标出，
`agents.py` 那边只留一句 `prompts.XXX_USER.format(...)`。用 `.format()` 而不是 f-string，
就是为了把「话」和「代码」彻底分开 —— 提示词在这个文件里是一段完整可读的话。

两个注意点：

- **占位符名字改了会直接 `KeyError`**（不会静默出错）。`scripts/check_prompts.py`
  把每个模板都渲染一遍，提前把这类错抓出来 —— 否则要等跑到那条分支才炸，
  而「修正器」这种分支平时很少触发。
- **离线模式（`LLM_MODE=mock`）不走这些提示词**（它有自己固定的输出），
  所以改完提示词必须用真实模型验证，mock 跑通说明不了问题。

> 表结构**渲染**（`tier1_text` / `detail_text`）留在 `app/catalog.py` ——
> 那是把目录数据格式化成文本喂给模型，不是提示词。
> （原先还有一个「表结构」页面视图和 `/api/schema` 接口，已经删掉了：
> 表目录是给智能体看的数据，不是给用户看的页面。`as_dict()` / `relations()` 一并删除。）

### 两条硬边界

**① 校验阶段没有任何数据库操作。**

校验智能体不 `EXPLAIN`、不查 `information_schema`、也不判断表是否存在。
早期版本不是这样 —— 它跑 EXPLAIN，失败时还去查「当前可见的表」、算出「缺失的表」。
那等于**校验阶段自己去偷看现实**：表一旦被改名或删掉，系统立刻自己发现并改口，
于是修正智能体永远等不到那个真实的报错，也就永远测不出它能不能处理。

现在的分工：**SQL 能不能跑，由执行器在执行时给答案**，报错原话原样交给修正器。

**② 只有执行器执行 SQL。**

其他任何地方都不对业务库发语句。EXPLAIN 也归执行器（它不执行语句，只让 PostgreSQL
做完整的语法/语义分析），所以「预估影响 N 行」和「超过阈值转人工确认」都保住了。

### 表信息是**数据**，不是代码

表、字段、关系全部写在外部文件里（默认 `config/tables.json`），
**验证逻辑里没有任何一处写死表名或字段名** —— 换库、换租户、换环境都不用改代码：

```json
{
  "tables": [
    {"name": "customers",
     "summary": "客户档案：姓名、电话、所在城市、会员等级",
     "notes": "一个客户可以有多张订单。",
     "columns": [
       {"name": "id", "type": "INT", "desc": "客户 ID", "pk": true},
       {"name": "phone", "type": "TEXT", "desc": "联系电话", "nullable": true},
       {"name": "city", "type": "TEXT", "desc": "所在城市", "enum": ["北京", "上海"]}
     ]}
  ]
}
```

| 怎么换 | 怎么做 |
| --- | --- |
| 换一份文件 | 改 `config/tables.json`，重启即可 |
| 指到别处 | `.env` 里 `TABLES_FILE=D:\conf\other.json` |
| **运行时换** | `POST /api/catalog/reload`（可带 `{"path": "..."}`），**不必重启** |

换完立刻生效的地方：`sql_guard` 的表白名单、生成器的**两层**表结构
（第一层选表看简述+关系，第二层写 SQL 看完整字段）、校验器的**表/字段核对**、
以及「用户提到的表在不在目录里」那一关 —— 全都跟着变。

加载失败（文件不存在 / JSON 不合法 / 外键指向的表不在同一份目录里）会**直接报错起不来**，
不会拿一份空目录凑合跑 —— 空目录会让所有 SQL 都判「未授权」，那个报错会把人带偏到完全错误的方向。

#### 但目录**不是**从数据库读的

读库就等于「系统去偷看现实」：表一被改名，系统立刻自己发现并改口，
于是修正智能体永远等不到执行器抛出的那个真实报错，也就永远测不出它能不能处理。

所以这份目录是一份**外部给定的、明确的**定义；数据库只是**执行时的现实**。
两者不一致时，报错由**执行器**抛出来再交给修正器 —— 这正是要测的东西。
（实测：把目录换成一套数据库里并不存在的表，运行会如实失败并说明，而不是悄悄成功。）

### 链路不固定

每个智能体产出时都带一个 `handoff_to`（**它自己建议下一步交给谁**），
`router` 节点用运行时候选集过滤：

| 当前状态 | 允许去哪 | 守什么 |
| --- | --- | --- |
| 还没规划 | 规划器 | 不能直接生成 |
| 打招呼 / 被拒绝 | 汇总 | 不进生成，直接答复 |
| 没有 SQL | 生成 | — |
| 有 SQL 未校验 | 校验 | **绝不能跳过去执行** |
| 判定禁止 | 汇总 | 永不进执行 |
| 校验不通过 | 修正 / 规划器 | **让模型选**：小修还是重新理解 |
| 需确认未确认 | 执行（内部暂停） | 人工协作 |
| 校验通过但 mode ≠ execute | 汇总 | **用户说了不执行，一行都不动** |
| 执行失败 | 修正 / 规划器 | **让模型选**：改 SQL 还是重拆问题 |
| **做完一个子任务、后面还有** | **规划器（复查）** | **每步做完回头看一眼**：后面的计划还成不成立 |
| 执行成功还有子任务 | 生成 | — |
| 全部完成 | 汇总 | — |

所以简单问题一条 SQL 直达；复杂问题可能反复修正、甚至退回重新规划。
界面上每一步的 **`改了什么`** 都会标出来（模型想去 A，护栏拦住了 → 实际去 B）；
正常的推进（比如"上一步做完了，接着做下一步"）**不会**被标成告警 —— 那是流程本身，不是异常。

### 循环：按计划一步步走，每做完一步回头看

多子任务时最要命的不是"任务拆得对不对"，而是**三个子任务像三个孤军** ——
各查各的，1 查完的结果根本没人用，2 和 3 照样从全表捞一遍。

这一版把「连续性」钉在四个地方，缺一个都断：

| 环节 | 落在哪 | 干什么 |
| --- | --- | --- |
| **① 共享记忆** | 表 `agent_memory` · 写它的只有执行器 | 只有**真正执行过**的语句才算"事实"，每条带 `sql_id` + SQL 原文，可回查来源 |
| **② 六类结构化交接** | `prompts.HANDOFF_BLOCK` | 每次交接都按**六类**给状态：基于哪一版 / 已确认什么 / 仍在猜什么 / 允许做什么 / 产物在哪里 / 怎样算完成 |
| **③ 依赖显式化** | `QueryIntent.depends_on` / `acceptance` | 每个子任务声明**依赖谁**、**怎样算完成**；交接时按依赖取记忆，不把一大堆无关结果全灌进去 |
| **④ 复查循环** | 路由规则「做完一个 → 先回规划器」 | 每完成一个子任务就回规划器，拿**实际结果**判断：继续 / 调整后续任务 / 到此为止 |

执行器写完记忆后立刻广播一条 `memory` 事件，所以界面上"这一步产出了什么、能被谁复用"是看得见的：

```
执行 → 🧠 写入共享记忆 · sql_id=44 · 10 行
       查库存小于 10 的商品 —— 查询返回 10 行
       可复用实体：products.id = 1、3、5、9、6、2、4、7、8、10
```

下一个子任务的生成器拿到的就不是"上一步做了点事"，而是：

```
———— 交接给你的工作状态（不是聊天记录）————
【本子任务】st-2 · 查这些商品的订单明细（查询）
【依赖】st-1
【已确认的事实】以下每条都来自**已经真正执行过**的语句，可回到来源核对：
  · st-1：查库存小于 10 的商品 —— 查询返回 10 行
      来源：SELECT * FROM products WHERE stock < 10（已执行 · 返回 10 行）
      products.id = 1、3、5、9、6、2、4、7、8、10
【仍在猜什么】任务描述之外的细节（字段选择、聚合口径）由你判断；
             但**上游事实里给出的值必须原样使用，不许自己造**。
【允许做什么】只能访问这些表：customers、order_items、orders、products；禁止任何 DDL。
【产物在哪里】本步要产出一条 SQL（会记进 sql_audit，带 sql_id 可追溯）。
【怎样算完成】拿到订单行。
```

**"已确认的事实"这一栏只可能来自共享记忆** —— 也就是执行器真跑过、带 `sql_id` 的那些条目。
模型自己说的话进不来。这条是刻意的：文档里那句「下游拿到的不是任务，只是一句传闻」，
说的就是没有这一层时会出什么事。

#### 复查不是"重新拆一遍"

复查用的是另一套提示词（`PLANNER_REPLAN_SYSTEM`），它只能给三种结论：

| `plan_action` | 含义 | 运行时怎么处理 |
| --- | --- | --- |
| `continue` | 剩余计划没问题 | 照原样做下一个 |
| `revise` | 后续任务要调整 | 换掉计划，并**清空上一版 SQL** —— 否则就是"改了计划却没改动作" |
| `finish` | 已有信息足够回答 | **把剩余任务从计划里去掉**，直接收尾 |

`finish` 那条为什么要把任务删掉而不是留着不管：留着的话，一致性校验会判「有子任务没落地」从而否决，
等于运行时把规划器刚做出的结论又推翻一次。计划缩了，账才对得上 ——
被去掉的任务会出现在 `plan` 事件的 `dropped` 里，界面上照样写明白"复查后判定不必再做：st-2、st-3"。

复查**同一个位置只做一次**（`replanned_cursor` 记着做到哪了），否则"做完一个就复查"会变成原地打转。

### 协作时序图

点顶栏「📊 时序图」看整条链路的**时序图**（7 条生命线：用户 / 规划器 / SQL生成 / SQL校验 / SQL执行 / SQL修正 / 汇总审查）：

```
用户 ──提交问题──▶ 规划器
                    │  □ 判 mode / safety · 拆出 1 个任务
       为子任务 st-1 生成 SQL
                    ▼
                 SQL生成 ──□ 一层选表 · 生成 SQL · DELETE · 需确认
                    │  SQL 必须经过校验才能执行
                    ▼
                 SQL校验 ──□ 校验通过（零数据库操作）
                    │  校验通过，但属于需确认操作
                    ▼
                 SQL执行 ┄┄ ⏸ 需要确认：预计影响 3 行 ┄┄▶ 用户   （琥珀色虚线）
用户 ──✓ 确认执行──▶ SQL执行
                    │  □ 影响 3 行 · 5ms
       1 个子任务全部完成
                    ▼
                 汇总审查 ──✓ 交付结果──▶ 用户
```

- **灰实线**＝交接；**绿实线**＝通过/确认；**红虚线**＝否决/拒绝/取消；**琥珀虚线**＝暂停等人工确认
- **方框**＝该智能体的产出（含规划器的「🔁 复查」和「🧠 写入共享记忆」）
- 交接箭头下方若标 **护栏改道**，说明这一步模型想去别处、被运行时改到了另一处；
  这只是"护栏行使了决定权"，**不等于出错** —— 正常的推进（做完了接着做下一个）不会标成告警
- 灰色横条＝轮次分隔（修正后进入第 2 轮会另起一段）
- 右上角**导出 PNG**（丢进 PPT / 文档）或**导出 SVG**（矢量，随意缩放）

### 数据流转链路（点顶栏「🔀 数据流转」）

时序图看的是**形状**，这个看的是**内容**：每一次交接，前者到底把什么交给了后者。

```
共 6 次流转 · 规划器复查 2 次 · 共享记忆 3 条 · 护栏改道 1 次 · 轮次 1 · 事件 40 条

② SQL生成 ──▶ SQL校验        护栏改道
   模型建议交给 SQL执行  →  护栏改去 SQL校验
   理由：SQL 必须经过校验才能执行
   产出 · 第一层选表（只看表简述与关系）
     选中：customers、order_items、orders
     依据：按关键词选中 orders
   产出 · SQL        [只读] SELECT
     SELECT * FROM products LIMIT 20

④ SQL执行 ──▶ 规划器          按模型的建议交接
   产出 · 🧠 共享记忆   agent_memory   只有执行器真跑过的才算事实
     查库存小于 10 的商品 —— 查询返回 10 行
     来源 sql_id=44 · 10 行 · 已核对
     可复用实体：products.id = 1、3、5、9、6、2、4、7、8、10

⑤ 规划器 ──▶ SQL生成          按模型的建议交接
   产出 · 🔁 规划器复查    剩余计划不变，继续做
     复查结论：已完成 1 个，拿到 1 条已确认的事实；它们不影响剩余任务的前提，按原计划继续。
     ✓ st-1 [查询] 查库存小于 10 的商品    依赖 … · 完成标准：拿到商品 id 清单
     · st-2 [查询] 查这些商品的订单明细    依赖 st-1 · 完成标准：拿到订单行
```

每一段都包含：

| 看什么 | 说明 |
| --- | --- |
| **谁 → 谁** | 这次交接的两个智能体 |
| **护栏有没有改道** | `按模型的建议交接` / `护栏改道`；改道时把**模型原本想去哪**和**护栏的改道理由**并列写出 |
| **流转的内容** | 这一步的产出：任务拆解 / **复查结论** / 选中的表 / SQL 与风险 / 每条校验项 / **写入的共享记忆** / 确认请求与级联提醒 / 执行结果 / 最终答复 |
| **结束方式** | 正常结束、主动停止重试、修正智能体放弃、出错，都会单独成段 |

顶部汇总条给出**总流转次数**、**规划器复查次数**、**共享记忆条数**和**护栏改道次数**。
右上角「展开全部原始结构」可以一次性铺开所有原始数据。
数据全部来自 `agent_event` 表（可逐条回放），刷新页面后依然完整。

右上角还能**导出 HTML**：得到的是一份**自包含**的单文件页面 —— 样式全部内联，
不引任何外部资源、不用连网、不用起服务，拷到别的机器上双击就能在任意浏览器打开。
导出时「真实传递过去的内容·完整结构」会**强制展开**：
静态页里没有那个折叠开关，折起来反而把最该看的部分藏了。

#### 摘要之上，还有一层「真实传过去的内容」

上面那些是人话摘要 —— **是我挑的字段**。摘要会骗人，所以每个卡片底部都附一段
**原样落库的完整结构**：这一步的所有原始事件 + 节点 `return` 出去的状态增量。

为什么需要后者：这个系统里智能体**只通过共享状态通信**，没有点对点消息。
LangGraph 把每个节点 `return` 的字典合并进状态，下一个节点读到的就是这个 ——
而那才是「真实传过去的内容」。

实测同一个节点「广播了什么」和「交出去了什么」的差集：

| 智能体 | 广播的事件 | **只存在于状态增量、从没广播过**的字段 |
| --- | --- | --- |
| 规划器 | `node_start` `plan` `node_end` | `cursor` `replanned_cursor` `plan_note` `last_agent` `next_agent` `status` `version` |
| 生成器 | `node_start` `tables` `sql` `node_end` | `checks: null` `confirmed: false` `result: null` `next_agent` |
| 校验器 | `node_start` `check`×6 `verdict` `node_end` | `attempts` `checks` `history`（含查询行） |
| **执行器** | `node_start` `result` `memory` `node_end` | **`explain`（完整 EXPLAIN 执行计划树）** **`memory` 的完整版（含 `columns`/`rows`/`sql_text`，广播里只有摘要）** `result` `history` `cursor` |

最典型的是执行器：它只广播了「返回 8 行」，但它交出去的状态里带着
**整棵 EXPLAIN 计划树**（`Seq Scan` / `Plan Rows` / `Total Cost` …）和
**模型自己建议的 `next_agent`**（护栏改道前的原始值）—— 这两个在事件流里一个字都看不到。

所以多了一个事件类型 `state_delta`，由编排器在每个节点返回后落库：

```python
def traced(role, fn):
    """把节点真正 return 出去的状态增量记成事件。"""
    async def run(state):
        out = await fn(state)
        await rt.emit(state["global_task_id"], role, "state_delta",
                      {"keys": sorted(out), "delta": _slim(out)}, ...)
        return out
    return run
```

`_slim` **只裁长度、不裁结构**：列表超过 20 项只留前 20、字符串超 1500 字截断，
但键名和嵌套关系一个不少（砍掉键名就等于又变成一句总结）。
深度上限给到 12、另配 3000 节点总预算兜底 —— 早期设 5，结果 EXPLAIN 的 `plans`
直接被砍成「层级过深」，正好把最有价值的部分裁掉了。

### 汇总答复长什么样

最后那个气泡才是**交付物**，所以它不能是一句「影响 8 行」—— 用户问「北京客户的订单总额」，
就得看见数字。汇总审查器拿到的输入里带着每个子任务**查询返回的 `columns` 与 `rows`**，
并被要求用 **Markdown** 产出成品：

```
针对「查一下北京客户的订单总额」，共处理 1 个数据操作。

**st-1** · 查一下北京客户的订单总额

| id | name | phone      | city | level | created_at           |
| -- | ---- | ---------- | ---- | ----- | -------------------- |
| 1  | 张伟 | 13800000001 | 北京 | 金牌  | 2024-03-11 02:20:00  |
| 2  | 李娜 | 13800000002 | 北京 | 银牌  | 2024-07-02 07:40:00  |
| …  |      |            |      |       |                      |
```

提示词里写死了三条边界：

- **禁止只写「返回 N 行」而不给数据** —— 那等于没有回答用户
- 行数太多时注明「共 N 行，这里展示前 M 行」
- **表格里每一个值都必须来自执行结果**，一个都不许编

界面把这份 Markdown 渲染成真正的 HTML 表格（只支持标题 / 加粗 / 行内代码 / 列表 / 表格），
而且**先转义再套标签** —— 答复里就算夹了 `<script>` 也注入不进来。

离线模式（`LLM_MODE=mock`）产出**同样形状**的答复，否则离线跑通了也说明不了线上没问题。

几条刻意的取舍：

- **token 是响应里带回来的真数，不按字符数估算** —— 估算出来的账单没法对账。
  为此结构化输出走 `include_raw=True`：解析结果照旧，同时把原始响应留下（用量只在那儿）。
- **读不到就记 0**，不猜。各家字段名不一样（`usage_metadata` /
  `response_metadata.token_usage`），`scripts/check_usage.py` 把这些形状都验了一遍。
- **缓存命中单独记一列**：DeepSeek 会给提示词缓存命中量，它和输入 token 是**包含**关系，
  混在一起就算不出真实花费。上面这份里 48% 的输入是命中缓存的。
- **失败的调用也记**（token 记实际拿到的、`ok=false` + 错误原文）——
  重试一样花了输入 token，漏掉的话账单会比真实花费少。
- **按 `stage` 分开记**：同一个生成智能体，选表和写 SQL 的消耗差一倍，
  只看角色分组会把这件事盖住。
- 离线 `LLM_MODE=mock` **没有大模型调用**，面板直接说明这一点，
  而不是显示一堆 0 让人以为"这个模型真省"。
  （反过来：现在跑在 mock 上、但这一轮是以前用真实模型跑的 —— 那批历史明细照样显示，
  只有"确实一条调用记录都没有"时才给 mock 提示。）
- 不给金额：单价经常变，硬编码一个价目表只会给出一个错的数。
  token 数和对账口径是准的，换算成钱由你按当期价格算。
- **只统计这一轮，不做「全部会话累计」**：这个面板回答的是"这一轮花了多少"，
  把别的会话的账混进来，数字就不好对账了（也容易让人以为贵的是这次）。
  （`GET /api/usage` 这个接口还在，只是界面不展示。）
- 右上角**导出 PNG**：面板内容重画成一张 SVG 再栅格化成 2 倍图。
  不用 html2canvas 那类方案 —— 要么引 CDN（内网就废），要么用 `<foreignObject>`
  （部分浏览器根本画不出来、中文还容易缺字）。自己拼的 SVG 只含 rect / text / line，
  任何浏览器都能正确出图，表宽还跟着内容走、不会被面板宽度截断。
- 消耗是**观测**，不是业务：写账失败只记日志，不影响主流程（`record_llm` 里吞掉异常）。

## 3. 四层安全防线（都有实测）

### 第一层 · 静态防线（`app/sql_guard.py`）

| 级别 | 语句 | 处理 |
| --- | --- | --- |
| 🚫 **禁止** | `DROP` `TRUNCATE` `ALTER` `CREATE` `GRANT` `COPY` `DO $$` `SELECT INTO`、多语句、事务控制、读文件函数、**目录里没有的表**… | **直接拒绝** |
| ⏸ **需确认** | `DELETE`（任何形式）；`UPDATE` 无顶层 `WHERE` | 暂停等确认 |
| ✅ **自动** | `SELECT` / `WITH`；`INSERT`；`UPDATE` 带 `WHERE` | 直接执行 |

细节处理过：抹掉字符串与注释后再扫描（`WHERE x='DROP TABLE'` 不误报、`DROP/**/TABLE` 不漏报）；
用 token 层级取**顶层 DML**（`WITH x AS (SELECT…) DELETE FROM t` 正确识别为 DELETE）；
剥掉括号内容再找 `WHERE`（子查询里的 WHERE 不算，避免全表更新被误判为安全）。

**55 个对抗性用例全过**：`python scripts\check_guard.py`
（白名单直接取自 `app/catalog.py`，所以「库里存在但目录里没有」的表一律不认）

### 第二层 · 按表信息核对（`app/catalog_check.py`）

`sql_guard` 挡的是「表不在白名单里」，但挡不住**「表对、字段是编的」**——
语法没错、表白名单也过，照样进执行器。所以在校验器里加了这一关：

```
SELECT id, nickname FROM customers LIMIT 10
→ rt-catalog = fail：按表信息核对不过：nickname（目录里没有这个字段）
→ checks.passed = False   →  路由去 fixer（**永远到不了执行器**）
```

它读的是 `app/catalog.py`，**不碰数据库**（校验阶段零数据库操作）。能认出来的写法：
别名（`c.name`）、函数（`date_trunc('month', created_at)`）、输出别名（`AS n` 之后 `ORDER BY n`）、
CTE（`WITH x AS (...) SELECT * FROM x`）、schema 前缀（`public.products`）、`::type` 强制转换。

**保守优先：拿不准的宁可放过。** 误杀一条正常查询，比漏掉一条编造字段更糟 ——
所以 `check_guard.py` 里放行用例（14 条）刻意比拦下用例（4 条）多，
把各种真实写法都压过一遍。

### 第三层 · 数据库权限兜底（**真正的保证**）

应用层校验可以被绕过，权限绕不过去。执行用户 SQL 用的是受限角色：

```sql
CREATE ROLE agent_sql_runner LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON customers, products, orders, order_items TO agent_sql_runner;
-- 刻意不给任何 DDL 权限
```

`python scripts\check_isolation.py` 实测：

```
cs_v1        读/插/改/删 ✓   删表/清空/改结构/建表/建索引/删库 全部被拒
             提权尝试（GRANT/REVOKE/改owner）→ 权限快照前后完全一致
agent_sql    连项目自己的系统表都读不到（permission denied）
```

### 第四层 · 执行沙箱

- 每条 SQL 包在**显式事务**里，出错自动 `ROLLBACK`
- 连接级 `statement_timeout=5000ms`
- 查询结果截断到 `MAX_ROWS=500`
- 预估影响超过 `CONFIRM_ROW_THRESHOLD=1000` 也转人工确认

## 4. 人工协作（human-in-the-loop）

需确认的操作，执行器调用 LangGraph 原生 `interrupt()` 暂停，前端渲染确认卡片：

```
⏸ 需要你确认后才执行
   DELETE FROM orders WHERE status = '已取消'
   风险：需确认（DELETE）｜ 涉及表：orders ｜ 预估影响：3 行
   ⚠ orders 的删除会级联删除 order_items.order_id
   [ 确认执行 ]   [ 取消 ]
```

用户点确认 → `POST /api/runs/{id}/confirm` → `Command(resume=...)` 继续跑。
**取消的话一行都不改**（审计里停在 `await_confirm`，不会有 `executed`）。

> ⚠️ **Python 3.10 的坑**：LangGraph 给异步节点注入 config 靠
> `asyncio.create_task(coro, context=ctx)`，而 `context=` 是 **3.11+** 才有的。
> 3.10 上节点里调 `interrupt()` 会报 `Called get_config outside of a runnable context`。
> `app/graph.py` 的 `_with_config` 手动补了这个上下文，等价于 3.11+ 的默认行为。
>
> 这个坑有个后遗症：`interrupt()` 之前的代码在恢复后会**重跑**，
> 所以执行器把 EXPLAIN 放在 `interrupt` 之前（纯读、无副作用），
> 而 `node_start` / 租约等副作用一律放在 `interrupt` 之后。

## 5. 表设计 · 两库隔离

| 库 | 表 | 谁用 |
| --- | --- | --- |
| **cs_v1** | `customers` / `products` / `orders` / `order_items` | 智能体执行 SQL 的**目标**（受限角色只有 DML） |
| **agent_sql** | `agent_run` / `agent_task` / `agent_event` / `sql_audit` / `agent_memory` / `llm_call` | 项目**自身**记录（只有应用的 postgres 连接能碰） |
| `config/tables.json` | 上面 4 张表的表名 / 字段 / 关系 | 智能体关于「库里有什么」的**唯一依据**（数据文件，非代码） |

`agent_memory` 就是**共享记忆**：`(global_task_id, sub_task_id)` 唯一，
一条记忆 = 一个已执行过的子任务留下的「带来源的事实」——
`claim`（结论）+ `sql_id`/`sql_text`（来源，可回查）+ `entities`（抽出的主键值，供下游直接引用）+ 返回的行。

它和业务库的关系，按文档里那句来：**共享记忆记录引用和状态，不能取代权威数据源** ——
所以每条都留着 `sql_id`，要核随时能回到 `sql_audit` 里的原句。

`llm_call` 是**消耗明细**：每次大模型调用一条，记 role / stage / 轮次 / 子任务 / 模型 /
输入输出 token / 缓存命中 / 耗时 / 成败。token 是响应里的真数，不是估算的。

业务表刻意带外键关系（`orders.customer_id → customers`、`order_items.order_id → orders ON DELETE CASCADE`），
既能耗演示 JOIN/聚合，也能演示"删除会级联"这种真实提醒。

`agent_run` 除了一轮任务本身，还带 `conversation_id` / `turn` 两列支撑多轮对话；
`agent_event` 里除了各智能体的广播，还有编排器补记的 `state_delta`（节点真正交出去的状态增量）。

`sql_audit` 记下每条 SQL 的全程：`generated → validated / rejected → await_confirm → confirmed → executed / failed`，
含 `risk_level`、`est_rows`、`affected_rows`、`confirmed_by`、`error`、`duration_ms`。

### 三条克制原则（都来自踩坑）

**① 启动不碰业务库结构。**

服务启动（`Orchestrator.migrate()`）只做**一件事**：保证 `agent_sql` 里的账本表存在。
**刻意不执行 `sql/biz.sql`**。早期版本在这里无条件 `CREATE TABLE IF NOT EXISTS`，
结果「你手动删掉/改名一张业务表做测试」会在重启后被悄悄改回来 —— 测试环境被工具自己复原，比报错更难查。
建业务表是 `scripts/init_db.py` 的职责，边界划清：

| 动作 | 谁做 | 碰不碰 cs_v1 结构 |
| --- | --- | --- |
| 起服务 / 重启 | `run_server.py` | ❌ 不碰 |
| 建表 + 灌种子 | `scripts/init_db.py --reset` | ✅ 只有它碰 |
| 智能体执行 SQL | 受限角色 `agent_sql_runner` | ❌ 权限上就做不了 DDL |

**② 表不存在时，绝不换一张同构表顶上。**

这是「换了问题」而不是「修好了 SQL」。比如 `products` 不存在、库里有 `products1`，
模型很容易"聪明地"改写成 `FROM products1` —— 语句能跑通，但回答的已经不是用户问的那张表了。
所以这条规则在**三层**同时钉死：

- **系统目录**（`app/catalog.py`）：白名单只有目录里定义的表。`products1` 连模型都看不到，
  `sql_guard` 直接判「未授权」
- **提示词**：生成器的选表步骤「只从给出的表名里选，绝对不许编造表名」；
  修正器「表名不存在时，绝不许换成另一张同构表」
- **运行时护栏**（`sql_guard.check_intent_tables`）：SQL 用到的表必须落在**生成器选定的表**之内，
  且拒绝文案直接说明「不允许为了绕开『表不存在』而更换表名 —— 那等于换了问题」

模型可能想抄近路，但**运行时不认这种"修好"**。

**③ 校验阶段不读库，表结构由外部数据文件定义。**

表和字段写在 `config/tables.json`（可用 `TABLES_FILE` 指到别处，运行时可 `POST /api/catalog/reload` 热换），
`schema_info` 那份「读 information_schema 的快照」整个删掉了，代码里也没有任何写死的表名/字段名。
这样「系统以为的库」和「真实的库」可以不一致 —— 而不一致时**报错必须由执行器抛出来**，
这才测得出修正智能体到底会不会处理。系统自己去偷看现实，等于把这个测试点抹掉了。

## 6. 八条运行时一致性不变量（`app/validators.py`）

| ID | 不变量 |
| --- | --- |
| S1 | 每条 SQL 都要有意图说明并对应到子任务（没有 SQL 时是空真） |
| S2 | SQL 只能访问被授权的表 |
| S3 | SQL **必须经过校验**才能执行 |
| S4 | 静态判定禁止的语句**永远不能被执行** |
| S5 | 需确认的操作必须有**用户确认记录** |
| S6 | 执行过的 SQL 必须有结果留痕 |
| S7 | 子任务覆盖率 —— **按 `mode` 判**：`execute` 要求每个子任务都落地；`chat` 反过来查「有没有偷偷执行」 |
| S8 | 所有执行记录都要带幂等键（防"确认后重复执行"） |

只要有一条 fail，汇总审查器**不得** approve —— 硬门禁，模型说了不算。

> S7 为什么要分模式：用户说了「不要执行」，那"没执行"就是**正确行为**。
> 如果还按"每个子任务都要执行"去判，系统会被自己的不变量判失败 —— 那就荒唐了。

### 修正闭环的坑（已修，来自真实使用的反馈）

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 修正智能体反复生成 `public.products.x` 这种形式 | `extract_tables` 遇到 `schema.table` 时把 **`public` 当成表名**，于是「加 schema 前缀」这种**本来合理的修正**被误判成越权 | 正则区分 schema 前缀：`public.` 放行、`pg_catalog`/`information_schema` 拒绝；拒绝文案也改成「**不要写 schema 前缀**」 |
| 修正一遍遍重复，**没人感知** | 没有「无进展」判定，只是把轮次耗尽 | ① 把**已试过并失败的 SQL 列表**喂给修正智能体，并明令「不许重复」；② 给它一个 `give_up` 出口，判断修不了就直接说；③ 路由护栏新增**无进展检测**：同一条 SQL 失败 ≥2 次、或同一错误连续出现 ≥2 次 → **主动停止**并抛出 `stalled` 事件 |
| 表被改名后，修正智能体**永远等不到真实报错** | 校验阶段的 `EXPLAIN` + `db.diagnose()`（查 `information_schema` 列出可见/缺失的表）等于**校验阶段自己偷看现实**：表一被改名，系统立刻自己发现并改口，报错根本轮不到修正器看 | **校验阶段彻底不碰数据库**，`db.diagnose()` 整个删掉。语法/语义/表是否存在全部由**执行器** EXPLAIN 时暴露，数据库原话原样交给修正器 |
| 模型把不存在的表**换成一张同构表**顶上（`products` → `products1`） | 表清单来自「受限角色能看见什么」，而库里恰好有张同构表，于是它"合理地"改了表名 —— 语句跑通了，回答的却已经是另一个问题 | 表清单改为**系统内置目录**（`app/catalog.py`），白名单不再来自库。目录外的表连模型都看不到，`sql_guard` 直接判未授权；`check_intent_tables` 再拦一道「目录里有、但这次任务不该用」 |
| 「打招呼」和「被拒绝」被自己判成**失败** | S1 的写法 `not bool(history) is False and not bad1` 在 history 为空时算出 False | 改成空真：没有 SQL 就没有「缺意图说明」这回事 |
| 被静态防线拦下，S7 还判一次「子任务未落地」→ veto | 明明是**主动拦下**（正确行为），却又被自己的不变量判失败，报告自相矛盾 | `validate(blocked=...)`：静态防线拦下时不执行是**预期行为**，S7 判 pass 并说明原因 |
| **方向跑偏**：加了一堆「贴 SQL → 评估 / 修正」的模式与调度权 | 越做越复杂，而且**给 SQL 开了旁门** —— 不是从任务生成、而是从外部塞进来 | 整个删掉。**SQL 只由生成器根据任务产出**，模式只剩 `chat` / `execute`；入库的每一条 SQL 走同一条链路 |
| **用户贴的 SQL 被悄悄换表执行了** | 规划器把「修正 users 表那条语句」当成了任务，生成器看到目录里没有 `users`，就"聪明地"换成 `customers` 顶上 —— 校验全过、执行成功、返回 0 行。护栏拦不住：它拿的是**生成器自己选定的表**去比对，自己跟自己比当然过 | 两条**运行时**硬拦（不交给模型判断）：① 输入里夹带 SQL → 直接按越界拒；② 用户提到的表不在目录里 → 直接说明不可用，**绝不拿别的表顶替**。前者顺带保证入库的 SQL 只出自生成器 |
| **表对、字段是编的** 拦不住 | `sql_guard` 只做表级白名单，字段层没人管；语法没错就能一路走到执行器 | 新增 `app/catalog_check.py`：按表目录静态核对表和字段，作为校验器的 `rt-catalog` 一关。实测字段写错 → `checks.passed=False` → 路由去 fixer，**永远到不了执行器** |
| **表信息写死在代码里** | `app/catalog.py` 里直接定义 4 张表，验证逻辑就绑死在这一套 schema 上；换库、换租户都得改代码 | 表信息搬到外部数据文件 `config/tables.json`（`TABLES_FILE` 可指到别处，`POST /api/catalog/reload` 可热换）。**验证逻辑一处硬编码都没有** —— 换一套表，白名单、两层表结构、字段核对、目录外表识别全都跟着变 |
| **三个子任务像三个孤军** | 规划器只拆任务、任务之间没有任何结果传递：1 查出来的商品 id，2 和 3 拿不到，于是各查各的全表；`depends_on` 只在提示词里躺着，从来没进过任何一条真正的交接 | 四件事一起补：① 执行器写**共享记忆**（`agent_memory`，带 `sql_id` 可回查，`verified` 只由执行成功置位）；② 交接按文档的**六类结构**给全（`HANDOFF_BLOCK`）；③ `depends_on` 真的用来**取哪些记忆**，`acceptance` 写进交接；④ 每做完一步回规划器**复查**（`continue` / `revise` / `finish`） |
| **复查做成了原地打转** | "做完一个就复查"如果没有记号，复查完回到同一个位置又满足条件，图会一直绕 | `replanned_cursor` 记住复查到哪了；同一个位置只复查一次。`revise` 时**必须清空上一版 SQL**，否则就是"改了计划却没改动作" |
| **气泡把三个子任务挤在一起** | 前端气泡按 `runId::round::role` 分组，而三个子任务都在 `round=0`、都是 `generator` —— 于是三份生成结果叠进同一个气泡，看起来就像什么都没传下去 | 气泡改成按**一次节点调用**分组：`node_start` 开一个新气泡并登记为该角色的"当前气泡"，它后续的事件都落进去 |
| **"统计 token" 拿到的永远是 0** | `with_structured_output()` 默认只返回**解析后的 Pydantic 对象**，原始响应（用量只在里面）被丢掉了 —— 于是只能按字符数估算，而估算的账单不能对账 | 结构化输出改成 `include_raw=True`：`parsed` 照旧，`raw` 一起拿回来读 `usage_metadata`。读不到就**记 0**，不猜；缓存命中单列一列（它和输入 token 是包含关系）；失败的调用也记（重试一样花输入 token） |
| **消耗清单接口一打开就 500**（`'str' object has no attribute 'isoformat'`） | 账本不同方法返回的时间**形状不一致**：`list_tasks` / `list_audit` 给 datetime，而 `list_events` / `list_memory` / `list_llm_calls` 已经在账本层转成字符串（它们要进 state 与事件流）。序列化层却一律当 datetime 处理 | 序列化层的 `_iso()` 改成**幂等**：`None` / 字符串原样返回，datetime 才 `isoformat()`。教训是这类 bug **只在真有数据时才炸** —— 当时用 mock 模式测（没有 `llm_call` 行）一路 200，正好把冒烟测试骗过去了；现在 `check_usage.py` 把「空 / 字符串 / datetime」三种形状都钉进自检里 |

界面上会明确显示：

```

    停止重试：同一条 SQL 已经失败 2 次，修正没有产生新内容
    ▽ 已经试过并失败的 2 版 SQL
       第 1 轮  ...失败原因...   <SQL>
       第 2 轮  ...失败原因...   <SQL>
    修正没有产生新内容，继续重试只会浪费轮次，因此主动停下并把过程摊开给你看。
```

## 9. 演示讲解顺序（5 分钟）

1. **先来一个正常的**：「查一下北京客户的订单总额」→ 规划→生成→校验→执行一气呵成，
   答复里是一张**真表格**
2. **看多子任务的连续性**：问一个必须分三步的问题（例如
   「先找出库存小于 10 的商品，再看这些商品都有哪些订单，最后统计涉及多少客户」）→
   看它是不是**一步一停**：每做完一步回规划器复查，执行器那一步多出「🧠 写入共享记忆」，
   下一条 SQL 的交接里带着上一步查出来的**具体 id**，而不是"上一步做了点事"
3. **看意图识别**：连着问「你好，你能做什么？」→「给我一条 SQL，不要执行」→
   「帮我看看这段 SQL 对不对：`SELECT city, count(*) FROM customers GROUP BY city`」，
   三条链路完全不同，而且**后两条一行数据都没动**
4. **看多轮对话**：在同一会话里追问「那再按城市分组看看」→ 规划器拿到了上一轮实际执行的 SQL
5. **看链路不固定**：点「📊 时序图」看形状（含复查与共享记忆那两行）；
   点「🔀 数据流转」看每次交接过去的内容，以及被护栏改道的那一步（模型原本想去哪 + 护栏为什么改），
   再展开「真实传递过去的内容」看原始结构
6. **危险请求**：「帮我删掉 orders 表」→ 规划器拒绝，解释 + 给替代方案
7. **人工协作**：「删掉所有已取消的订单」→ ⏸ 暂停，看确认卡片里的影响评估与级联提醒 → 确认执行
8. **收尾讲安全**：应用层拦截可以被绕过，但**数据库权限绕不过去** —— `check_isolation.py` 实测为证

> 技术选型可以不同，边界不能空着。
