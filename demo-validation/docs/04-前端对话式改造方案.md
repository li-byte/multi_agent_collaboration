# 04 · 前端对话式改造方案

> ⚠️ **本文档描述的是早期「带快照」版本的对话式改造。**
> 当时提到的「追问哪一版代码 / 哪个时间窗」在通用版里**已被去掉**
> （那是系统的内部问题，不该问用户）。当前实现见 **`docs/05-通用版设计.md`**。
> 本文保留作为设计过程记录。

> 目标：把「表单 + 卡片时间线」改成「对话框 + 群聊式协作流」
> 状态：**P1 已实施**（纯前端，后端一行未改）；P2 待定
> 影响文件：`web/index.html`（已改）；后端仍只在 P2 才动

## 0. 已实施情况（P1）

| 确认项 | 结论 |
|---|---|
| 对话范围 | **全过程**——四个智能体轮流发言，不是只用来发起任务 |
| 缺快照信息 | **追问用户**（点选项或打字均可） |
| 原卡片时间线 | **已彻底删除**（`renderTimeline` / `renderBlock` 已移除） |
| 右栏 | **已收成顶栏三个按钮 + 覆盖层**（时序图 / 一致性校验 / 账本） |

实测验证：

```
前端 JS 语法（Node --check）   ✅ 通过
解析函数单测                   ✅ 11/11（时间窗、点表述、commit 抽取）
API 端到端自检                 ✅ 11/11（后端未受影响）
页面特征检查                   ✅ 对话容器 / 气泡 / 追问选项 / 交接条 / 三按钮
                               ✅ 旧时间线已移除 / 旧右栏已移除
```

**实施中发现并修掉的两个坑：**

1. 系统总结气泡里的动作按钮（`data-act`）和追问选项（`data-field`）都用了 `.opt` 类，
   点击动作按钮会误触发「填入草稿 → 建档」，导致莫名开一个新会话。
   已在选择器里加 `&& t.dataset.field` 守卫。
2. 回放历史会话时，用户当时说的那句话不在账本里。
   已改为从 `run.alert.message` 复原一条用户气泡，让会话读起来完整。

## 1. 为什么要改

现在左栏是一张表单（标题 / 告警 / 时间窗 / 快照 commit），一眼看上去就是个**通用告警入口**：

- 4 个字段全是「参数」，没有一个是「领域对象」
- 输入就是一段自由文本原样丢进去
- 界面上到处只有「机制的形状」，没有「问题的形状」

改成对话式的价值不只是好看，而是它能把文章的核心直接演出来：

| 现在的表单 | 对话式 |
|---|---|
| 用户手填「快照 commit」 | 系统**追问**「这次看哪一版代码？」← 正是文章里那句追问 |
| 四个角色的产出是四张卡片 | 四个角色**轮流发言**，协作关系一眼可见 |
| 否决是一条红色回流线 | 审查器**明确说**「我不通过，理由是…，退回给研究员」 |

## 2. 现状盘点：哪些能直接复用

先看清楚，免得白改。现在 `web/index.html` 里已经有的东西：

| 已有 | 能否复用 |
|---|---|
| `store.blocks`（`round::role` 唯一的分块） | ✅ **完全复用**，一个块 = 一个气泡 |
| `handleEvent(e)` 事件分发 | ✅ **完全复用**，不用动 |
| `ensureBlock()` / `newBlock` 逻辑 | ✅ 复用 |
| SSE 订阅 + 断线重连 + 历史回放 | ✅ 复用 |
| `ROLE_CN` 中文角色名 | ✅ 复用（还要加头像） |
| 证据抽屉 + `openDrawer()` | ✅ 复用 |
| `buildSequence()` / `renderSequence()` SVG 时序图 | ✅ 复用，入口位置调整 |
| `parseWindow()` 时间窗解析 | ✅ 复用，挪到对话输入解析里 |
| 右栏三个 Tab 渲染函数 | ✅ 复用，改成覆盖层内容 |

> **关键结论：数据层不用动，只换渲染层。**
> `handleEvent` → `store.blocks` 这条链路保持原样，只是把 `renderBlock()`（卡片）换成 `renderBubble()`（气泡）。

**右栏去哪了？** 三个 Tab 收成顶栏按钮，点开是覆盖层（全屏），因为：
- 对话流需要宽度
- 细节（验收清单、8 条不变量）**默认折在气泡里**，想看直接展开，不用跳栏

## 4. 核心：事件 → 气泡 映射表

后端已经在发这些事件，前端只要把它们翻译成"谁在说话"：

| SSE 事件 | 变成什么 |
|---|---|
| 用户点击发送 | **右侧蓝气泡**（用户） |
| `run_created` | **系统气泡**：「已锚定事实：commit-b · 14:00–16:00」 |
| `node_start` | **正在输入占位**：`(研) 研究员正在查证据…` + 三点动画 |
| `node_end` | 把占位替换成正式发言摘要 |
| `handoff` | **交接条**（气泡之间的细条）：「规划器 → 研究员：交接 4 个子任务」 |
| `finding` | 挂到研究员气泡里的「结论行」：状态徽标 + 主张 + 证据 chip |
| `artifact` | 挂到执行器气泡里的「产物卡」：基于哪版 / 覆盖窗 / 验收清单 |
| `consistency` | 挂到审查器气泡里的「8 条不变量」（pass 折叠，**fail 自动展开**） |
| `review` | 审查器气泡：`✓ 通过` / `✕ 不通过`（红）；否决时追加「↺ 退回XX · 版本 a→b」 |
| `done` | **系统气泡**：「排查完成，共 N 轮，M 次回流」+ 操作按钮 |
| `error` | 红色系统气泡 |

**头像用中文首字**，顺手解决英文看不懂的问题：
`(规)` `(研)` `(执)` `(审)`，各自配色 —— 规划器紫 / 研究员青 / 执行器橙 / 审查器玫红。

> 一个「角色 + 一轮」= 一个气泡，和现在的 `round::role` 分块规则**完全一致**，所以 `store.blocks` 不用改。

## 5. 对话式建单流程（含追问）

这是唯一需要新逻辑的地方：用户说人话，但协作需要一个**结构化快照**。

```
用户输入自由文本
      │
      ▼
 【快照提取】抓 repo / commit / time_window
      │
      ├── 缺字段 ──▶ 返回追问：这次看哪一版？时间窗呢？
      │               前端渲染成「系统追问气泡 + 可点选项」
      │               用户点一下按钮即可，不用打字
      │               （把已收集的字段暂存在 store.draft 里）
      │
      └── 齐了 ────▶ 建 run → 订阅 SSE → 开始跑
```

追问气泡长这样（点按钮，不打字）：

```
系统：开始排查前，先把事实锚死 ——
      这次看哪一版代码？
      [ commit-a（13:40 发布） ]  [ commit-b（15:20 发布） ]
      时间窗？
      [ 14:00–16:00 ]  [ 15:20–16:30 ]  [ 自定义… ]
```

**这一步不是多余的** —— 它正是文章里那句追问的可视化：

> 「哪一版代码？」「哪段日志？」「这个结论是已经确认的事实，还是 Researcher 的判断？」

## 6. 边界：纯前端 vs 需要后端

**只改前端就能做（P1）**

- 表单 → 对话框
- 卡片 → 气泡
- 右栏 Tab → 顶栏按钮 + 覆盖层
- 输入解析：前端用正则抓 `14:00 到 16:00`、`commit-b`，`parseWindow()` 已有
- 抓不到就出选项按钮（纯前端逻辑）
- **后端一行不动**

**需要后端配合（P2，可选）**

- `POST /api/chat`：用 LLM 从自然语言抽 `repo / commit / time_window`
  - 比正则聪明，能听懂「昨天下午两点到四点」「上周五那次发布之后」
- 缺字段时返回 `{need: [...]}` 让前端渲染追问

> **建议：先做 P1 纯前端改造，把体验做出来；好用再加 P2。**
> 这样改动成本可控，后端稳定不动。

## 8. 风险与注意点

| 风险 | 处理 |
|---|---|
| **几秒等待像卡死** | 每一步 `node_start` 必须先出「正在查证据…」占位 + 三点动画 |
| **气泡太长** | 验收清单、8 条不变量、假设默认折叠，仅 fail 自动展开 |
| **回流看不见** | 否决气泡必须显眼（红色）+ 独立的「↺ 退回XX · 版本 a→b」条 —— 这是全篇重点 |
| **自动滚动抢屏** | 判断用户是否在底部附近，不在就不滚 |
| **引入聊天库** | ❌ 不引。继续手写，保持无构建、可离线、不依赖 CDN |
| **历史会话回放** | 沿用 `GET /api/runs/{id}` + 事件回放，直接重建成气泡流 |
| **会话列表语义** | 现在一个 run 就是一次排查，等价于一个"会话"，不用新建概念 |
