# 05 · 通用版设计（当前实现）

> 状态：**已实施并验证**
> 取代：`docs/01` ~ `docs/04`（那四份描述的是早期「带快照」的场景版）

---

## 1. 变更说明：去掉了什么

早期版本把一致性锚在**快照**上（`repo / commit / time_window`），
结果整套东西都带上了运维味，而且**让用户去回答系统的内部问题**（"哪一版代码？"）。

通用版的需求很简单：

> **用户问一个问题、给一份资料 → 多个智能体协作处理 → 返回一个答案。**
> 问题可以是健康、代码、法律、任何行业的。

| 去掉 | 原因 |
| --- | --- |
| `snapshot`（repo / commit / time_window） | 只对代码类问题有意义，换个行业就废了 |
| 追问「哪一版代码」「哪个时间窗」 | 那是**系统的内部问题**，不该问用户 |
| `based_on_commit` / `covers_time_window` | 运维味的契约形状 |
| `V1_snapshot_pinned` / `V6_evidence_covers_window` | 依赖快照 |

## 2. 换成了什么

「同一份事实」原来靠快照保证，现在**靠引用保证**：

| 原来（场景版） | 现在（通用版） |
| --- | --- |
| 结论必须锚定 `commit-b` | **每条结论必须给出依据**（哪份资料 + 哪句原文） |
| 引用证据必须真实存在 | **摘录必须能在资料里逐字找到** |
| 必须覆盖时间窗后半段 | **拆出的每个子问题都必须被回答** |
| 用户提供 commit 和时间窗 | **用户提供资料**；没给就问他要 |
| mock 的 8 条假证据 | `source_chunk` 表：用户贴的原文，切成片段 |

---

## 3. 数据流

```
用户：问题 + 资料原文
        │
        ▼
  sources.build_chunks()          按空行切段，编号 D1-1 / D1-2 / D2-1 …
        │
        ▼
  source_chunk 表                 权威事实层：只写一次，只读不改
        │
        ├─ planner    拆成 2-5 个子问题（st-1 / st-2 …）
        ├─ researcher 逐个子问题查资料 → 结论 + citations
        ├─ executor   汇总成答案 → 每个分点带 citations + acceptance
        └─ reviewer   validators 跑 8 条不变量 → 硬门禁 → 通过 / 否决回流
                        │
                        ▼
                  返回给用户的答案
```

**没有资料就不建档**：`POST /api/runs` 直接返回 `400 need_material`，
前端据此渲染成"请贴资料"的追问气泡。

## 4. 契约（`app/state.py`）

```python
class Citation(BaseModel):
    source_id: str   # 'D1-2' = 第 1 份资料的第 2 段
    quote: str       # 原文摘录，必须逐字一致

class SubTask(BaseModel):        # 规划器
    sub_task_id: str
    question: str                 # 拆出的子问题
    why: str                      # 为什么要拆它
    depends_on: list[str]

class Finding(BaseModel):        # 研究员
    sub_task_id: str              # 回答的是哪个子问题
    claim: str
    status: Literal["候选","已验证","冲突","已否决"]
    citations: list[Citation]
    assumptions: list[str]        # 资料没写、只能推测的部分

class AnswerPoint(BaseModel):    # 执行器
    sub_task_id: str              # 一一对应子问题（覆盖率校验用）
    statement: str
    citations: list[Citation]

class Answer(BaseModel):
    answer_id: str
    summary: str                  # 一句话直接回答问题
    points: list[AnswerPoint]     # 必须覆盖每个子问题
    recommendations: list[str]
    acceptance: list[AcceptanceItem]
    caveats: list[str]            # 资料不足 / 有争议的地方，必须诚实列出
```

> `Answer.caveats` 是通用版新增的：**没有一个知识库能回答所有问题**，
> 所以「资料没说」必须是契约里的一等公民，而不是让模型硬编。

### 接入层适配器

实测 DeepSeek 会把嵌套对象序列化成 JSON 字符串、把 `list[str]` 写成换行拼接的长文本。
所以 `state.py` 用 `mode="before"` 校验器统一归一化，**契约本身不变**。
`scripts/check_contracts.py` 有 13 个对抗性用例守着这一层。

## 5. 八条不变量（`app/validators.py`）

| ID | 不变量 | 违反后果 |
| --- | --- | --- |
| `V1_answer_cited` | 答案的每个分点都要有原文依据，或**显式声明资料不足** | 否决回流 |
| **`V2_quote_verbatim`** | **引用的摘录必须能在资料里逐字找到** | 否决回流（**防编造**） |
| `V3_finding_cited` | 每条研究结论都要有原文依据，或显式声明资料不足 | 否决回流 |
| `V4_answer_cites_research` | 答案只能引用研究结论引用过的片段 | 否决回流 |
| `V5_acceptance_cited` | 每条验收条件都要有原文依据，或显式声明资料不足 | 否决回流 |
| **`V6_subtask_coverage`** | **拆出的每个子问题都要有答案覆盖** | 否决回流 |
| `V7_version_monotonic` | 状态版本必须被推进过 | 丢弃过期写入 |
| `V8_idempotent_side_effect` | 所有执行记录必须带幂等键 | 拒绝执行 |

### 逐字校验怎么做的（`app/sources.py`）

```python
def normalize(text):            # 去掉所有空白
    return re.sub(r"\s+", "", text or "")

def quote_matches(quote, content):
    q = normalize(quote)
    return len(q) >= MIN_QUOTE and q in normalize(content)
```

- **容忍空白差异**（换行、缩进不影响判定）
- **不容忍改写**：全角/半角括号不同、改标点、加省略号 → 一律判否
- **过短的摘录不算有效引用**（`MIN_QUOTE = 6`，防"的"这种）

### 两道防线的分工

| 防线 | 抓什么 | 靠什么 | 确定性 |
| --- | --- | --- | --- |
| 校验器 `V2` | 编造原文 / 引用不存在的资料 | 字符串逐字匹配 | ✅ |
| 审查器 | 曲解原文 / 依据不支持结论 | 回到原文核对语义 | ⚠️ 模型判断 |

运行时能证明"这句话确实来自原文"，**证明不了**"这句话支持这个结论"。
这就是审查器必须存在、而且能否决的原因。

## 6. 硬门禁与确定性回流

### 硬门禁（`app/agents.py::reviewer`）

```python
if not report.passed and out.decision == "approve":
    out = ReviewerOutput(decision="veto", ...)   # 模型的 approve 一律无效
```

只要有一条不变量 fail，审查器不得 approve，即使模型坚持放行。

### 回流什么时候发生

**完全取决于模型的真实表现 —— 没有任何人为注入。**

系统只做一件事：研究结论漏掉了某个子问题，或者答案里出现了「既没有依据、又没有声明资料不足」的分点，
运行时校验就 fail → 审查器被强制否决 → 退回研究员补查 → 版本 +1、进入下一轮。

真实运行里它会自然发生在这些情况：

| 触发条件 | 命中的不变量 |
| --- | --- |
| 规划器拆得很细，研究员第一次只答了一部分 | `V6` |
| 模型给出的摘录改写了原文（不是逐字复制） | `V2` |
| 答案漏掉了某个子问题 | `V6` |
| 答案引用了研究没查过的片段 | `V4` |

> 早期版本曾用 `DEMO_MODE` 注入一次「漏覆盖」来保证演示能出现回流。
> **已经移除** —— 演示要展示真实行为，不是剧本。
> 想看回流，就给一份**只覆盖问题一部分**的资料，它会自己触发。

## 6.1 「资料不足」是合法出路

资料不可能穷尽所有问题。所以系统必须允许回答「我不知道」——
但**必须是显式声明**，不能是沉默，更不能是编造。

```python
class Finding(BaseModel):
    citations: list[Citation]
    insufficient: bool = False     # 资料里确实没有相关内容

class AnswerPoint(BaseModel):
    citations: list[Citation]
    insufficient: bool = False

class AcceptanceItem(BaseModel):
    citations: list[Citation]
    insufficient: bool = False
```

校验口径相应改成 `_grounded()`：

```python
def _grounded(item) -> bool:
    """有原文依据，或者显式声明了资料不足。"""
    return bool(item.get("citations")) or bool(item.get("insufficient"))
```

- `V1` / `V3` / `V5` 都按这个口径判定 —— 有就查真伪，没有就必须声明
- `V2` 只校验**实际存在**的引用；一条引用都没有时不再判否（否则"诚实说不知道"会被否决到失败）
- 至于「声明资料不足是不是在偷懒」——那是**语义判断**，交给审查器，运行时管不了

**实测**（`mock` 离线，两个真实场景，均 1 轮通过、0 次否决）：

```
场景 A  资料覆盖了问题      → 12 条引用全部逐字命中，3 个分点都有依据
场景 B  资料答不上这个问题  → 0 条引用，3 个分点显式声明「资料不足」
```

两个场景都**没有编造、没有漏答**，各自给出了它该给的答案。

## 8. 验证结果

```
Python 编译                 ✅ 18 个文件
前端 JS 语法（Node）        ✅
契约 + 引用自检             ✅ 13/13
Web 端到端自检              ✅ 15/15（两个真实场景）
      场景 A 资料覆盖问题        → 1 轮通过 · 12 条引用全部逐字命中 · 0 次否决
      场景 B 资料答不上问题      → 1 轮通过 · 0 条引用 · 3 个分点声明「资料不足」
      两个场景都不编造、都不漏答、都以 done 结束
      无资料建任务被正确拒绝（400 need_material）
```

### 实施中发现的四个真 bug（都是跑起来才暴露的）

1. **`DROP TABLE ... RETURNING` 不是合法 SQL** —— 建表脚本的重置逻辑报错。
2. **适配器把 Citation 对象丢了** —— mock 模式直接传 `Citation` 实例，
   而 `coerce_citations` 只放行 dict/str，导致引用全空、链路一路否决到失败。
3. **`chunk_id` 是全局主键** —— 每次提问都生成 `D1-1`、`D1-2`…
   第二次提问就撞主键被 `DO NOTHING` 丢掉，资料插不进去。
   已把主键改成 `(global_task_id, chunk_id)`。**只跑一次永远发现不了。**
4. **「资料答不上来」时会被否决到失败** —— V2 要求"整条链路必须有引用"、
   V5 要求"验收条件必须有引用"，于是诚实地回答"资料不足"反而被判不合格。
   已引入 `insufficient` 显式声明通道，并让 V2 只校验实际存在的引用。

## 9. 想换成真实知识库怎么办

现在的 `source_chunk` 存的是用户当场贴的原文。要接真实知识库，只需换掉"资料从哪来"这一步：

| 现在 | 换成 |
| --- | --- |
| 前端把资料原文贴进来 | 后端从向量库 / 文档库 / 网页检索出片段 |
| `sources.build_chunks()` 按空行切段 | 按检索返回的 chunk 直接建 `source_chunk` 行 |
| 其余（契约、8 条不变量、硬门禁、回流、账本） | **完全不用改** |

因为一致性机制只依赖「有一段可逐字校验的原文」，**不关心这段原文是用户贴的还是检索来的**。
