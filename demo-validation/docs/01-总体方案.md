## 1. 目标与非目标

### 1.1 目标

1. 用 **LangGraph 1.x** 编排 Planner / Researcher / Executor / Reviewer 四角色协作。
2. 把文章里的「三对齐」——**同一个任务、同一份事实、同一套状态**——变成可运行、可观察的代码。
3. 提供 **Web 界面**，实时展示协作链路：谁交给谁什么、依据哪一版、谁否决了谁、状态如何推进。
4. 让「否决 → 回流 → 重做」在演示中**稳定可复现**，不依赖 LLM 随机出错。
5. 落地运行时保障：版本号、证据引用、验收条件、幂等键、租约、状态机、事件账本。

### 1.2 非目标（明确不做，控制复杂度）

- ❌ 不接真实监控 / 日志 / 发布系统 —— 证据源为内置 mock 数据，但**带版本和时间**（`commit-a` / `commit-b`，不同时间点指标）。
- ❌ 不做多用户、鉴权、权限体系。
- ❌ 不做分布式部署、消息队列、Kafka。
- ❌ 不追求 Agent 数量 —— **只有 4 个角色**，不引入 Supervisor/Swarm 等额外抽象。
- ❌ 不做前端工程化 —— 无 npm、无打包，单个 HTML 文件。

### 1.3 一句话概括设计主张

> **LLM 负责"判断下一步做什么"，运行时负责"证明这一步确实发生过"。**
> 四个角色的输出都必须是一份**带版本、带证据引用、可被校验**的结构化契约，
> 而不是一段自然语言。校验器不通过，Reviewer 不允许 approve。

## 2. 演示案例：线上 `user-service` 变慢排查

直接沿用文章里的例子——直观、好讲、天然包含"版本"与"时间窗"这两个一致性要素。

### 2.1 输入

```json
{
  "title": "user-service P99 劣化排查",
  "alert": "user-service P99 从 200ms 涨到 1.2s",
  "time_window": ["14:00", "16:00"],
  "repo": "user-service"
}
```

### 2.2 事实锚点（snapshot）

整条链路**只认一个 snapshot**，所有 Agent 的产物都必须标注它：

```json
{
  "commit": "commit-b",
  "time_window": ["14:00", "16:00"],
  "repo": "user-service"
}
```

### 2.3 内置证据源（mock，但可追溯）

| 证据 ID | 类型 | 版本 | 时间 | 内容要点 |
| --- | --- | --- | --- | --- |
| `slowlog#14:32` | 慢查询日志 | `commit-a` | 14:32 | `orders` 表全表扫描，单次 980ms |
| `pgstat#14:35` | 指标 | `commit-a` | 14:35 | `seq_scan` on orders 激增 |
| `pgstat#14:40` | 指标 | `commit-a` | 14:40 | 连接池等待 0ms |
| `deploy#13:40` | 发布记录 | `commit-a` | 13:40 | 发布：调整连接池参数 |
| `deploy#15:20` | 发布记录 | `commit-b` | 15:20 | 发布：回滚部分索引优化 |
| `pgstat#15:35` | 指标 | `commit-b` | 15:35 | **连接池等待 340ms，活跃连接打满** |
| `slowlog#15:40` | 慢查询日志 | `commit-b` | 15:40 | 语句本身 < 10ms，**但排队 600ms** |
| `config#15:20` | 配置 | `commit-b` | 15:20 | `max_connections` 由 200 → 50 |

### 2.4 场景里埋的两个根因（这是"稳定否决"的关键）

- **14:00–15:20**：`orders` 表缺索引 → 慢查询。
- **15:20 之后**：`commit-b` 把 `max_connections` 改小 → **连接池排队**才是主因。

因此，一个只修 `orders` 索引的 Executor 产物，**无法解释 15:35 之后的指标** ——
Reviewer 可以基于**证据本身**判定"修复未覆盖全时间窗"，触发回流。
这不是靠 LLM 心情，而是靠**数据 + 校验器**确定性触发。

## 4. 一致性模型（本方案的核心）

### 4.1 三对齐

| 对齐目标 | 载体 | 在本系统里的体现 |
| --- | --- | --- |
| **同一个任务** | `global_task_id` + `sub_task_id` | Planner 拆出的每个子任务有稳定 ID；`agent_task` 主键三元组 `(run, sub_task, attempt)` 保证不重复认领 |
| **同一份事实** | `snapshot` + `evidence_refs` | 全链路冻结同一个 snapshot；每条结论必须引用 `evidence` 表里真实存在的证据 ID |
| **同一套状态** | `TaskState` + `version` | 共享状态是唯一交接对象；每次推进 `version+1`，旧版本更新被拒绝 |

### 4.2 七条一致性不变量（确定性校验，`app/validators.py`）

| ID | 不变量 | 违反后果 |
| --- | --- | --- |
| `V1_snapshot_pinned` | 所有产物的 `based_on` 必须等于 run 的 snapshot | 否决回流 |
| `V2_evidence_exists` | 所有 `evidence_refs` 必须真实存在于 `evidence` 表 | 否决回流（**防编造证据**） |
| `V3_finding_has_evidence` | 每条 `finding` 至少 1 条证据 | 否决回流 |
| `V4_artifact_cites_findings` | `artifact` 必须引用它所依据的 `finding` 证据 | 否决回流 |
| `V5_acceptance_covered` | 每条验收项必须有证据支撑 | 否决回流 |
| `V6_version_monotonic` | 状态 `version` 单调递增，拒绝过期更新 | 丢弃过期写入 |
| `V7_idempotent_side_effect` | 写操作必须带幂等键 | 拒绝执行 |

> **硬门禁**：`V*` 只要有一条 fail，Reviewer 节点**不允许**输出 `approve`，
> 即使 LLM 坚持要放行 —— 由运行时强制改写为 `veto` 并记入 `blockers`。

### 4.3 结果状态机（结论级）

```
候选 ──► 已验证 ──► 进入最终结果
  │
  ├──► 冲突 ──► 汇总器标为待处理线索（不进入最终结果）
  └──► 已否决 ──► 回流重查
```

### 4.4 任务状态机（运行级）

```
created → planning → researching → executing → reviewing
                          ▲                        │
                          └──── veto（回流, version+1, attempt+1）────┘
                                                   │ approve
                                                   ▼
                                                 done

异常分支：executing → failed（可重试）
                    → unknown（状态未知：先查远端，不盲目重放）
```

## 5. Agent 角色设计

四个角色各司其职，**每个角色的输出都是一个 Pydantic 契约**（详见 `docs/02`）。

### 5.1 Planner（规划器）

| 项 | 内容 |
| --- | --- |
| 输入 | 告警 + snapshot |
| 输出契约 | `PlannerOutput{plan_reason, sub_tasks[]}` |
| `SubTask` 字段 | `sub_task_id` / `title` / `depends_on` / `parallelizable` / `inputs_required` |
| 一致性职责 | 划定**任务边界**；标记依赖与可并行性（回应"为什么拆"） |
| 提示词要点 | 必须区分"可并行"与"强依赖"；每个子任务必须写清"需要什么输入" |

### 5.2 Researcher（研究员）

| 项 | 内容 |
| --- | --- |
| 输入 | `sub_tasks` + snapshot + **证据源全文**（mock 数据） |
| 输出契约 | `ResearcherOutput{findings[]}` |
| `Finding` 字段 | `claim` / `status`（候选/已验证/冲突/已否决）/ `evidence_refs` / `assumptions` |
| 一致性职责 | 产出**带来源的结论**；区分"已确认"与"仍在猜"（回应"交什么"） |
| 硬约束 | 允许引用**不存在**的证据 ID —— 这正是 `V2` 要抓的演示点 |

### 5.3 Executor（执行器）

| 项 | 内容 |
| --- | --- |
| 输入 | `findings` + snapshot |
| 输出契约 | `ExecutorOutput{artifact}` |
| `Artifact` 字段 | `based_on_commit` / `covers_time_window` / `changes[]` / `evidence_refs[]` / `acceptance[]` / `verify_command` |
| 一致性职责 | 产物必须**锚定版本与时间窗**、**引用依据的证据**、**自带验收条件** |
| 硬约束 | 不许只说"已完成"；必须给出可执行的 `verify_command` |

### 5.4 Reviewer（审查器）

| 项 | 内容 |
| --- | --- |
| 输入 | `artifact` + `findings` + **校验器报告** + 原始证据 |
| 输出契约 | `ReviewerOutput{decision, checks[], blockers[], reason}` |
| 一致性职责 | 逐条核对验收项 → 能否回到原始证据 → 是否覆盖全时间窗 |
| 关键能力 | 输出 `veto` 时，**必须改变后续路由**（回流）与 `version`；否则只是评论 |

## 6. LangGraph 图设计

### 6.1 共享状态（唯一的交接对象）

```python
class TaskState(TypedDict, total=False):
    global_task_id: str
    snapshot: dict          # 事实锚点，全程冻结
    status: str             # 运行级状态机
    version: int            # 乐观锁版本
    round: int              # 回流轮次
    sub_tasks: list[dict]
    findings: list[dict]
    artifacts: list[dict]
    consistency: dict       # 校验器报告（运行时"证明"）
    review: dict
    events: Annotated[list[dict], operator.add]   # 节点追加，供前端时间线
```

### 6.2 节点与边

```
START
  │
  ▼
planner ──► researcher ──► executor ──► reviewer ──┬── approve ──► END
   ▲                                               │
   │                                               └── veto ──┐
   └──────────────────────────────────────────────────────────┘
                     (回流: round+1, version+1)
```

- **节点**：`planner` / `researcher` / `executor` / `reviewer`
- **条件边**：`reviewer → route_after_review(state)` 返回 `"approve"` 或 `"veto"`
- **回流目标**：`researcher`（补证据）或 `executor`（改修复），由 `review.blockers` 决定
- **上限**：`MAX_ROUNDS=3`，超过则 `status=failed` 并保留现场（防止死循环）

### 6.3 持久化

| 用途 | 方案 |
| --- | --- |
| 图状态持久化 | `langgraph-checkpoint-postgres` 的 `AsyncPostgresSaver`，`thread_id = global_task_id` |
| 一致性账本 | 自建 `agent_run` / `agent_task` / `agent_event` / `finding`（见 `docs/02`） |
| 权威事实 | 自建 `evidence` 表（启动时由 mock 数据灌入） |

> 两项互补：checkpoint 保证**图能断点恢复**；账本保证**人能审计状态推进**。

## 7. 运行时保障机制

| 机制 | 实现要点 | 对应文章观点 |
| --- | --- | --- |
| **版本冻结** | run 创建时写死 snapshot，节点只读不写 | "基于哪一版"必须可回答 |
| **证据引用** | 结论只允许引用 `evidence` 表中存在的 ID | 摘要不能替代事实出处 |
| **硬门禁** | 校验器 fail ⇒ 强制 veto，覆盖 LLM 判断 | 模型负责判断，运行时负责证明 |
| **幂等键** | 写操作键 = `run_id : sub_task_id : 动作` | 状态未知 ≠ 失败 |
| **租约** | `lease_until`，过期才可被接管 | 调度器重启不重复派发 |
| **子任务级重试** | `attempt` 落在子任务，不重跑全局 | 带副作用的动作不能重复 |
| **事件账本** | `agent_event` 有序追加，SSE 直接读 | 完成是状态机里的状态 |
| **上限保护** | `MAX_ROUNDS` 与超时 | 防止死循环 |


### 8.2 关键可视化点（对应一致性三对齐）

| 可视化 | 强化的一致性概念 |
| --- | --- |
| 每张卡片右上角标 `基于 v3` | **同一份事实**：所有卡片来自同一 snapshot |
| 证据 chip 可点击 → 抽屉显示原文 | **可追溯**：结论能回到事实出处 |
| 结论带 `候选 / 已验证 / 冲突 / 已否决` 徽标 | **结果契约**，非自然语言拼接 |
| 回流用**红色曲线箭头 + `v+1`** | **同一套状态**：否决真的改变了状态 |
| 右侧"一致性校验"面板实时刷新 7 条不变量 | **运行时证明** |
| 右侧"账本表"显示 `version/attempt/lease/idem_key` | 幂等、租约、子任务级重试 |

### 8.3 交互

- **新建排查任务**：表单预填 `user-service` 告警，一键启动。
- **实时刷新**：SSE 推送，节点开始/结束即插卡，无需轮询、无需手动刷新。
- **重放历史**：点左栏任一 run，从账本重建完整时间线（一致性可审计）。

## 9. 与文章「四问」的映射（面试讲解用）

| 文章四问 | 系统里的落点 | 界面上看哪里 |
| --- | --- | --- |
| ① 为什么拆？ | Planner 的 `sub_tasks`（边界 + 依赖 + 可并行） | 时间线第 1 张卡 |
| ② 交接什么？ | 共享 `TaskState`（snapshot/evidence/assumptions/acceptance） | 右栏"共享状态"面板 |
| ③ 谁拍板？ | Reviewer + 结果状态机 + 条件路由 | 红色回流箭头 |
| ④ 凭什么算完成？ | `acceptance` 逐条有证据 + 校验器全绿 | 右栏"一致性校验"面板 |

**面试讲解顺序建议**：
先展示一次正常链路 → 再展示被否决回流的那一次 → 打开校验面板说明"这不是模型说了算" →
最后打开账本表说明版本/幂等/租约。

## 10. 风险与取舍

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| LLM 输出不符合契约 | 解析失败中断 | `with_structured_output` + Pydantic 校验 + 失败重试 1 次，仍失败则回落为"候选"结论并标记 |
| LLM 可能编造证据 ID | 演示失真 | `V2` 校验器确定性拦截（这本身是演示亮点） |
| 演示时未触发回流 | 讲不清重点 | `DEMO_MODE=on` 时注入"首轮只覆盖部分时间窗"的约束，保证稳定否决一次 |
| `max_connections` 等敏感词误伤 | 无 | 全部为 mock 数据，不接真实系统 |
| DeepSeek 网络不可达 | 无法运行 | 提供 `LLM_MODE=mock` 离线兜底（返回预置的结构化输出），保证界面链路仍可演示 |
| PG 不可达 | 无法持久化 | 启动时 `/api/health` 明确报错；不使用内存兜底，避免"看起来一致其实没落账" |
