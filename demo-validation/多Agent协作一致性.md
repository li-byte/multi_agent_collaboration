# 多 Agent 协作如何保持一致性

> 来源：《面试官：讲一讲多 Agent 协作如何保持一致性》— 架构师（JiaGouX）
> 主题：多 Agent 系统中，任务 / 事实 / 状态三者的对齐与一致性工程
> 沉淀时间：2026-09-15

## 一、核心论点

**多 Agent 最危险的状况不是意见不同，而是每个 Agent 都在自己的世界里正确。**

- 一致 ≠ 让所有 Agent 说同一个答案。Researcher 与 Reviewer 本就该有分歧，甚至应有人专门提反例。
- 真正要对齐的三件事：
  1. **同一个任务** —— 处理的是不是同一个任务
  2. **同一份事实** —— 依据的是不是同一份事实
  3. **同一套状态** —— 推进的是不是同一套状态

> 推理可以有分歧，协议不能含糊。

## 二、四个关键追问（面试主线）

围绕 user-service 变慢这条链，把架构边界讲完整：
**为什么拆、交什么、依据哪一版、冲突怎么处理、失败从哪里恢复、凭什么算完成。**

### 第一问：任务为什么要拆成多个 Agent？

**并行 ≠ 把任务复制几份同时发出去。**

- 先分清楚两件事：
  - 任务本身能不能并行（看任务依赖）
  - 系统是不是一开始就固定了并行关系（看编排方式）
- 无强依赖 → 可静态拆子任务；执行中不断产生新线索 → 需动态编排（暂停 / 合并 / 重拆 / 补派）。
- 粒度问题：太粗 → 子任务重叠；太细 → Agent 互相等待补上下文。
- 防止同一子任务被两个 Agent 认领：给任务稳定身份 + 条件认领 + 租约 + 唯一约束，把"不重复"变成数据库可检查的事实。
- 拆分收益要覆盖成本：通信、上下文复制、等待、重试、汇总。

> 数据佐证（Google Research 实验口径，非通用比例）：
> - 可并行探索的金融分析任务：集中式多 Agent 较单 Agent 基线 **+80.9%**
> - 严格顺序的 PlanCraft 任务：多 Agent **-39% ~ -70%**
> → 结论：**任务结构比 Agent 数量更重要。**
>
> Anthropic 的多 Agent 研究系统采用宽度优先拆法：把可独立搜索的方向交给不同 Agent；前后高度依赖同一上下文的工作不适合拆开。

### 第二问：第一个 Agent 到底交给下一个 Agent 什么？

**传的不是聊天记录，而是"拿来就能继续工作的状态"。**

Researcher 说"慢在数据库"只能当线索，不能直接交给 Executor 改代码。Executor 至少需要：
- 问题发生的时间段
- 对应的 SQL / 哪段日志
- 引用的哪一版日志、当前代码与配置版本
- 已排除的方向
- 改完后的验收方式

**交接状态的结构（非固定格式，关键是别把六类东西混成一段自然语言）：**

```
Task
 ├─ 基于哪一版：snapshot / commit
 ├─ 已确认什么：evidence refs
 ├─ 仍在猜什么：assumptions
 ├─ 允许做什么：capability / constraints
 ├─ 产物在哪里：artifact refs
 └─ 怎样算完成：acceptance
```

**三类东西要分开：**
- 聊天记录 = 历史
- 摘要 = 当前工作集的一部分
- 代码库 / 测试系统 / 部署平台 / 业务数据库 = 某类事实的权威来源（摘要不能替代事实出处）

**任务执行记录（agent_task）核心字段：**

```
agent_task
 ├─ global_task_id / sub_task_id
 ├─ agent_id
 ├─ input_snapshot
 ├─ status / version
 ├─ attempt / lease_until
 └─ result_ref
```

字段作用：global_task_id 串起全局任务；sub_task_id 识别具体工作；attempt 区分尝试；version 拒绝过期更新；lease_until 表示认领失效时间。

### 第三问：两个 Agent 结论不一样，谁来拍板？

**分歧本身有价值；麻烦的是它们基于不同现实却被当成同一现实汇总。**

典型错位：
- 一个基于 commit-a，另一个基于 commit-b
- 一个引用 14:00 日志，另一个引用 16:00 指标
- 一个看到发布前配置，另一个看到发布后配置

**汇总不能只做文本拼接：**
- 让每条结论能回到 输入快照 / 来源 / 证据 / 产物
- 结果打标：候选 / 已验证 / 冲突 / 已否决，汇总器据此决定取舍
- 定义版本化结果契约，或用适配器把异构输出统一成同一种结构（协议不是让 JSON 整齐，而是让系统知道"基于什么、证明了什么、还缺什么"）

**共享记忆的写入顺序：** 先作"带来源的候选主张"保存 → 经 实体 / 关系 / 时间 / 来源 检查 → 再进可复用事实层。共享记忆记录引用和状态，不能取代权威数据源。

**Reviewer 必须能改变后续状态：** 回到原始证据、明确否决条件、有权退回重查 / 换路线 / 缩小范围 / 请求人工确认。审查改变不了后续动作，就只是评论。参考 Google Antigravity Teamwork：候选生成 → 压力测试 → 综合 → 迭代，被否决路线与反对意见影响下一轮。

### 第四问：Agent 说"完成了"，系统为什么相信它？

**完成 = 状态机里的一个状态，不是 Agent 回复里的一个句号。**

验收要看证据而非措辞：
- 测的是哪个 commit、执行了什么命令、退出码、报告在哪
- Reviewer 有没有留 blocker
- 测试之后工作区有没有继续变化

**超时的正确姿势：** 读操作超时可重试；写操作（发消息 / 发布 / 改库 / 退款）超时 ≠ 未发生。→ 先带幂等键，超时后查远端状态，按"未执行 / 已执行 / 状态未知"分支；能安全重放才重调，否则保留人工确认或补偿入口。**状态未知 ≠ 失败。**

**失败重试要落在子任务层：**
- 子任务状态：未执行 / 执行中 / 已完成 / 失败 / 状态未知
- 只重试失败子任务；状态未知先查远端
- 重放用 `global_task_id + sub_task_id + 业务动作` 组成幂等键，由唯一约束 / 下游接口保证不产生二次副作用
- 调度器重启后：租约 + 心跳，租约内任务归当前 Agent，过期才可被接管，接管前确认执行记录，避免两个执行者同时操作

**稳定起点：** 全局任务状态机 + 子任务最终一致性补偿（不意味着都要上分布式事务）。

## 三、与传统架构的对应关系

| 多 Agent 概念 | 传统架构对应物 |
| --- | --- |
| 任务边界 | 服务边界 |
| 交接对象 | API 契约 / 领域事件 |
| 权威事实 | 主数据 |
| 状态推进 | 工作流 |
| 超时恢复 | 幂等命令 / 补偿事务 |

> 多 Agent 没绕开分布式系统的老问题，只是把执行者从服务和线程换成了会自主判断的 Agent。

## 四、Harness 的职责（文章结论）

模型负责判断下一步做什么，运行时负责证明这一步确实发生过。Harness 需要承担：
1. 给 Agent 正确的工作集
2. 限制它能做的动作
3. 记录真实发生的结果
4. 失败后把任务带回可继续处理的状态

## 五、生产环境观测指标

- 任务重复率
- 状态冲突率
- 补偿成功率
- 调度可用性
- 状态未知积压量
- 归档前确认：无活动租约 / 重试 / 补偿（保留时长由业务与审计决定）
