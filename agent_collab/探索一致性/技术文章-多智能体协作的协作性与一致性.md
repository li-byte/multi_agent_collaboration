# 多智能体协作：协作是因，一致是果

> 多个 Agent 一起干活，最容易翻车的不是"它们吵起来了"，而是**每个 Agent 都在自己的世界里正确**。
> 本文把这件事拆成两个维度、15 种失效方式、14 个机制和 12 条验收判据，并给出一份可直接自评的清单。

---

## 一、一个很常见的翻车现场

假设你让三个 Agent 协作完成一件事：出一份季度经营分析。

- **A（取数）**：从两个系统各取了一部分数据，拼成一份"事实"。
- **B（写结论）**：发现某个口径的数据缺失，觉得"按常识应该是这样"，于是自己补了一个值继续往下写。
- **C（审校）**：只看到 B 写好的成稿，逐句核对了文字表述，签了"通过"。
- **系统**：因为超时重试了一次，A 又被触发了一遍。
- **收口**：B 和 C 对某个增长率的判断不同，谁也说服不了谁，最后**以最后生成的版本为准**。

这件事从每个 Agent 的视角看都没错：A 确实取到了数，B 的推测"合理"，C 的审校"尽责"，重试是"必要的容错"。

但这件事作为一个整体，已经烂了：

| 现场表现 | 它其实是什么问题 |
|---|---|
| A 用了两个来源的数据，版本不一致 | **事实分裂**——各存一份，都"正确" |
| B 把推测当数据用了 | **假设污染**——未验证的推断进了证据链 |
| C 看不到 A、B 的中间过程 | **协作不可见**——审校只能看结果，看不出依据 |
| 重试导致 A 又跑了一遍 | **重复做功**——若这一步有副作用，就是事故 |
| 判断不同，最后"以最新为准" | **假收敛**——两个答案并存，只是没人再提 |

这个现场值得记住一句话：**多个 Agent 的失败，很少是"某一步做错了"，而是"每一步都对，合起来不对"。**

## 二、问题的本质

多智能体系统最危险的情况不是 Agent 之间意见不同，而是**每个 Agent 都在自己的世界里正确**。

它真正需要对齐的只有三件事：

- **同一个任务**：不重复派发、不丢失、可追踪；
- **同一份事实**：依据明确、版本清晰、假设与已验证分离；
- **同一套状态**：推进有证据、失败可恢复、完成可验证。

而"对齐"要解决两个不同性质的问题，混在一起谈就永远谈不清：

1. **怎么让它们一起把事做成？** —— 这是**协作**问题（过程）；
2. **怎么保证做成之后只有一个答案？** —— 这是**一致性**问题（结果）。

**协作是因，一致是果。**

只做一致性（加日志、加校验、加锁），你得到的是一台**能精确记录失败的机器**；
只做协作（分工、并发、多轮对齐），你得到的是**一场越来越热闹、越来越收不了口的讨论**。

## 三、把目标拆成两个维度

### 3.1 协作性：描述"过程"，分四级

| 等级 | 名称 | 含义 | 做不到会怎样 |
|---|---|---|---|
| H1 | **分工清晰** | 每个 Agent 知道自己的职责与能力边界 | 谁都以为别人会做，或两人做同一部分 |
| H2 | **交互有序** | 派发—承诺—移交—求援—应答都有去向与回音 | 任务悬空、交接断链、重复做功 |
| H3 | **相互校验** | 交叉验证是常规动作，质疑被当作贡献 | 单点结论无人复核，错误直达结果 |
| H4 | **协商共识** | 分歧靠交换依据协商，谈不拢就保留并上报 | 表面一致，内部两个真相 |

注意这里的递进关系：**协作不等于"不重复"**。不重复、不遗漏只是 H2 的要求；真正的协作从 H1 的"分工"开始，到 H4 的"协商"才算完整。

### 3.2 一致性：描述"结果"，分四级

| 等级 | 名称 | 含义 | 做不到会怎样 |
|---|---|---|---|
| C1 | **事实一致** | 所有 Agent 依据同一份事实（同版本、同来源） | 一方用旧版、一方用新版，各自都对，结论打架 |
| C2 | **状态一致** | "进行到哪、谁在做、做完没有"只有一个答案 | 两个 Agent 都以为自己在做同一件事 |
| C3 | **结论一致** | 冲突有确定的收敛路径，对外只有一个答案 | 两个结论并存，最后谁嗓门大听谁的 |
| C4 | **过程一致** | 事后可重建全过程，换个时间看解释不变 | 出了分歧只能靠回忆复盘 |

### 3.3 两个维度的关系

```
      协作性（过程 · 引擎）              一致性（结果 · 护栏）
      ┌────────────────────┐           ┌────────────────────┐
      │ H1 分工清晰         │           │ C1 事实一致         │
      │ H2 交互有序         │ ──产生──► │ C2 状态一致         │
      │ H3 相互校验         │           │ C3 结论一致         │
      │ H4 协商共识         │           │ C4 过程一致         │
      └────────────────────┘           └────────────────────┘
```

- **协作机制是引擎**：它让多个 Agent 真正把事做成；
- **一致性机制是护栏**：它保证做成的事只有一份答案、可追溯、不重复。

## 四、失败有 15 种方式

只要承认 Agent 是**各自独立、具有不确定性、且会被重跑**的，下面这些失效就必然发生，而且**不因你换什么框架而消失**。

### 4.1 协作失效（过程侧）

| 编号 | 失效 | 典型表现 |
|---|---|---|
| X1 | 分工不清 | 谁都以为别人会做；或两人做同一部分，无人收口 |
| X2 | 承诺缺失 | 任务被"派发"了，但没人真正认领与负责 |
| X3 | 求援无门 | 卡住了没人可问，或问了没回音，只能自己猜 |
| X4 | 校验缺位 | 结论由单点产出，无独立复核 |
| X5 | 协作不可见 | 不知道别人在做什么、做到哪，导致重复或撞车 |
| X6 | 分歧被压制 | 有异议不说、或说了被搁置，用"表面一致"换推进 |

### 4.2 一致性失效（结果侧）

| 编号 | 失效 | 典型表现 |
|---|---|---|
| F1 | 事实分裂 | 各存一份事实，都"正确"，版本不同 |
| F2 | 假设污染 | 未验证的推断当结论用，下游继续往上盖楼 |
| F3 | 重复做功 | 重复派发、重跑、两个执行者都以为该自己做 |
| F4 | 交接断链 | 上游做完没人通知，或下游没等到就跑了 |
| F5 | 冲突无收敛 | 两个结论并存，没有规则决定听谁的 |
| F6 | 完成无判据 | 都认为做完了，但没人能证明真做完了 |
| F7 | 副作用重复 | 外部世界被改变了两次，且不可撤销 |
| F8 | 中断失忆 | 崩溃后不知道那一步做没做完，重跑等于重复做功 |
| F9 | 事后说不清 | 无法回答"这条结论依据哪一版事实、谁给的" |

### 4.3 关键发现：协作失效是一致性失效的上游

这是整篇文章最值得带走的一张表：

| 协作失效 | 会导致 | 机理 |
|---|---|---|
| X1 分工不清 | F3 重复做功、F4 交接断链 | 没有明确归属，就没人负责收口 |
| X2 承诺缺失 | F4 断链、F6 完成无判据 | 无人负责，就无人能声明"完成" |
| **X3 求援无门** | **F2 假设污染** | **没人可问，只能把猜测当结论用** |
| X4 校验缺位 | F5 冲突无收敛 | 只有一个视角，就没有冲突可收敛，只有错误 |
| X5 协作不可见 | F1 事实分裂、F3 重复做功 | 看不见彼此，就各自记一份、各自做一遍 |
| X6 分歧被压制 | F5 冲突无收敛 | 分歧没被提出，问题在收口时集中爆发 |

**推论**：多数一致性事故，根因在协作层。只加固护栏而不修引擎，问题会持续复现。

尤其注意 **X3 → F2**：我们通常把"假设污染"当成模型爱瞎猜的问题，其实更常见的成因是**它没地方问**。

## 五、需要 14 个机制

### 5.1 一致性机制（护栏，8 个）

| 编号 | 机制 | 缺了会退化成 |
|---|---|---|
| M1 | 单一事实源 + 事实版本化（假设与已验证分开存放） | "共享一段文本"，照样各读各的版本 |
| M2 | 任务的唯一身份 + 认领（唯一且有期限） | "谁先跑谁做"，重跑即双跑 |
| M3 | 结构化交接契约：我基于什么｜我做了什么｜我留了什么｜你还需要什么 | "把全部上下文塞给下一个"，信息过载且不可校验 |
| M4 | 结论收敛规则（依据版本可比才合并） | "最后一个说话的人赢" |
| M5 | 完成判据前置（开始前就定死、可判定） | "看起来差不多了" |
| M6 | 副作用账本 + 唯一标识（不确定时先对账） | "事后翻日志"，防不住第二次 |
| M7 | 步骤两态留痕（开始过 / 完成了） | "崩了就整体重来" |
| M8 | 全过程留痕与回放（含因果与依据） | 有日志但拼不出因果 |

### 5.2 协作机制（引擎，6 个）

| 编号 | 机制 | 缺了会退化成 |
|---|---|---|
| M9 | **能力与角色声明**：我能做什么 / 不能做什么 / 依赖什么 | "能者多劳"，强者全包、能力边界无人知晓 |
| M10 | **任务承诺机制**：任务要被"接受"（可拒绝、可让出），接受即负责且有期限 | "任务悬空"，看起来都安排了，实际没人负责 |
| M11 | **求援与应答通道**：有去向、有期限、有回音 | "各猜各的"，假设悄悄进入证据链 |
| M12 | **交叉校验**：关键结论由独立视角复核，质疑同等记账 | 单点产出，错误直达结果 |
| M13 | **协商与共识规则**：先交换依据再协商，禁止用压制换表面一致 | "表面一致"——对外一个答案，内部两个真相 |
| M14 | **协作可见性**：谁在做、做到哪、缺什么，随时可见 | "各干各的，最后合并"，合并时才发现撞车 |

一句话记忆：

> 给多智能体**一本共同的账本**（M1、M6、M7、M8）、**一套共同的规矩**（M2、M3、M4、M5），以及**一张能协作的网**（M9~M14）。

### 5.3 几个最容易做错的细节

- **M1 的常见误用**：用"共享上下文 / 共用提示词"冒充事实共享。它既无版本也无来源，等于没有。
- **M3 的常见误用**：把完整聊天记录当交接。信息越多，责任越模糊。
- **M4 的常见误用**：用投票、取最新、取高置信度来决定冲突。**在事实版本不可比时，这些都是假收敛。**
- **M6 的常见误用**：把幂等责任推给被调用的下游。
- **M7 的常见误用**：只在成功时记录——崩溃点成为盲区。
- **M10 的常见误用**：把"已通知"当作"已认领"。
- **M11 的常见误用**：把"记录了一个疑问"当成"发起了求援"（没有去向与回音）。
- **M12 的常见误用**：把"再问一遍同一个 Agent"当成交叉校验。

## 六、机制之间是有层级的，不能跳级

```
协作引擎（产生）                          一致性护栏（收口）
M9  能力声明  ┐                          ┌ M1  单一事实源 + 版本
M14 可见性    ├─► M10 承诺 ─► M11 求援 ─►├ M2  唯一身份 + 认领
              │        └─► M12 交叉校验 ─►├ M3  交接契约
              └────────► M13 协商共识   ─►├ M4  收敛规则
                                         ├ M5  完成判据
                                         ├ M6  副作用账本
                                         ├ M7  两态留痕
                                         └ M8  留痕与回放
```

**M9 与 M14 是最下层的前提**：知道自己能做什么、知道别人在做什么。
没有 M14 的可见性，M1 的"单一事实源"根本建立不起来——因为你连谁在写都不知道。

**下层不成立，上层无法补救。** 这也是为什么"先上日志系统，协作后面再说"通常行不通。

## 七、怎么判断你真的做到了

### 7.1 一致性判据（结果侧）

| 编号 | 判据 |
|---|---|
| A1 | 任一时刻，只有**一份事实、一个状态答案** |
| A2 | 任一结论都能回答"**依据哪一版事实、谁在什么时候给的**" |
| A3 | 同一动作不会因重跑或重派**被执行两次**，且可**检测** |
| A4 | 中途中断后，接手者**无需重新问一遍**，也不重复做功 |
| A5 | 冲突有**确定的收敛路径**；不可比的分歧**被保留**而非被默默合并 |
| A6 | "做完了"**在开始前就已定义**，且可以判定 |

### 7.2 协作性判据（过程侧）

| 编号 | 判据 |
|---|---|
| A7 | 每个 Agent 的**能力边界与职责**显式，分工决策有据可依 |
| A8 | 每件事有**明确负责且自愿接受**的 Agent，且有期限 |
| A9 | 求援**有去向、有期限、有回音**，无静默消失 |
| A10 | 关键结论由**独立视角**复核，质疑被记录与处理 |
| A11 | 分歧被**显式提出并协商**，而非被压制、搁置或默默合并 |
| A12 | 任一时刻能回答"**现在有谁在做、做到哪、缺什么**" |

### 7.3 一张自评清单（可以直接拿去打分）

| # | 自查问题 | 是/否 |
|---|---|---|
| 1 | 事实是否只有一个写入点，且每条带来源与版本？ | |
| 2 | 假设是否与已验证事实分开存放，且默认不进入下游依据？ | |
| 3 | 每件事是否有稳定身份，"谁在做"是否唯一且有期限？ | |
| 4 | 交接是否结构化（依据/产出/遗留/判据），而非聊天记录？ | |
| 5 | 冲突是否有确定收敛路径，不可比时是否显式保留分歧？ | |
| 6 | 完成条件是否在开始前确定，且可判定？ | |
| 7 | 对外部世界的改变是否有唯一标识与明确终态？不确定时是否先对账？ | |
| 8 | 每个步骤是否同时记录"开始过"与"完成了"？ | |
| 9 | 是否能重建"谁、何时、基于什么、做了什么决定"，且结果稳定？ | |
| 10 | 每个 Agent 的能力边界与职责是否显式声明？ | |
| 11 | 每件事是否都有自愿接受、明确负责的 Agent？ | |
| 12 | 求援是否有去向、有期限、有回音？ | |
| 13 | 关键结论是否由独立视角复核，异议是否被记录？ | |
| 14 | 分歧是否被显式提出并协商，而非被搁置？ | |
| 15 | 任一时刻是否都能看到"谁在做、做到哪、缺什么"？ | |

**这 15 问里有任何一个是"否"，说明你缺的不是模型能力，而是机制。**

## 八、几条容易被忽略的边界

| 边界 | 说明 |
|---|---|
| **一致 ≠ 正确** | 全体可以一致地错。机制保证"唯一、可追溯"，不保证结论对 |
| **一致 ≠ 强一致** | 跨外部系统只能做到"可对账"，做不到"同时成功" |
| **协作 ≠ 一致同意** | 协作的目标是"依据充分、路径清晰"，不是"人人满意"；分歧可以被保留 |
| **协作有成本** | 分工、校验、协商都要付出沟通成本。**过度协作**（无止境对齐）同样会拖垮系统，所以机制强度应该分级 |
| **收敛不由设施保证** | 如果两个 Agent 永远谈不拢，只能靠"判据不满足"或"人来终止"；设施只保证不糊弄 |
| **假设无法被消灭** | 只能被隔离（标注且不进入强制链），不能被消除——这是设计选择，不是妥协 |
| **设施不替 Agent 思考** | 它保证依据唯一、过程可查、动作不重复、协作有序，但不产生任何判断 |

特别提醒最后一条：**不要指望一套一致性机制能提升模型结论的正确率**。它是工程约束，不是智力增强。

## 九、反面清单

| 反模式 | 问题所在 |
|---|---|
| "我们共享上下文，所以事实是一致的" | 无版本、无来源的共享不构成事实一致（违反 M1） |
| "任务已经派出去了" | 派发不等于承诺，无人负责收口（违反 M10） |
| "一个人出结论，其他人点头" | 无独立视角，错误直达结果（违反 M12） |
| "有异议先搁置，先往下走" | 压制分歧换表面一致，问题在收口时爆发（违反 M13） |
| "各干各的，最后合并" | 过程黑箱，撞车与事实分裂不可避免（违反 M14、M1） |
| "谁强谁全干" | 能力不声明、不互补，多智能体只剩成本（违反 M9） |
| "有疑问就自己先假设一下" | 求援没走通，假设被当结论用（违反 M11、M1） |
| "我们记了详细日志" | 有事件无因果、无依据，仍答不出 A2（违反 M8） |
| "让每个 Agent 自己保证幂等" | 把公共纪律下放为个体责任，成本随数量增长且不可证明 |
| "冲突时取最新 / 投票决定" | 事实版本不可比时属假收敛（违反 M4） |
| "流程跑完了就算完成" | 用过程代替结果判据（违反 M5） |
| "超时就重试" | 对不可撤销的副作用而言，重试即事故（违反 M6） |
| "崩了就整体重跑" | 重复做功、重复副作用（违反 M7） |

## 十、结语

多智能体的一致性，本质不是"让 Agent 更聪明"，而是给它们三样东西：

- **一本共同的账本**：事实与状态唯一、动作与依据可追溯；
- **一套共同的规矩**：交接不断链、冲突有出路、完成有判据；
- **一张能协作的网**：能力说得清、任务有人认、卡住有人帮、结论有人验、分歧能协商、彼此看得见。

如果只记一句话：

> **协作是因，一致是果。**
> 先有分工、承诺、求援、校验与协商，才谈得上"同一件事、同一份事实、同一套状态"。
