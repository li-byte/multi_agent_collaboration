# agent_collab 多智能体协作一致性底座 · 设计方案 v2（按评审修正）

> **文档定位**：架构与流程设计，不含具体代码实现。
> **本版依据**：《方案评审-中间件定位可行性与风险论证》的 6 项契约、12 条风险与不变量压缩建议。

## 1. 定位与边界

### 1.1 一句话定位

> LangGraph 决定「下一步做什么」，agent_collab 记录并证明「这一步确实发生过、依据是哪一版事实、副作用只执行了一次」。

### 1.2 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 业务层：Agent 节点（Planner / Researcher / Executor / Reviewer）│
├──────────────────────────────────────────────────────────────┤
│ 编排层：LangGraph（图定义、路由、并行扇出、checkpoint、interrupt）│
├──────────────────────────────────────────────────────────────┤
│ 一致性中间件：agent_collab（本方案）                            │
│   任务认领 API · 事实账本 · 交接握手 · 副作用三态账本 · 不变量自检 │
├──────────────────────────────────────────────────────────────┤
│ 存储层：PostgreSQL / Memory                                    │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 职责划分

| 组件 | 负责 | 不负责 |
|---|---|---|
| LangGraph | 节点/边、条件路由、并行控制流、图级 checkpoint、人工审批 `interrupt` | 不关心任务是否被重复认领、不验证事实版本 |
| **agent_collab** | 认领 API（CAS+租约）、事实版本账本、交接版本闭包校验、副作用三态账本、不变量自检、一致性报告与回放 | **不提供调度器**、不做图恢复、不执行工具、不做业务仲裁 |
| 业务 Agent | 按 Handoff 执行、产出候选结论、调用外部系统、显式 reserve/commit | 不管理任务状态机、不保证幂等 |

### 1.4 不做的事（诚实边界）

- 不内置 LLM、不内置工具实现、**不内置调度器**、不做分布式调度
- 不自动从函数参数推断副作用 key（碰撞会静默导致防重失效）
- 不保证 Agent 结论正确，只保证过程可审计、可复现、副作用可对账
- 不提供跨库强一致事务（跨服务用 Outbox/Saga，**超出本底座边界**）
- **`capability / constraints` 只是传给 Agent 的只读声明**，框架无法强制（它不执行工具）
- **Memory 档不能证明任何并发类不变量**（见 §5 验证档位列）

## 2. 接入契约（新增）

### 2.1 构造

```python
collab = Collab(
    prefix="crm",              # 必填：隔离前缀（表前缀 + namespace 列 + 内存 key 前缀）
    store="memory",            # 默认 memory；可选 "postgres"
    # dsn="postgresql://...",  # store="postgres" 时必填
    lease_seconds=60,          # 认领租约
    fail_policy="write_closed",# 写路径 fail-closed，读路径 fail-open（§6）
)
```

启动即校验：`prefix` 合法（`^[a-z][a-z0-9_]{1,30}$`）、`store ∈ {memory, postgres}`、postgres 必须有 DSN —— 不合法直接 `ConfigError`。

### 2.2 十个调用（中间件的全部对外面）

| # | 调用 | 作用 | 写库 | 失败语义 |
|---|---|---|---|---|
| 1 | `Collab(...)` | 声明前缀与后端 | 0 | `ConfigError` |
| 2 | `with collab.step(run_id, sub_task_id, agent, attempt) as ctx` | 两阶段落盘 `started/committed`；异常时自动 revoke 占位并写 `failed` | 2 | **fail-closed** |
| 3 | `ctx.fact(key, value, kind, source_type, based_on)` | 写事实 | 1/条 | 缺 `based_on` 阻塞 |
| 4 | `ctx.assumption(text)` | 写假设（`kind=assumption`），不进强制链 | 1/条 | 不阻塞 |
| 5 | `ctx.reserve(key, target)` | 副作用占位（返回可复用状态） | 1 | 重复 key 返回既有状态 |
| 6 | `ctx.commit(tok, evidence)` | 结账（**证据必填**） | 1 | 空证据 → 记 `unverified` |
| 7 | `ctx.revoke(key, reason)` | 纠错：确认外部未发生 / 结果未知 | 1 | append-only 留痕 |
| 8 | `ctx.handoff(to_agent)` | 渲染结构化交接单（含 `based_fact_versions`） | 0–1 | 版本闭包缺失阻塞 |
| 9 | `collab.verify(sub_task_id)` | 下游入口握手：校验版本闭包与步骤相位 | 1 读 | 不一致 → 按 §7.2 处理 |
| 10 | `collab.accept(sub_task_id, acceptance)` | 机检验收（checker 由使用者注册） | 1 读 + 1 写 | 未通过不置 `committed` |
| 11 | `collab.claim(sub_task_id)` | **可选**：CAS 认领，不提供调度器 | 1 条件更新 | 未抢到返回 False |
| 12 | `collab.report(run_id)` / `collab.timeline(run_id, depth=3)` | 一致性报告 / 回放 | 只读 | **fail-open + 降级标记** |

### 2.3 关联键（写死）

| 键 | 来源 | 约束 |
|---|---|---|
| `run_id` | **= LangGraph `thread_id`** | 全链路唯一且不回退；禁止重跑时换新 id |
| `sub_task_id` | 使用者的 Planner 生成 | 稳定身份，重跑不变 |
| `agent` | 节点名 | 与图节点名一致 |
| `attempt` | LangGraph `retry_policy` / 中间件认领递增 | **进唯一键**（节点重跑是常态） |

> 所有唯一约束统一为 `(namespace, run_id, sub_task_id, agent, attempt, idempotency_key)`。

### 2.4 同步 / 异步双入口

图既可能走 `invoke` 也可能走 `ainvoke`（本机实测两者均存在）。因此：

- 同步：`collab.step(...)` / `collab.claim(...)`
- 异步：`collab.astep(...)` / `collab.aclaim(...)`（内部走线程池桥或原生异步驱动）

**禁止**在 async 节点里调用同步入口（会阻塞事件循环）。

### 2.5 写放大预算

单步数据库往返 **≤ 4 次**（`started` + `committed` + 事实 + 副作用）。超出即视为设计问题；`started` 与事实允许合并批量提交。

## 3. 数据模型（沿用 v1，补强）

### 3.1 任务模型（agent_task）

`global_task_id` · `sub_task_id` · `parent_sub_task_id` · `owner_agent` · `status(pending→running→committed/failed/unknown/cancelled)` · `version` · `attempt` · `lease_until` · `input_snapshot_ref` · `based_fact_versions` · `result_ref`

**补强**：`attempt` 进唯一键；认领为**条件更新**（`WHERE version=? AND (status='pending' OR lease_until<now())`），影响行数=1 才算认领成功；**中间件不扫描、不派发**。

### 3.2 事实模型（fact）

`ref` · `key` · `kind(observation/derivation/assumption/decision)` · `value(摘要或正文引用)` · `source_type(authoritative/model/human)` · `produced_by_step` · `based_on` · `snapshot_ref` · `superseded_by` · `valid`

**执行点（v1 缺失）**：`verify()` 与交接单渲染时**真正过滤** `kind=assumption` 与 `superseded_by != null` 的事实；下游不得使用"最新"这种模糊引用。

**补强**：`snapshot_ref` 的采集接口必须由使用者提供（见 §7.5 契约 6）。

### 3.3 交接单模型（Handoff）

`sub_task_id` · `input_snapshot` · `evidence_refs` · `assumptions` · `capability` · `constraints` · `artifacts` · `acceptance` · `based_fact_versions`

**修正措辞**：`capability / constraints` 是**给 Agent 的只读声明**，用于让 Agent 自己判断能做什么；框架**不执行、不拦截、不保证**它们被遵守。若需要运行时强约束，必须由使用者在自己的工具层实现。

### 3.4 副作用账本（effect_ledger）

`run_id + sub_task_id + action + target + idempotency_key`（唯一键）· `status(reserved → executing → succeeded/failed/unknown → committed/revoked/compensated)` · `evidence`（`committed` 必填）

**补强**：`unknown` 的出口只有一个 —— 使用者注册的 `reconcile(effect)` 回调（见 §4.7）。

### 3.5 候选主张模型（proposal）

`sub_task_id` · `claim` · `evidence_refs` · `based_fact_versions` · `confidence` · `status(candidate → validated/conflict/rejected/accepted_as_fact)`

**修正**：中间件**只标记 `conflict`**（依据：`based_fact_versions` 不一致 / 时间窗不一致），**不仲裁**。`accepted_as_fact` 由使用者的 evaluator/arbiter 决定并调用 `ctx.fact(...)` 落账。

## 4. 关键流程

### 4.1 认领（由使用者触发，中间件只提供 API）

```
使用者侧（队列 / 图入口 / 定时任务）：
  1. 取出一批候选 sub_task（这是使用者的调度逻辑）
  2. 对每个候选调用 collab.claim(sub_task_id, owner=agent, attempt=n)
  3. claim 内部：单条条件 UPDATE（CAS + 租约），返回是否抢到
  4. 抢到 → 构建 Handoff → 进入图节点；没抢到 → 跳过（不是错误）
```

**边界**：中间件不扫描、不轮询、不派发、不做优先级。图恢复时若租约已过期，**必须重新 claim 才能继续**（防止两个执行者同时跑同一 sub_task）。

### 4.2 交接握手

```
下游节点入口：
  1. collab.verify(sub_task_id) → 校验 based_fact_versions 中每条事实存在且 valid
  2. 不一致（被 supersede / 缺失）→ 拒绝执行，交回上游重新生成 Handoff
  3. 一致 → 注入节点状态，开始执行
```

### 4.3 步骤两阶段与写序（写死）

```
图 checkpoint 之前                    中间件账本
    │                                     │
    │                          ① 写 started（含 attempt）
    ├── 节点执行 ──────────────────────────┤
    │                                     │
    │                          ② 写 committed（含产出引用）
    └── ③ 图 checkpoint ───────────────────┘
```

**规则**：账本先行、图后行。若 ② 失败 → 节点不得返回成功（fail-closed）；若 ③ 失败 → 账本已 committed，图恢复时重新执行该节点会被 `attempt/幂等键` 挡住，不产生重复副作用。

### 4.4 冲突标记（不仲裁）

```
1. 多个 Agent 产出 proposal
2. 中间件检查 based_fact_versions 是否一致
   - 一致 → 各自落账，status=candidate
   - 不一致 → status=conflict，并在一致性报告标记
3. conflict 的处置（重查 / 降级 / 人工）由使用者决定
```

### 4.5 完成验收

```
子任务可标记 committed 的必要条件：
  a. acceptance 条件由使用者注册的 checker 机检通过
  b. 该子任务的写类副作用无 unknown 残留
  c. 产出基于的 based_fact_versions 全部 valid
```

### 4.6 失败与恢复

- 子任务 `failed` → 局部重试，`attempt+1`，复用已 `committed` 的结果
- 步骤 `started` 未闭合（torn_step）→ 中间件报告；**是否重跑由图/使用者决定**，中间件只保证"重跑时不会重复副作用"
- 图恢复 → 先 `verify()` 再执行；租约过期需重新 `claim`

### 4.7 `unknown` 对账

```python
def reconcile(effect) -> str:      # 使用者注册；返回 committed | failed | unknown
    ...
```

- 未注册 `reconcile` → `unknown` 只能进人工队列，并在报告标注「N 个副作用状态未知」
- `reconcile` 返回 `unknown` → 保持未知，**不允许**据此推进下游

## 5. 一致性不变量（N-01 ~ N-12 + 验证档位）

| 编号 | 不变量（断言） | 验证档位 |
|---|---|---|
| N-01 | 步骤相位合法：不存在 `committed` 先于 `started`，也不存在未闭合 `started` | memory + PG |
| N-02 | 事实不可变：写入后 `ref` 不变，新版本产生新 `ref` | memory + PG |
| N-03 | 交接闭包：Handoff 缺 `based_fact_versions` 即阻塞 | memory + PG |
| N-04 | 副作用唯一：`UNIQUE(namespace, run_id, sub_task_id, action, target, idempotency_key)` | memory + PG |
| N-05 | 假设隔离：`kind=assumption` 不进入强制证据链，也不被 `verify()` 接受 | memory + PG |
| N-06 | 唯一认领：同一 `sub_task` 同时最多一个 `owner`，且 `owner` 与 `lease` 一致 | **仅 PG 多进程** |
| N-07 | 迟到消息防护：状态更新带 `version/attempt` 条件，过期写被拒绝 | **仅 PG 多进程** |
| N-08 | 局部重试：失败只重该 `sub_task`，`attempt` 递增且复用已成功结果 | PG（内存档只能验证"不重跑已成功步骤"） |
| N-09 | 完成可验证：`acceptance` 机检通过 + 无 `unknown` 残留副作用 | memory + PG |
| N-10 | 回放可重建：`timeline` 仅凭 `step_log + effect_ledger` 可重建（**不含 LLM 内容确定性**） | memory + PG |
| N-11 | 写放大预算：单步数据库往返 ≤ 4 | memory + PG |
| N-12 | 关联键一致：账本 `run_id` 与图 `thread_id` 映射唯一且不回退 | PG |

> v1 的 C-11（审计可追溯）降级为报告字段 `audit_traceability`；C-16（Outbox）移出本底座，另立文档。
> **selfcheck 只有把档位跑对，绿才算数**：memory 档全绿只证明 N-01~N-05、N-09~N-11。

## 6. 中间件自身的故障策略

| 路径 | 策略 | 理由 |
|---|---|---|
| 写路径（`fact/assumption/reserve/commit/revoke/claim`） | **fail-closed**：中间件不可用即拒绝操作、拒绝推进 | 宁可阻塞，也不漏账 —— 漏账即失去一致性卖点 |
| 读路径（`report/timeline/verify` 的读取部分） | **fail-open + 降级标记**：返回可用信息并标注「本次报告不完整」 | 观测能力不该成为编排的单点故障 |
| `step()` 退出 | 若 `committed` 写失败 → **节点视为失败**，不得返回成功 | 与 §4.3 写序一致 |

## 7. 与 LangGraph 的集成

### 7.1 桥接层

| 组件 | 职责 | 自动化程度 |
|---|---|---|
| `CollabStateGraph` | 包装节点：进入前 `verify()`、开始时 `started`、成功时 `committed` | 全自动 |
| `NodeCtx` | 注入节点 state，提供 `fact/assumption/reserve/commit/revoke` | 手动调用（刻意保留） |
| effect 上下文管理器 | 异常时自动 `revoke` 占位；key 仍由开发者显式给 | 半自动 |
| 异步适配 | `astep/aclaim` 供 `ainvoke` 链路使用 | 全自动 |

### 7.2 与图 checkpoint 的关系（不争权威）

- **LangGraph 负责「跑到哪」，agent_collab 负责「算不算发生过」** —— 两者不重叠、不互相同步状态机。
- 恢复流程：图恢复到节点 N → 节点入口调用 `verify()` → 若账本显示 N 为 `started` 未 `committed` → **由图的策略决定重跑或终止**，中间件只提供事实与门禁。
- 中间件**不实现**节点级恢复，也**不读写** LangGraph 的 checkpoint 表。

### 7.3 重跑语义

本机实测 `add_node(..., retry_policy=...)` 存在 → 同一节点被重跑是常态：

- `attempt` 必须进唯一键与 step_log
- 重跑时 `reserve()` 会命中既有 key → 返回 `reusable`，Agent 直接复用首次证据

### 7.4 人工审批

留在 LangGraph（`interrupt / Command`）。中间件只做两件事：记录"该审批已发生"、以及在无审批记录时拒绝把高危副作用置为 `committed`。

### 7.5 必须由使用者提供的 6 项契约

| # | 契约 | 缺了会怎样 |
|---|---|---|
| 1 | 关联键稳定传入（`run_id=thread_id`） | 账本分裂成多份 |
| 2 | `verify()` 入口握手被调用 | 下游可能基于被推翻的事实执行 |
| 3 | `reconcile(effect)` 回调 | `unknown` 无出口，C-15/N-09 不成立 |
| 4 | 异步链路使用 `astep` | 阻塞事件循环（R6） |
| 5 | `acceptance` checker 注册 | 完成验收退化为人工目测 |
| 6 | `snapshot_ref` 采集（代码版本/日志区间/指标区间） | 事实缺可复现锚点 |

## 8. 风险与应对（12 条）

| # | 风险 | 等级 | 应对 |
|---|---|---|---|
| R1 | 关联键不稳定（重跑/fork 换 run_id） | 🔴 | §2.3 写死映射；`run_id` 由调用方稳定传入 |
| R2 | `unknown` 无对账出口 | 🔴 | §4.7 `reconcile` 契约；无回调进人工队列 |
| R3 | 中间件故障语义未定 | 🔴 | §6 写 closed / 读 open + 降级标记 |
| R4 | 一致性窗口（图与账本写序） | 🔴 | §4.3 账本先行、图后行 |
| R5 | memory 档对并发类不变量是假绿 | 🟡 | §5 验证档位列；memory 档报告标注 |
| R6 | async 阻塞事件循环 | 🟡 | §2.4 双入口 |

## 11. 总结

本版把 v1 的「架构很完整但接不进来、绿得不明不白」两处短板补齐：

1. **接得进来**：§2 给出 1 构造 + 12 调用的窄腰接口、关联键、双入口、写放大预算；
2. **绿得明白**：§5 的 12 条不变量每条都标注了「在 memory 还是 PG 多进程档可被证明」；
3. **故障可控**：§4.3 写序 + §6 故障策略定死了「宁可阻塞也不漏账」，且不把观测能力变成编排的单点；
4. **边界不越**：不提供调度器、不执行工具、不仲裁、不碰图 checkpoint —— 只加一层调用。
