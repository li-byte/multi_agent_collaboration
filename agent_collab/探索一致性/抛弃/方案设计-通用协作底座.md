# agent_collab 多智能体协作一致性底座 · 设计方案

> **文档定位**：架构与流程设计，不含具体代码实现。描述系统“做什么、怎么做、为什么这么做”。
> **核心目标**：在 LangGraph 编排之上，通过 agent_collab 提供任务认领、事实版本化、交接闭包、副作用防重与完成验收的一致性保障。
> **设计依据**：参考多 Agent 协作面试四问（任务不重复派、交接对象、结论仲裁、完成验收）及生产级不变量 C-01~C-18。

---

## 1. 设计目标与原则

### 1.1 要解决的核心问题

多 Agent 系统最危险的情况不是 Agent 之间意见不同，而是每个 Agent 都在自己的世界里正确。真正需要对齐的是三件事：

- **同一个任务**：不重复派发、不丢失、可追踪
- **同一份事实**：依据明确、版本清晰、假设与已验证分离
- **同一套状态**：推进有证据、失败可恢复、完成可验证

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **推理可有分歧，协议不能含糊** | Agent 结论可以不同，但交接格式、事实来源、状态更新必须结构化 |
| **模型负责判断，运行时负责证明** | LLM 决定下一步做什么，agent_collab 记录并证明这一步确实发生过 |
| **显式优于隐式** | 副作用占位、事实写入由开发者显式调用，不黑盒自动生成 |
| **局部失败局部重试** | 子任务级失败不影响全局，不盲目重跑整条链路 |
| **版本化一切** | 任务、事实、交接、副作用均有版本或幂等键，支持回放与审计 |

### 1.3 不做的事（诚实边界）

- 不内置 LLM、不内置工具实现、不内置分布式调度
- 不自动从函数参数推断副作用 key（避免碰撞导致静默防重失效）
- 不保证 Agent 结论正确（只保证过程可审计、可复现）
- 不提供跨库强一致事务（跨服务用 Outbox/Saga 补偿）

## 2. 总体架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│ 业务层：Agent 节点（Planner/Researcher/Executor/Reviewer）│
│ 负责推理、调用工具、产生候选结论                          │
├─────────────────────────────────────────────────────────┤
│ 编排层：LangGraph                                        │
│ 负责图定义、路由、并行扇出/扇入、checkpoint 恢复、人工审批 │
├─────────────────────────────────────────────────────────┤
│ 一致性中间件：agent_collab                               │
│ 负责任务认领、事实黑板、交接单、副作用账本、不变量检查     │
├─────────────────────────────────────────────────────────┤
│ 存储层：PostgreSQL / Memory                              │
│ 持久化任务、事实、交接、副作用、步骤日志、Outbox 事件      │
└─────────────────────────────────────────────────────────┘
```

### 2.2 职责划分

| 组件 | 职责 | 不负责 |
|------|------|--------|
| LangGraph | 定义节点/边、条件路由、并行控制流、状态快照恢复 | 不关心任务是否被重复认领、不验证事实版本 |
| agent_collab | 任务唯一认领、事实版本管理、交接闭包、副作用两阶段提交、不变量自检 | 不定义业务图结构、不执行具体工具调用 |
| 业务 Agent | 根据 Handoff 执行任务、产出候选结论、调用外部系统 | 不管理任务状态机、不保证幂等 |

## 3. 核心数据模型设计

### 3.1 任务模型（agent_task）

每个子任务拥有全局唯一身份，支持认领、租约、版本控制：

- **global_task_id**：一次用户请求的全局标识
- **sub_task_id**：子任务稳定身份（不因重跑而改变）
- **parent_sub_task_id**：支持动态重拆/合并
- **owner_agent**：当前执行者
- **status**：pending → running → committed / failed / unknown / cancelled
- **version**：乐观锁，每次状态变更递增
- **attempt**：第几次尝试（用于过期消息防护）
- **lease_until**：租约到期时间（防止僵尸占用）
- **input_snapshot_ref**：不可变输入快照引用
- **based_fact_versions**：本任务依赖的事实版本集合
- **result_ref**：产出物引用

**设计要点**：认领操作通过数据库条件更新（CAS）完成，不先读后写，确保同一时刻最多一个 Agent 拥有任务。

### 3.2 事实模型（fact / blackboard）

事实分为不同种类，避免假设混入已验证结论：

- **ref**：全局唯一引用，如 `resolver:db:slow:14:05@v2`
- **key**：业务键，如 `sales:2024`
- **kind**：observation（已观测）/ derivation（推导）/ assumption（假设）/ decision（决策）
- **value**：摘要或正文引用（权威源只存引用，不存全文）
- **source_type**：authoritative（权威源）/ model（模型产出）/ human（人工）
- **produced_by_step**：由哪个步骤产生
- **based_on**：依赖的事实引用+版本列表
- **snapshot_ref**：对应的代码版本、日志区间、指标区间
- **superseded_by**：被哪个新版本替代
- **valid**：当前是否有效

**设计要点**：假设（assumption）不得直接进入强制证据链；下游 Agent 必须基于明确版本的事实，不能使用“最新”这种模糊引用。

### 3.3 交接单模型（Handoff）

Agent 之间传递的不是聊天记录，而是结构化工作状态：

- **sub_task_id**：目标子任务
- **input_snapshot**：代码版本、日志区间、指标区间、排除假设
- **evidence_refs**：已确认事实的引用列表
- **assumptions**：明确标注的未证实部分
- **capability**：允许执行的动作（如 read_log / run_sql_readonly）
- **constraints**：禁止动作（如 drop / force_deploy）
- **artifacts**：产物引用（patch / report / test_result）
- **acceptance**：可机检验收条件（如 p95<200ms、tests green）
- **based_fact_versions**：所依据的事实版本集合

**设计要点**：节点开始处理前，必须验证 based_fact_versions 中所有事实存在且未被替代；否则阻塞并重新获取，不盲跑。

### 3.4 副作用账本模型（effect_ledger）

所有写类外部调用必须留痕：

- **run_id + sub_task_id + action + target + idempotency_key**：唯一键
- **status**：reserved → executing → succeeded / failed / unknown
- **succeeded → committed**（带证据）
- **failed → revoked / retried**
- **unknown → queried_remote → committed / failed / manual / compensated**

**设计要点**：写操作必须带幂等键；超时后先查远端状态，确认未执行才可重放；不可逆操作（退款/发布）默认需人工审批。

### 3.5 候选主张模型（proposal）

Agent 产出先存为候选，不直接写共享事实：

- **sub_task_id**：来源子任务
- **claim**：具体主张
- **evidence_refs**：支撑证据的事实引用
- **based_fact_versions**：基于的事实版本
- **confidence**：置信度
- **status**：candidate → validated / conflict / rejected / accepted_as_fact

**设计要点**：仲裁器根据证据版本、时间窗、配置版本判断是否可以合并；不同版本的事实导致的冲突不强行合并。

## 4. 关键流程设计

### 4.1 任务认领与执行流程

```
1. 调度器扫描 pending 且租约过期的 sub_task
2. 执行 CAS 更新：UPDATE agent_task SET owner=me, status=running, version=version+1
   WHERE sub_task_id=? AND version=? AND (status='pending' OR lease_expired)
3. 影响行数=1 → 认领成功；=0 → 被别人拿走或租约未到期，放弃
4. 认领成功后，构建 Handoff（含 input_snapshot、evidence_refs、acceptance 等）
5. 将 Handoff 注入 LangGraph 节点状态，启动执行
6. 执行中：步骤开始/成功/失败由 CollabStateGraph 自动记录
7. 执行完：更新 agent_task status，写结果引用
```

### 4.2 交接与事实对齐流程

```
1. 上游 Agent 完成处理，产出事实（write_fact）和候选结论
2. 构建 Handoff 对象：
   - 收集 based_fact_versions（所有依赖事实的当前版本）
   - 打包 evidence_refs
   - 明确 assumptions（未证实部分）
   - 定义 acceptance（可机检条件）
3. 下游 Agent 收到 Handoff，开始处理前：
   - 检查 based_fact_versions 中每个事实是否存在且 valid=true
   - 若有事实已被 supersede，则请求上游重新生成 Handoff
   - 若通过，注入节点状态，开始执行
```

### 4.3 冲突仲裁流程

```
1. 多个 Agent 产出候选主张（proposal）
2. 仲裁器（Arbiter）收集所有 proposal，检查：
   - 是否基于同一事实版本？（是→可比较；否→标记 conflict）
   - 是否在同一时间窗/配置版本下？（否→标记 conflict）
   - 证据是否充分？（不足→rejected）
3. 无冲突且证据充分→ accepted_as_fact，写入 blackboard
4. 有冲突→ 送 Reviewer 或人工，保留反例记录
5. 仲裁结果影响后续路由：conflict 时 router 不盲目继续，可触发重查或降级
```

### 4.4 完成验收与恢复流程

```
完成必要条件（全部满足才可标记 global_task=accepted）：
  a. 所有子任务 status=committed
  b. 每个子任务的 acceptance 条件全部机检通过
  c. 所有写类副作用有 committed 证据（unknown 必须转 manual/committed）
  d. Reviewer 基于同一 based_fact_versions 出 verdict

失败恢复：
  - 子任务 failed → 局部重试（最多 N 次），重试带新 attempt 号
  - 子任务 unknown → 查远端状态，确认未执行则重放，已执行则提交证据
  - 调度器重启 → 只接管 lease_until<now 且 status=pending/unknown 的任务
  - 整任务重跑 → 复用已 committed 的只读/幂等写结果，不重复执行
```

## 5. 一致性不变量（C-01 ~ C-18）

| 编号 | 不变量 | 保障机制 |
|------|--------|----------|
| C-01 | 步骤状态机合法 | step_log 记录 started/committed/failed，不允许跳跃 |
| C-02 | 事实版本不可变 | fact 写入后 ref 不变，新版本产生新 ref |
| C-03 | 交接闭包完整 | Handoff 必须包含 based_fact_versions，缺失则阻塞 |
| C-04 | 副作用唯一执行 | UNIQUE(namespace, run_id, idempotency_key) 约束 |
| C-05 | 假设不进入证据链 | kind=assumption 的事实不参与强制验证 |
| C-06 | 任务唯一认领 | CAS + 租约，同 sub_task 同时最多一个 owner |
| C-07 | 过期消息防护 | attempt/version/lease 更新带条件，旧消息不覆盖新状态 |
| C-08 | 局部重试隔离 | 子任务失败只重该 sub_task，不影响其他 |
| C-09 | 完成可验证 | 必须有 committed 证据 + acceptance 通过 |
| C-10 | 回放确定性 | timeline 基于 step_log + effect_ledger 可重建 |
| C-11 | 审计可追溯 | 所有写操作留痕，含操作者、时间、依据版本 |
| C-12 | 任务唯一认领（生产级） | 同 C-06，增加跨调度器场景的数据库唯一约束 |
| C-13 | Handoff 版本闭包 | 节点开始处理前校验 based_on 事实存在且未 supersede |
| C-14 | 假设与事实分离 | assumption 不写入 observation/decision 类型事实 |
| C-15 | 副作用三态证据 | 写类 effect 终态只能是 committed/failed/unknown→补偿 |
| C-16 | 跨服务事件不丢 | Outbox 模式：本地事务同时写业务状态+事件，后台投递 |
| C-17 | 局部重试 | 子任务失败重试带新 attempt，复用已成功结果 |
| C-18 | 过期消息防护（增强） | 状态更新带 version 条件，迟到消息被拒绝 |

`selfcheck` 工具可自动检测上述不变量是否满足，全绿为阶段交付门槛。

## 6. 与 LangGraph 的集成设计

### 6.1 集成模式

agent_collab 作为 **一致性中间件** 嵌入 LangGraph，而非反过来。LangGraph 负责控制流，agent_collab 负责账本。

### 6.2 桥接层设计

| 组件 | 职责 | 自动化程度 |
|------|------|-----------|
| **CollabStateGraph** | 继承 LangGraph StateGraph，自动包装节点，记录 step 生命周期（started/committed/failed） | 全自动，零侵入业务代码 |
| **NodeCtx** | 注入到节点 state 中，提供 fact/reserve/commit 等 API | 手动调用，但接口极简 |
| **effect 上下文管理器** | 可选的半自动辅助，异常时自动 revoke 副作用占位 | 半自动，key 仍由开发者显式指定 |

### 6.3 为什么不全自动

- **副作用防重若黑盒化**：自动生成 key 可能碰撞或为空，导致静默拦截或重复执行，违背核心卖点
- **事实自动写入**：节点返回值自动转 fact 会污染黑板（临时变量、调试信息混入）
- **设计原则**：让开发者意识到自己在做什么，关键决策点（reserve/commit）必须显式

### 6.4 并行与恢复

- **并行扇出**：独立子任务使用独立 sub_task_id 和 fact 前缀，通过 LangGraph 的 list reducer 避免状态覆盖
- **Checkpoint 恢复**：LangGraph PostgresSaver 负责节点级恢复；agent_collab 的 step_log 负责 torn_step 检测
- **人工审批**：通过 LangGraph `interrupt` / `Command` 实现高危操作（生产发布、退款）的人工确认

## 7. 风险评估与应对

| 风险 | 等级 | 应对策略 |
|------|------|----------|
| LangGraph 版本升级改内部 API | 中 | 桥接层用包装而非 monkey-patch，定期回归测试 |
| 并行 fact 命名冲突 | 中 | 强制 sub_task 前缀 + 版本约束 |
| 副作用 key 碰撞 | 高（若全自动） | 设计上禁止自动生成 key，强制显式指定 |
| Outbox 事件堆积 | 中 | 监控 outbox 表大小，设置 retention 策略 |
| 租约过期误判 | 低 | 可配置 lease 时长，结合心跳；过期前可续约 |
| 跨服务状态不一致 | 中 | Outbox + Saga 补偿，定期 consistency_report 巡检 |

## 8. 实施路径

| 阶段 | 内容 | 交付标准 |
|------|------|----------|
| ① 核心底座 | agent_task / fact / handoff / effect_ledger / step_log schema 与单写者内存实现 | 单元自测通过 |
| ② 桥接层 | CollabBridge + CollabStateGraph + NodeCtx + effect 管理器 | 可接入 LangGraph |
| ③ 单链验证 | resolver → researcher → executor → reviewer 跑通 | selfcheck C-01~C-11 全绿 |
| ④ 并行与人工 | 并行子任务 + interrupt 审批 + Outbox 跨服务 | selfcheck C-12~C-18 全绿 |
| ⑤ 生产加固 | unknown 对账、Saga 补偿、监控告警、归档策略 | 一致性报告持续通过 |

## 9. 总结

本方案将 agent_collab 定位为 **通信+协作+一致性证明底座**，LangGraph 定位为 **编排引擎**。两者通过 CollabStateGraph 桥接，实现：

- **任务不重复派**：CAS 认领 + 租约 + 唯一约束
- **交接传事实版本**：结构化 Handoff + 版本闭包校验
- **冲突按证据仲裁**：候选主张 + 版本化仲裁规则
- **完成凭验收+证据**：状态机 + acceptance 机检 + 副作用 committed 证明

设计上坚持“显式优于隐式”，关键决策点（副作用占位、事实写入）由开发者主动调用，避免黑盒化带来的静默风险。所有不变量可通过 `selfcheck` 自动验证，为生产环境提供可审计、可回放、可恢复的多 Agent 协作基础。
