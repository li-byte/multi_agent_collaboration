# 方案评审 · 中间件定位下的可行性与风险论证

| 项目 | 说明 |
|---|---|
| 评审对象 | `方案设计-通用协作底座.md`（agent_collab 多智能体协作一致性底座 · 设计方案） |
| 评审前提 | **不合并 LangGraph、不改图、不接管控制流**：agent_collab 只是架在 LangGraph 之上的一层调用（中间件） |
| 环境事实 | 本机实测：python 3.10.0、langgraph 1.2.11、langgraph-checkpoint-postgres 3.1.2、psycopg 3.3.5、pydantic 2.13.5、PostgreSQL 18.1 @192.168.10.101:5432 |
| 评审范围 | 只判三件事：① 这层调用插不插得进去 ② 插进去能不能被证明 ③ 代价多大 |
| 本文性质 | 论证与建议，**不修改设计文档原文** |

## 0. 结论摘要

| 档位 | 结论 |
|---|---|
| 作为**架构答辩稿** | 可行性高：四问齐全，模型扎实 |
| 作为**可复制的中间件** | **可行性中偏高**（上一轮按"要自己实现编排/恢复/调度"评为中偏低，澄清后上调） |
| 作为**生产级一致性服务** | 可行，但门槛不在功能，而在 6 个契约是否写死 |

三句话结论：

1. **边界是对的** —— 中间件只做「记账 + 校验 + 报告」，与 LangGraph 零冲突；前提是把 §4.1 的「调度器扫描」移出框架（中间件只暴露认领 API，不提供调度器）。
2. **模型是扎实的** —— task / fact / handoff / effect / proposal 五个模型比常见方案完整，fact 的 `kind` 与 `source_type`、effect 的 `unknown` 三态是真正的亮点。
3. **短板在接口纪律与验证矩阵** —— 18 条不变量里没有一条写清「在哪一档环境里可以被证明」，这会让 selfcheck 的绿变成假绿。

一句话：**这是一个窄腰中间件，成败在 6 个契约，不在功能多少。**

## 1. 环境事实（论证依据，本机实测）

| 事实 | 值 | 对方案的意味 |
|---|---|---|
| `langgraph` | 1.2.11 | 桥接层可做，无技术障碍 |
| `StateGraph / START / END` | 可用 | 节点包装（`add_node` 传 callable）可行 |
| `interrupt / Command` | 可用 | 人工审批留在 LangGraph，中间件不碰 |
| `PostgresSaver` | 可用（`setup / from_conn_string / put / get_tuple / list`） | 图级 checkpoint 由 LangGraph 负责，中间件**不重复实现** |
| 编译后图方法 | `invoke / ainvoke / stream / astream / get_state / update_state` | **图既可能走同步也可能走异步**，中间件必须双入口 |
| `add_node(..., retry_policy=...)` | 存在 | **同一节点被重跑是常态**，幂等键必须含 `attempt` |
| `pip` 依赖现状 | langchain 1.4.0 等已装 | 中间件自身仍应保持「只依赖 pydantic（+ psycopg）」 |

**结论**：桥接的障碍不在 API，而在语义 —— 见 §5 风险。

## 2. 定位澄清带来的判定变化（对照上一轮评审）

| 项 | 上一轮判定 | 澄清后判定 | 原因 |
|---|---|---|---|
| 双恢复真相源 | 🔴 最致命 | 🟡 **降级为「握手协议」** | 中间件不恢复执行，只提供 receipt；节点入口 `verify()` 一次即可，不需要争权威 |
| 队列语义 vs 图执行语义 | 🔴 架构错配 | 🟢 **降级为范围外** | 调度器不属中间件：只暴露 `claim()`，扫描与派发交回使用者的队列/图 |
| 缺接入面 | 🔴 致命 | 🟡 **降级为「压缩成窄腰 API」** | 作为中间件，接入面本就该只有 1 个构造 + 少量调用 |
| memory 档假绿 | 🔴 不变 | 🔴 **不变** | 并发类不变量在单进程内存里必然全绿 |
| `unknown→queried_remote` | 🔴 不变 | 🔴 **不变（硬缺口）** | 框架不执行工具，就必须由使用者提供对账回调 |
| 仲裁器业务语义入侵 | 🟡 不变 | 🟡 **不变** | 建议只做冲突标记，仲裁结论外置 |

**净效果**：要自己实现的东西少了一半（编排、并行、审批、图恢复全部不用做），**剩下的全是契约问题**。

## 3. 建议的「窄腰」接口（这层调用到底长什么样）

```python
collab = Collab(prefix="crm", store="memory")        # 或 store="postgres", dsn="..."

with collab.step(run_id, sub_task_id, agent="researcher", attempt=1) as ctx:
    ctx.fact("sales:2024", {...}, kind="observation", source_type="model")
    ctx.assumption("上游采样延迟可能影响结论")        # 显式标注，不进强制证据链
    tok = ctx.reserve("publish:doc42", target="doc/42")
    if tok.reusable:
        ...                                          # 已完成，复用首次证据
    ctx.commit(tok, evidence="HTTP 201 url=...")
```

| # | 调用 | 作用 | 写库 | 失败语义 |
|---|---|---|---|---|
| 1 | `Collab(prefix, store, dsn)` | 声明隔离前缀与后端 | 0 | `ConfigError`（启动即失败） |
| 2 | `with collab.step(...)` | 两阶段落盘 `started/committed`；异常时自动 revoke 占位并写 `failed` | 2 | 写路径 fail-closed |
| 3 | `ctx.fact(...)` | 写事实（`kind` / `source_type` / `based_on`） | 1/条 | 缺 `based_on` 时阻塞 |
| 4 | `ctx.assumption(...)` | 写假设，`kind=assumption`，不进强制链 | 1/条 | 不阻塞 |
| 5 | `ctx.reserve / commit / revoke` | 副作用三态 + 证据 | 1–2 | 重复 key 返回既有状态 |
| 6 | `ctx.handoff(to_agent)` | 渲染结构化交接单（含 `based_fact_versions`） | 0–1 | 版本闭包缺失则阻塞 |
| 7 | `collab.verify(sub_task_id)` | 下游入口校验版本闭包 | 1 读 | 失败即拒绝进入节点 |
| 8 | `collab.accept(sub_task_id, acceptance)` | 机检验收（用户注册 checker） | 1 读 + 1 写 | 未通过则不置 `committed` |
| 9 | `collab.report(run_id)` / `timeline(run_id, depth=3)` | 一致性报告 / 回放 | 只读 | 只读路径 fail-open + 降级标记 |
| 10 | `collab.claim(sub_task_id)` | **可选**：CAS 认领（不提供调度器） | 1 条件更新 | 未抢到返回 False |

**写放大预算：每步 ≤ 4 次数据库往返**（`started` + `committed` + 事实 + 副作用）。超了就是设计问题，不是实现问题。

## 4. 模块级可行性

| 模块 | 可行性 | 前置条件 / 必须补的东西 |
|---|---|---|
| 任务模型 §3.1（CAS + 租约 + attempt） | PG 下可行 | 只暴露 `claim()` API，**不实现调度器**；`attempt` 必须进唯一键 |
| 事实模型 §3.2（kind / source_type / based_on / superseded_by） | **可行且优于同类方案** | 需要执行点：`verify()` 里真正过滤 `assumption` 与 `superseded` |
| 交接单 §3.3 | 部分可行 | `capability / constraints` 只能作为**传给 agent 的只读声明**；框架不执行工具，声称"强制"就是虚的 |
| 副作用账本 §3.4（含 unknown） | 部分可行 | 必须补 `reconcile(effect)` 用户回调，否则 `unknown→committed/failed` 无路可走 |
| 候选主张 §3.5 / 仲裁 §4.3 | 有条件可行 | 建议框架只做「存取 + 版本闭包校验 + 冲突标记」，仲裁规则外置 |
| 完成验收 §4.4（acceptance 机检） | 可行 | checker 由使用者注册；中间件只落账 + 当门禁 |
| step_log / torn_step | 可行 | 与图 checkpoint 的关系用「握手协议」解耦，不争权威 |
| 报告 / 回放 §5 C-10 | 可行 | 建议补 `timeline(depth=)`，否则长 run 回放退化成全图遍历 |

## 5. 风险点（重排后 12 条）

### 🔴 高危（不定就不该开工）

**R1 关联键不稳定。** 所有唯一约束（`namespace+run_id+idempotency_key`、step_log、版本闭包）都挂在 `run_id` 上。若 LangGraph 的 `thread_id` 因重跑 / fork / 子图而变，账本会分裂成两份互不认识的记录。
→ 必须写死 `run_id ↔ thread_id` 的映射规则，并把 `sub_task_id / agent / attempt` 一起纳入关联键。

**R2 `unknown` 对账缺回调。** §3.4 要求「超时后先查远端状态」，§1.3 又声明「不内置工具实现」。框架不知道任何工具存在，凭什么查远端？
→ 契约层补 `reconcile(effect) -> committed | failed | unknown`，由使用者注册；缺该回调时 `unknown` 只能进人工队列，并如实标注。

**R3 中间件故障语义未定。** 中间件挂了，图是继续跑还是停？
→ 建议：**写路径 fail-closed**（拒绝 `commit`，宁可阻塞也不漏账），**只读路径 fail-open + 降级标记**（报告里标记「本次报告不完整」）。两者都必须在文档里写死，不能留白。

**R4 一致性窗口（写序未定）。** 图 checkpoint 成功但账本写失败（或反之）→ 出现「图认为发生、账本认为没发生」的窗口。
→ 顺序写死：**进节点先写 `started`，再执行；执行完先写 `committed`，再让图 checkpoint**。即"账本先行、图后行"。

### 🟡 中危（影响可信度或性能）

**R5 memory 档对并发类不变量是假绿。** C-06 / C-07 / C-12 / C-18（唯一认领、迟到消息防护、跨调度器唯一约束）在单进程内存里必然全绿。
→ 不变量表加「验证档位」列：这 4 条**只在 PG 多进程档可被证明**。

**R6 async 阻塞。** 图走 `ainvoke` 时，同步中间件会阻塞事件循环。
→ 提供双入口：`step()` / `astep()`，或同步实现 + `run_in_executor` 桥。

**R7 每步写放大。** 5 类写操作串行 = 每步 3–5 次往返，长链路下延迟显著。
→ 定预算（≤4 RT/step），`started` 与事实可合并批量提交。

**R8 仲裁误入业务语义。** §4.3 的「同一时间窗 / 配置版本 / 证据充分」是业务判断，写进框架会让通用性掉档。
→ 框架只标记 `conflict`，结论由使用者的 evaluator/arbiter 给。

**R9 不变量表重复与不可机检。**
→ 见 §6，18 条压到 12 条。

### 🟢 低危（补充即闭环）

**R10 `snapshot_ref` 采集接口缺失**：`code_version / log_range / metric_range` 由谁采集、什么格式，全文未定义，但 §3.2/§3.3 已把它当成既有能力。

**R11 子任务产生与注册流程未定义**：§4.1 从「扫描 pending」开始，但谁把 `sub_task` 写成 `pending` 没有说（且这属于使用者的 Planner，不属于中间件）。

**R12 LangGraph 版本漂移**：§7 已识别；补充——本机锁定 1.2.11，桥接层应只用 `StateGraph` 公开接口 + 自己的适配器，且**假设节点会被重跑**（`retry_policy` 存在即为证据）。

## 7. 必须补的 6 项契约（不补不能开工）

1. **关联键契约**：`run_id + sub_task_id + agent + attempt` 由调用方稳定传入，`run_id ↔ thread_id` 映射写死
2. **入口握手**：节点开始时 `verify()` 校验账本视角的步骤相位与版本闭包，不一致按 §5-R4 策略处理
3. **`reconcile` 回调**：`unknown` 副作用的远端对账，由使用者注册
4. **双入口**：同步 + 异步（`ainvoke` 场景）
5. **不变量验证矩阵**：每条标注 memory / PG 可验证性
6. **故障策略**：写路径 fail-closed / 读路径 fail-open + 降级标记，二者写进报告

## 8. 分期建议（按中间件边界重排，替代 §8 五阶段）

| 里程碑 | 内容 | 可被证明的不变量 | 交付门槛 |
|---|---|---|---|

## 9. 待决策的 5 个点

| # | 问题 | 建议 |
|---|---|---|
| 1 | 故障策略默认值 | 写路径 fail-closed、读路径 fail-open + 降级标记 |
| 2 | 是否提供 `claim()` 认领 API | 提供（用 PG），但**不提供调度器**；memory 档明确不支持跨进程认领 |
| 3 | `capability / constraints` 是声明还是强制 | **只能是声明**（框架不执行工具），文档措辞需改，避免"保障"二字 |
| 4 | 仲裁：内置规则还是只做冲突标记 | **只做冲突标记**，仲裁结论外置给使用者 |
| 5 | M3 LangGraph 桥接是否现在做 | 建议先 M1 + M2 落地，M3 视需要再上 |

---

## 10. 总结

1. **定位澄清后，这层中间件技术上无阻碍**：本机 LangGraph 1.2.11 的 `StateGraph / interrupt / Command / PostgresSaver / retry_policy` 均已实测可用，桥接不需要碰内部 API。
2. **风险从「工程实现」转移到「契约纪律」**：关联键、入口握手、`reconcile` 回调、双入口、故障策略、验证矩阵 —— 这 6 项不写死，功能做得再多也不成立。
3. **18 条不变量必须压到 12 条并标注验证档位**，否则 selfcheck 的绿是假绿，生产环境的绿才是真的。
