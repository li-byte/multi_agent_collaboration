# 多智能体协作 · 一致性验证

用 **LangGraph 1.x + LangChain 1.x** 搭的两套多智能体系统，回答同一个问题：

> **多个智能体协作时，怎么保证它们说的是同一件事？**

不是「让几个 Agent 最后说出同一个答案」，而是对齐三件事：
**处理的是不是同一个任务、依据的是不是同一份事实、推进的是不是同一套状态。**

> 推理可以有分歧，协议不能含糊。
> **模型负责判断，运行时负责证明。**

---

## 两个阶段

| | [`demo-validation`](./demo-validation) 🧊 | [`sql-agent`](./sql-agent) |
| --- | --- | --- |
| **做什么** | 通用问答：用户提问 + 给资料，四个智能体协作给答案 | 自然语言转 SQL：六个智能体协作生成 / 验证 / 执行 |
| **智能体** | 规划器 · 研究员 · 执行器 · 审查器 | 规划器 · SQL生成 · SQL验证 · SQL执行 · SQL修正 · 汇总审查 |
| **链路** | 固定：`规划 → 研究 → 执行 → 审查`（可否决回流） | **不固定**：每个智能体自己建议下一步，护栏决定能不能去 |
| **「同一份事实」靠什么** | 结论必须**逐字引用**用户给的原文 | SQL 里的表/字段必须在**真实 schema** 里、必须过 `EXPLAIN` |
| **有副作用吗** | 没有（只出文字） | **有**（改数据、删数据）→ 所以多了三层防线 + 人工确认 |
| **状态** | 🧊 已验证冻结 | ✅ 已完成并通过自检 |

---

## 各自证明了什么

这是全篇最重要的区分 —— **运行时能证明的东西是有边界的，边界外必须交给审查器。**

| | 运行时**能**证明 | 运行时**证明不了**（交给审查器） |
| --- | --- | --- |
| `demo-validation` | 这句话**确实逐字来自**你给的资料（字符串匹配，确定性） | 这句话是否**支持**得出的结论（语义） |
| `sql-agent` | 没越权、语法语义通过、验证过才执行、确认过才删（全部确定性） | 这条 SQL 是否**真的完成了**你的意图（语义） |

所以两套系统里，**校验器和审查器缺一不可**：一个是确定性的，一个是语义的。

## 共用的设计骨架

| 设计 | 说明 |
| --- | --- |
| **共享状态是唯一交接载体** | Agent 之间传的是可继续执行的工作状态，**不是聊天记录** |
| **硬门禁** | 运行时校验不过，模型的 `approve` 一律被改写成 `veto` |
| **事实来源必须可校验** | 引用要能定位到原文；表名字段名要能对上真实 schema |
| **权威层只读** | Agent 只能引用，不能改写事实 |
| **账本** | 租约 / 幂等键 / 乐观锁 / 事件回放 —— 与业务无关的通用能力 |
| **接入层适配器** | LLM 输出先归一化再进契约（嵌套对象被序列化成字符串、list 写成换行长文本……这些坑都踩过） |
| **两条防线分工** | 运行时抓结构，审查器抓语义 |

## 快速开始

两个项目各自独立，都用 Python 3.10：

```powershell
# ① 通用问答（冻结版）
cd demo-validation
$py = '..\.venv310\Scripts\python.exe'
& $py scripts\init_db.py
& $py run_server.py                    # → http://127.0.0.1:8000

# ② 自然语言转 SQL
cd ..\sql-agent
& $py scripts\init_db.py --reset       # 建角色 + 建两个库的表 + 灌种子数据
& $py scripts\check_guard.py           # 39 项静态防线自检
& $py scripts\check_isolation.py       # 两库隔离 + 权限兜底实测
& $py run_server.py                    # → http://127.0.0.1:8000
```

各自的详细说明与演示脚本见子项目的 `README.md`。

## 两个项目里最值得看的设计点

### `demo-validation` · 引用必须逐字命中

```python
class Citation(BaseModel):
    source_id: str   # D1-2 = 第 1 份资料的第 2 段
    quote: str       # 原文摘录，必须逐字一致
```

运行时把摘录去掉空白后去资料里做**字符串匹配**。容忍换行缩进，**不容忍改写**
（换全角半角、改标点、加省略号一律判否）。于是「依据必须真实存在」从一句口号
变成了一条**确定性可检查**的规则。

资料答不上来时，系统走 `insufficient` 显式声明通道 —— **沉默不行，编造更不行，
但"这份资料答不了"是合法的**。否则系统永远无法诚实地说"我不知道"。

### `sql-agent` · 三层安全防线

| 层 | 做法 | 作用 |
| --- | --- | --- |
| 应用层 | `sql_guard` 风险分级 + 危险语句扫描（先抹掉字符串与注释再扫） | 负责**解释与体验** |
| **数据库层** | 受限角色**只有 DML 权限，没有任何 DDL** | 负责**兜底与保证** |
| 执行沙箱 | 事务 + 超时 + 行数上限 + 影响行数阈值 | 限制爆炸半径 |

应用层拦截可以被绕过，**权限绕不过去**。`scripts/check_isolation.py` 实测：
删表 / 清空 / 改结构 / 建表 / 删库全被拒，提权尝试后权限快照完全一致。

### `sql-agent` · 链路不固定

```
候选集只有一个元素 → 直接去，模型的建议无效（硬边界）
候选集有多个元素   → 让模型在合法范围内自己选（真正的协作自由度）
```

只有两处是真的多选：**验证不通过**（小修 vs 重新理解问题）和
**执行失败**（改 SQL vs 重新拆问题）—— 该有分歧的地方允许分歧，
不该松的边界一条都不松。界面上会标出「⚠ 护栏改了模型的建议」。

## 踩过的坑（都已修，留档）

1. **Windows 上 uvicorn 会用 `ProactorEventLoop`**，而 psycopg 异步只能跑 `SelectorEventLoop` ——
   所以两个项目都用 `run_server.py` 自己拿循环，不要用 `uvicorn app.server:app`。
2. **DeepSeek 不支持 `response_format: json_schema`** —— `with_structured_output` 必须走 function calling。
3. **DeepSeek 会把嵌套对象序列化成 JSON 字符串** —— 接入层必须做适配。
4. **Python 3.10 上 LangGraph 的 `interrupt()` 不可用** ——
   上下文注入依赖 `asyncio.create_task(context=...)`，那是 3.11+ 才有的。
5. **主键设计要按「运行」唯一**，否则第二次提问撞主键、数据插不进去（只跑一次永远发现不了）。
6. **游标不推进会导致图死循环** —— 执行成功后必须推进。
